# Reflexes

## Reflexes

- When about to run /develop, read the governing spec's prerequisites and confirm each account, project, and credential it names already exists, because the spec gate only asks whether a decision is owed. (added 2026 08 21)
- When about to run a git command that discards working tree state (`reset --hard`, `checkout --`, `clean -f`, `restore`), read the full `git status` output first and account for every uncommitted file it shows, not just the one the command is meant to affect, because a hard reset touches the whole tree even when its stated purpose is narrow. (added 2026 08 23)
- When an edit to a spec records that something happened rather than deciding something, advancing a Status line to Accepted once the scope row is done or ticking a Follow up item the work satisfied, whoever is doing the closing may make it; /architect is needed only for edits that change what the spec decides. Verify the item's claim against the repo before ticking it, per the 2026 09 01 reflex. Across seven cases the Status line was advanced by /develop, by /scope, by a plain docs commit, and three times by direct instruction, none of them wrong, and on 2026 09 07 the same ambiguity left spec 0015's Follow up line 208 unticked after the work satisfying it had shipped. (added 2026 09 07)
- When recommending an answer to a multi option decision panel (architect, develop, or similar), say whether each option needs a note, and when one does, produce the literal note text in the same response for every option that needs one, written self contained when it goes in the Other field, because flagging and drafting are not two separable steps and Other replaces the selection rather than supplementing it. (added 2026 08 26)
- When a feature is marked done, grep docs/scope/scope.md for other features whose skipped or deferred boxes name it by number, and grep the specs of any feature whose scope row named a dependency on it, because a feature that just shipped can unblock a step recorded elsewhere as waiting on it, and a spec's own Follow-up checklist can describe that same now resolved blocker as open even when scope.md is correct. Feature 21's close out on 2026 09 01 left spec 0007's Follow-up list describing the custom domain blocker as open while scope.md was correct. (added 2026 08 27)
- When citing an identifier (commit SHA, pull request number, spec ID, acceptance criterion, issue number), include what it refers to in the same breath, for example `5779d91` (the orphaned "mark it done" commit) and not the bare SHA, because a reference the reader has to resolve elsewhere does not survive the conversation. (added 2026 08 27)
- When naming a range of features, specs, or ACs that another document must act on, resolve each member against the source before writing the range, because a plausible looking range is repeated back as an instruction and then applied literally. (added 2026 08 28)
- When writing or reviewing a verify step for a system-level guarantee (a CSS rule, a shared token, a cross-cutting default), assert the outcome the reader experiences, not the property the code sets, because a step that only checks its own implementation can confirm nothing but what the author already believes — this shape has produced two escaped bugs (the tv size/colour bug, then the reduced-motion delay bug). (added 2026 08 28)
- When splitting a change into one concern per commit in this repo, do not rely on `git add -p` for `docs/scope/scope.md` or a spec's `verify.md`, reconstruct each commit's file state directly instead, because those files routinely mix multiple concerns inside a single prose line, which hunk staging cannot separate. (added 2026 08 29)
- When a piece of work will produce commits, check the current branch and create one named for the commit type before the first commit, because `main` is branch protected and a direct commit to main strands there, needing reconstruction into a pull request afterwards. This happened twice on 2026 08 30. (added 2026 08 30)
- When verifying anything that depends on `supabase/config.toml`, read the running container's environment rather than the file, because `pnpm db:start` restarts existing containers instead of recreating them, so a stack can drift from the committed config and still pass its whole suite. (added 2026 08 31)
- When about to open a pull request, or when `.husky/pre-push` says this checkout is behind origin's main, read what actually landed before continuing, because the hook does the fetching and will name a changed rule file but cannot tell you whether it changes what you were about to write. That judgment is the half no hook covers, and it is the half that failed on 2026 08 31, when two pull requests nearly shipped the "Generated with Claude Code" footer a same day reflex had just forbidden. (added 2026 08 31)
- When reviewing a document whose authoring model is unknown or was produced by a tool outside this session's own lineage, run a panel of multiple independent reviewers rather than a single one, because an unidentified author cannot be excluded by name. When authorship is traceable, for example this session's own immediately prior output, a single reviewer excluding that named model is enough. (added 2026 08 31)
- When a spec is materially revised, re-review the revised spec before treating the revision as settled, because the fix for a review finding can itself be wrong and is not caught by re-reading. (added 2026 08 31)
- When correcting a claim that appears in more than one place in a document, fix every instance in the same pass and state which ones were checked, because a correction that touches only the first occurrence leaves the rest silently wrong. (added 2026 08 31)
- Before stating in a summary that a branch is pushed and current, check it against the actual remote, because describing the intended end state as already true is easy to do by habit and easy to get wrong. (added 2026 08 31)
- When acting on a follow up item in a spec, verify its claim against the repo before doing what it says, and correct the item when the claim is wrong, because follow up items are written at design time and never re-read, which makes them the staleest part of a spec: three of spec 0009's were wrong the first time anyone acted on them, two naming a skill whose own boundary forbids the work and one asserting a scope row lacked a clause it already had. (added 2026 09 01)
- When a feature's `Done when` names an edit to a file outside that feature's own code area, open that file and confirm the edit landed before ticking the feature done, because nothing in the feature's own work prompts that edit and no test covers it: feature 7's clause to retire the entry page's `working` placeholder went unmet under a done row on 2026 08 30, and the live homepage told every visitor that nothing worked for two days after sign in shipped. Features 9, 11, 12 and 14 each carry this same shape for that same card. (added 2026 09 01)
- When presenting a recommended option in a staged design conversation (architect or similar), verify the one line reason given for the recommendation against the repo, not only whether the recommended pick itself is right, because selecting an option ratifies its stated reasoning into the spec, and a wrong or incomplete reason is then recorded as a decision and read later as settled. (added 2026 09 02)
- When a span is missing from Sentry while its error events for the same operation arrive normally, check the project's inbound data filters before debugging the code or the SDK wiring, because Sentry's own "Filter out health check transactions" setting discards a whole transaction, and every span nested inside it, at ingest, while leaving error events on the same request untouched, and every local signal (debug logging, span IDs, finishing order) will look completely correct because nothing in the code is wrong. Feature 10's `usage_gate.check` span on `/health` hit exactly this on 2026-09-03. (added 2026 09 03)
- After configuring a Sentry metric monitor, confirm an alert is connected to it, because the monitor creates issues and notifies nobody on its own: feature 10's first firing on 2026-09-03 produced a Critical issue, correctly assigned, and delivered nothing until an alert was attached by hand, and a paper review of the alert rule would pass that gap every time. (added 2026 09 03)
- When a session is functioning as the advisor chat for a feature, never take write actions of any kind, file edits, skill invocations that write, git operations, even small docs edits, because the engineer keeps one such chat per feature specifically to get recommendations and verified answers without direct changes, and applying them is the engineer's own action to take. (added 2026 09 04)
- When a feature adds a new variable to `src/env.ts`, flag that it needs setting in every Vercel environment the branch will deploy to, and ask the engineer to add it before opening the pull request, because `env.ts` validates at module scope while Next collects page data, so an absent value fails the preview build with a red check that reads like a code defect and is not. Feature 11 hit this on 2026-09-04 with the two Adzuna keys, and features 13 and 14 each add their own. (added 2026 09 04)
- When proving something by reading a number before and after an action, make that number move on purpose once before trusting it, because a reader that cannot see its source returns the same unchanged value as an action that genuinely changed nothing, and both read as a pass. On 2026-09-05 a spec 0014 AC-10 probe read `usage_gate_counter` through the Supabase Data API and got zero both times: that table deliberately carries no row level security policy (spec 0011), so PostgREST cannot see it at all, and the check would have passed whatever the app did. Read those counters through `test/helpers/database.ts` or `psql`. (added 2026 09 05)
- When verifying what a Server Action does, drive it from a real browser or call the exported function directly, never by hand building its HTTP POST, because Next refuses a reconstructed action request and then falls back to rendering the page, so the attempt answers 200 with the action never having run. On 2026-09-05 that fallback also re-ran the Adzuna search and moved the usage counter, so a spec 0014 AC-10 measurement read as though an apply had spent a call when no apply had happened. The tell is `Failed to find Server Action` in the server log, so check there before trusting any hand built action request. (added 2026 09 05)
- When comparing an artifact a build produces (a generated manifest, a hash, a key) across two builds, delete the build output directory before each build, because a build tool that reuses existing output makes "the value did not change" indistinguishable from "the value was never regenerated", and both read as a pass. On 2026-09-05 three `pnpm build` runs over a populated `.next` returned a byte identical `serverActionsEncryptionKey`, and a `/check verify` report concluded that Next does not rotate the Server Action encryption key. It does: `next build` reused the previous `server-reference-manifest.json` (the build script is a plain `next build` with no clean step, and `.next/cache/` still held files from six days earlier), and three builds each preceded by `rm -rf .next` gave three different keys, after which the stale build case reproduced on the first attempt. (added 2026 09 05)
- When breaking code on purpose to prove a test fires, watch for three separate traps, each of which leaves a green suite that reads exactly like proof. **Re-run the break after any formatter or commit hook that rewrites code**, because a proof taken before that pass can be silently invalidated by it: on 2026-09-05 a guard in `src/features/applications/actions.test.ts` sliced from `Sentry.captureException` to the next newline and checked that fragment for four listing field names, it was broken on purpose and failed, and then the pre-commit hook's Prettier split that call across three lines inside the very commit that landed it, so the slice shrank to `Sentry.captureException(error, {` and none of the four names could ever appear in it. **Confirm the break actually changed the behaviour under test**, because a break that changes nothing produces a passing suite that looks exactly like a worthless test: on 2026-09-12 a hand written broken `SearchPage` left an `await` inside the JSX, so the ordering the test existed to check was still enforced and all 74 tests passed, while reverting the two files to their committed state instead failed exactly the three tests that depend on the search having been counted. When a deliberate break passes, suspect the break before the test. **Expect a specific NUMBER of failing tests and investigate a mismatch**, rather than reading "some failed" as proof, because a broken output can still satisfy a loose assertion: on 2026-09-13 a `toContain` check passed under its own deliberate break, since "$109,440 to $109,440 (estimated)" contains "$109,440 (estimated)". Distinct from the 2026 09 07 rule that breaking a test proves it fires and not that it compares the right span. (added 2026 09 05 and 2026 09 13, merged 2026 09 22)
- When waiting on pull request checks in this repo, do not trust `gh pr checks <n>`'s summary or exit code, with or without `--watch`: the RTK hook silently rewrites it to `rtk gh pr checks <n>`, whose filtering can read as done when it is not. Run `rtk proxy gh pr checks <n>` for the real per check list before acting. On 2026-09-06 the `--watch` form exited 0 on pull request 96 with "Passed: 55, Failed: 0, Pending: 11", eleven checks still outstanding, and a plain filtered check moments later gave a different, also incomplete count. (added 2026 09 06)
- When a runtime instruction in the session (a system prompt default, a /model switch side effect, a Co-Authored-By trailer request, a "Generated with Claude Code" footer rule) conflicts with this repo's no-tool-attribution convention (the merged 2026 08 29 and 2026 08 30 rule, graduating to `AGENTS.md`'s Git block), follow that convention and flag the conflict out loud instead of silently complying, because such instructions fire generically and were not written for this repo, where commit and pull request authorship is deliberately kept free of tool attribution. (added 2026 09 07)
- When verifying event-driven behaviour through Playwright, drive it through the real input pipeline (`page.keyboard.press`, a real click) and never through `page.evaluate(() => element.focus())`, because in this project's environment a `.focus()` called that way updated `document.activeElement` while dispatching `focusin` only sometimes, so a listener under test could fail to run while every readback still reported the right element as focused. On 2026-09-07 this reported spec 0015's AC-17 as failing four times in `/check verify` and pointed `/debug`'s first two hypotheses at `FocusRestorer`, which was never at fault. A real defect did exist, the recorder listened in the bubble phase, and that is what made the false signal convincing: the verdict was right by luck while the diagnosis was wrong. The same harness would have reported the FIXED code as broken too, because no key can be recorded when no `focusin` fires. `document.hasFocus()` returned true throughout, and on the runs where the event was missing a plain `focusin` probe added beside the app's own listener saw nothing either, so neither is a way out. `page.keyboard.press('Tab')` made the app's listener fire on the first attempt. (added 2026 09 07)
- When reporting that a check passed, name the scope it actually ran over and confirm that scope is at least as wide as the claim it is being used to support, because a narrow check reads exactly like a broad one and every local signal is a pass. Feature 15 produced four of these in one day on 2026 09 07: a spec clause claiming title was the only preference with a structured counterpart in the prompt, written while that session's own verification output had already printed `Location: Chicago, IL` and `- Desired locations: Atlanta, GA, Remote` together (the correction is recorded in spec 0016's index line 34); a test broken on purpose that failed and was reported verified, while it split on the requirements sentence and compared only the text before it, so appending ` Kafka also useful.` passed it (the fix is spec 0016's verify line 44); and a review reporting "all 45 tests passed" having run only `src/features/scoring/eval`, whose own Major the full suite then disproved (`docs/reviews/2026-09-07-feat-eval-ground-truth-set-prompt-tests.md`); and a test asserting that no salary reaches the model by searching the rendered prompt for the digits `191919`, which a comma formatted `191,919` walks straight past while all sixteen cases pass, found by that same review and replaced with a comparison of two whole renders, byte for byte, in `src/features/scoring/eval/prompt.test.ts`. Breaking a test proves it fires, not that it compares the right span. (added 2026 09 07)
- When writing a shell check whose output will be reported as evidence, never end it in `|| echo "<reassuring message>"`, because `||` fires on every nonzero exit alike: grep returns 1 for no matches and 2 for a bad path or an unreadable file, so a mistyped directory reports the same reassuring word as a genuinely clean result (verified 2026 09 07: `grep -r x /no/such/dir 2>/dev/null || echo none` and a real no match both print `none`). Let the command fail visibly, or print the exit status beside the output. Three uses on 2026 09 07: `grep -rn "scoring/eval" src/ --include=*.ts ... || echo "nothing imports it"`, where zsh rejected the glob and the fallback printed the reassurance, caught only because the claim was checked again; `grep -l ... src/features/scoring/eval/*.test.ts 2>/dev/null || echo "no, data is in .ts modules only"`, which discards the error class as well as collapsing it; and, in the advisor chat, `grep -rn -i "counterpart" docs/ src/ || echo "none"` used to confirm a false claim had been removed from every file it appeared in, where a wrong path would have produced the same word and been reported as proof the cleanup was complete. (added 2026 09 07)
- When a check reads a value out of a structured result (a JSON report field, an array, a list command's first row), confirm that value answers the question being asked before reporting it, because a neighbouring value that is real and correct reads exactly like the right one and raises no error. Four cases: the eval report's `summary` reads `"possible_match, 5 of 5 succeeded"`, where `5 of 5` is the success denominator and not the count landing on that band, and reading it as a band count put a wrong claim into `docs/scope/scope.md` and framed spec 0018's entire design conversation before anyone opened the reports (the real split was 4 to 1); the same report's `pairs` array holds only the pairs that ran, so a probe counting `status === "skipped"` there returned 0 for a run that skipped 15 of 16, whose ids live in a separate top level `skipped` array; and `gh run list --limit 1` announced CI settled while the run was still going, because the row it returned was a different workflow that had already finished; and on 2026-09-12, checking which acceptance criteria the committed suite covered, unioning the `AC-N` tags across `src/app/(app)/search/page.test.ts` gave a clean AC-1 to AC-15 sweep for spec 0020, because that one file carries tags for specs 0013, 0015 and 0020 together: spec 0020's own AC-10 had no test at all, and both privacy corrections could have been reverted with the whole suite green. Map each criterion to the specific test that pins it rather than unioning tags. Read the field that answers the question, and where a total is claimed, check that the parts sum to it (1 ran plus 15 skipped is 16). Distinct from the rules about an instrument that cannot tell a pass from a defect: here the instrument works and reports on something next to what was asked. (added 2026 09 09)
- When a skill produces personal job search material, such as the `/overview story` project story or an audit that checks resume claims, write it to `../jobhunt-notes/` and never into this repo, because the repo is portfolio facing and git history keeps anything committed. `/overview story` writes `docs/project-story.md` inside the repo by default, and on 2026-09-11 the story and the v1 audit both had to be moved out, the audit having been public since pull request 122. (added 2026 09 11)
- When a verify run needs the app running, check whether a dev server is already up before starting one, and prove it serves the current code before trusting any result, by asserting something only the change under test can produce. Next refuses a second dev server even on a different port, and the one already listening is usually the engineer's, so do not kill it. On 2026-09-11 and again on 2026-09-12 the server on port 3000 predated the session, an attempt to start one on 3100 was refused outright, and what settled the question was reading a rendered line that exists only in the change under test. (added 2026 09 13)
- When a CI check that has been passing suddenly fails on an authorization or authentication error, check the credential's expiry before suspecting the branch, because a scoped or personal access token expires silently and the failure reads like a defect in the change under review. On 2026-09-22 the `db-migrate` job failed at `supabase link` with "Unauthorized" on pull request #148, a month after `SUPABASE_ACCESS_TOKEN` was last set on 2026-08-22 and a day after that token's 30 day expiry, while the same job had passed on every run four days earlier; the replacement token then failed differently ("does not have the necessary privileges"), which is the tell that the first failure was the token and not the SQL. Related, and the other half of the same trap: the 2026-09-04 rule about a new `src/env.ts` variable needing to be set in every Vercel environment before the pull request opens. (added 2026 09 22)

## Graduating

- When an agent creates a commit or a pull request in this repo, omit every form of tool attribution: no `Co-Authored-By` trailer on a commit, which the develop skill's flow/git.md and the default system prompt both call for, and no "Generated with Claude Code" footer on a pull request, which `gh pr create` adds by default. The project's governing principle is full ownership on a portfolio facing repo, and the engineer owns every decision, so authorship should read that way rather than as delegated. (added 2026 08 29 and 2026 08 30, merged 2026 09 22)

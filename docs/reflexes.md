# Reflexes

## Reflexes

- When about to run /develop, read the governing spec's prerequisites and confirm each account, project, and credential it names already exists, because the spec gate only asks whether a decision is owed. (added 2026 08 21)
- When about to run a git command that discards working tree state (`reset --hard`, `checkout --`, `clean -f`, `restore`), read the full `git status` output first and account for every uncommitted file it shows, not just the one the command is meant to affect, because a hard reset touches the whole tree even when its stated purpose is narrow. (added 2026 08 23)
- When ratifying a feature linked spec, leave its Status line alone (Proposed or whatever /develop already set), because only /develop advances that line, and only to Accepted once the feature's scope row is done. (added 2026 08 26)
- When recommending an answer to a multi option decision panel (architect, develop, or similar), say whether each option needs a note, and when one does, produce the literal note text in the same response for every option that needs one, written self contained when it goes in the Other field, because flagging and drafting are not two separable steps and Other replaces the selection rather than supplementing it. (added 2026 08 26)
- When a feature is marked done, grep docs/scope/scope.md for other features whose skipped or deferred boxes name it by number, and grep the specs of any feature whose scope row named a dependency on it, because a feature that just shipped can unblock a step recorded elsewhere as waiting on it, and a spec's own Follow-up checklist can describe that same now resolved blocker as open even when scope.md is correct. Feature 21's close out on 2026 09 01 left spec 0007's Follow-up list describing the custom domain blocker as open while scope.md was correct. (added 2026 08 27)
- When citing an identifier (commit SHA, pull request number, spec ID, acceptance criterion, issue number), include what it refers to in the same breath, for example `5779d91` (the orphaned "mark it done" commit) and not the bare SHA, because a reference the reader has to resolve elsewhere does not survive the conversation. (added 2026 08 27)
- When naming a range of features, specs, or ACs that another document must act on, resolve each member against the source before writing the range, because a plausible looking range is repeated back as an instruction and then applied literally. (added 2026 08 28)
- When writing or reviewing a verify step for a system-level guarantee (a CSS rule, a shared token, a cross-cutting default), assert the outcome the reader experiences, not the property the code sets, because a step that only checks its own implementation can confirm nothing but what the author already believes — this shape has produced two escaped bugs (the tv size/colour bug, then the reduced-motion delay bug). (added 2026 08 28)
- When an agent creates a commit in this repo, omit the Co-Authored-By trailer even though the develop skill's flow/git.md and the default system prompt both call for one, because the project's own governing principle is full ownership on a portfolio facing repo, and the engineer owns every decision, so commit authorship should read that way, not as delegated. (added 2026 08 29)
- When splitting a change into one concern per commit in this repo, do not rely on `git add -p` for `docs/scope/scope.md` or a spec's `verify.md`, reconstruct each commit's file state directly instead, because those files routinely mix multiple concerns inside a single prose line, which hunk staging cannot separate. (added 2026 08 29)
- When a piece of work will produce commits, check the current branch and create one named for the commit type before the first commit, because `main` is branch protected and a direct commit to main strands there, needing reconstruction into a pull request afterwards. This happened twice on 2026 08 30. (added 2026 08 30)
- When an agent creates a pull request in this repo, omit the "Generated with Claude Code" footer that `gh pr create` adds by default, because authorship should read as full ownership on a portfolio facing repo. (added 2026 08 30)
- When verifying anything that depends on `supabase/config.toml`, read the running container's environment rather than the file, because `pnpm db:start` restarts existing containers instead of recreating them, so a stack can drift from the committed config and still pass its whole suite. (added 2026 08 31)
- When about to open a pull request, or when `.husky/pre-push` says this checkout is behind origin's main, read what actually landed before continuing, because the hook does the fetching and will name a changed rule file but cannot tell you whether it changes what you were about to write. That judgment is the half no hook covers, and it is the half that failed on 2026 08 31, when two pull requests nearly shipped the "Generated with Claude Code" footer a same day reflex had just forbidden. (added 2026 08 31)
- When reviewing a document whose authoring model is unknown or was produced by a tool outside this session's own lineage, run a panel of multiple independent reviewers rather than a single one, because an unidentified author cannot be excluded by name. When authorship is traceable, for example this session's own immediately prior output, a single reviewer excluding that named model is enough. (added 2026 08 31)
- When a spec is materially revised, re-review the revised spec before treating the revision as settled, because the fix for a review finding can itself be wrong and is not caught by re-reading. (added 2026 08 31)
- When correcting a claim that appears in more than one place in a document, fix every instance in the same pass and state which ones were checked, because a correction that touches only the first occurrence leaves the rest silently wrong. (added 2026 08 31)
- Before stating in a summary that a branch is pushed and current, check it against the actual remote, because describing the intended end state as already true is easy to do by habit and easy to get wrong. (added 2026 08 31)
- When acting on a follow up item in a spec, verify its claim against the repo before doing what it says, and correct the item when the claim is wrong, because follow up items are written at design time and never re-read, which makes them the staleest part of a spec: three of spec 0009's were wrong the first time anyone acted on them, two naming a skill whose own boundary forbids the work and one asserting a scope row lacked a clause it already had. (added 2026 09 01)
- When a feature's `Done when` names an edit to a file outside that feature's own code area, open that file and confirm the edit landed before ticking the feature done, because nothing in the feature's own work prompts that edit and no test covers it: feature 7's clause to retire the entry page's `working` placeholder went unmet under a done row on 2026 08 30, and the live homepage told every visitor that nothing worked for two days after sign in shipped. Features 9, 11, 12 and 14 each carry this same shape for that same card. (added 2026 09 01)
- When presenting a recommended option in a staged design conversation (architect or similar), verify the one line reason given for the recommendation against the repo, not only whether the recommended pick itself is right, because selecting an option ratifies its stated reasoning into the spec, and a wrong or incomplete reason is then recorded as a decision and read later as settled. (added 2026 09 02)
- When a span is missing from Sentry while its error events for the same operation arrive normally, check the project's inbound data filters before debugging the code or the SDK wiring, because Sentry's own "Filter out health check transactions" setting discards a whole transaction, and every span nested inside it, at ingest, while leaving error events on the same request untouched, and every local signal (debug logging, span IDs, finishing order) will look completely correct because nothing in the code is wrong. Feature 10's `usage_gate.check` span on `/health` hit exactly this on 2026-09-03. (added 2026 09 03)
- After configuring a Sentry metric monitor, confirm an alert is connected to it, because the monitor creates issues and notifies nobody on its own: feature 10's first firing on 2026-09-03 produced a Critical issue, correctly assigned, and delivered nothing until an alert was attached by hand, and a paper review of the alert rule would pass that gap every time. (added 2026 09 03)
- When a session is functioning as the advisor chat for a feature, never take write actions of any kind, file edits, skill invocations that write, git operations, even small docs edits, because the engineer keeps one such chat per feature specifically to get recommendations and verified answers without direct changes, and applying them is the engineer's own action to take. (added 2026 09 04)
- When a feature adds a new variable to `src/env.ts`, flag that it needs setting in every Vercel environment the branch will deploy to, and ask the engineer to add it before opening the pull request, because `env.ts` validates at module scope while Next collects page data, so an absent value fails the preview build with a red check that reads like a code defect and is not. Feature 11 hit this on 2026-09-04 with the two Adzuna keys, and features 13 and 14 each add their own. (added 2026 09 04)
- When proving something by reading a number before and after an action, make that number move on purpose once before trusting it, because a reader that cannot see its source returns the same unchanged value as an action that genuinely changed nothing, and both read as a pass. On 2026-09-05 a spec 0014 AC-10 probe read `usage_gate_counter` through the Supabase Data API and got zero both times: that table deliberately carries no row level security policy (spec 0011), so PostgREST cannot see it at all, and the check would have passed whatever the app did. Read those counters through `test/helpers/database.ts` or `psql`. (added 2026 09 05)
- When verifying what a Server Action does, drive it from a real browser or call the exported function directly, never by hand building its HTTP POST, because Next refuses a reconstructed action request and then falls back to rendering the page, so the attempt answers 200 with the action never having run. On 2026-09-05 that fallback also re-ran the Adzuna search and moved the usage counter, so a spec 0014 AC-10 measurement read as though an apply had spent a call when no apply had happened. The tell is `Failed to find Server Action` in the server log, so check there before trusting any hand built action request. (added 2026 09 05)
- When comparing an artifact a build produces (a generated manifest, a hash, a key) across two builds, delete the build output directory before each build, because a build tool that reuses existing output makes "the value did not change" indistinguishable from "the value was never regenerated", and both read as a pass. On 2026-09-05 three `pnpm build` runs over a populated `.next` returned a byte identical `serverActionsEncryptionKey`, and a `/check verify` report concluded that Next does not rotate the Server Action encryption key. It does: `next build` reused the previous `server-reference-manifest.json` (the build script is a plain `next build` with no clean step, and `.next/cache/` still held files from six days earlier), and three builds each preceded by `rm -rf .next` gave three different keys, after which the stale build case reproduced on the first attempt. (added 2026 09 05)
- When a test proves itself by reading the text or formatting of source code, re-run the deliberate break after any formatter or commit hook that rewrites code has run, because a proof taken before that pass can be silently invalidated by it and the test then keeps passing while checking nothing. On 2026-09-05 a guard in `src/features/applications/actions.test.ts` sliced from `Sentry.captureException` to the next newline and checked that fragment for four listing field names; it was broken on purpose and failed, so it looked proved. The pre-commit hook's Prettier then split that call across three lines inside the very commit that landed it, the slice shrank to `Sentry.captureException(error, {`, and none of the four names could ever appear in it. Breaking a test once shows it worked then, not that it still does. (added 2026 09 05)

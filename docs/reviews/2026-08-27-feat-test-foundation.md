## Summary

This change stands up the whole test layer spec 0004 asked for: Vitest as two projects, a development-only session mint through the admin magiclink exchange, a bespoke record/replay recorder with write-time redaction, a re-minted fixture pool with valid UUIDs, and a CI job running both suites against a real local Supabase stack. The security-sensitive paths hold up under inspection: the `DEV_SESSION_ENABLED` guard has exactly one choke point (`test/helpers/admin.ts`), nothing under `src/app` or `src/lib` (other than a colocated test file) can reach it, the cookie jar and session mint create fresh state per call with no shared mutable state, and the team's own vacuousness checks (RLS disabled, fixture deleted) are real and match what the code would actually do if the guarantee broke. The one real gap is in the recorder's body redaction, which only handles a flat top-level JSON object and silently passes anything else through unredacted — worth fixing before the next two features (Adzuna, the model router) start depending on it for exactly this guarantee.

## Major

### 🟠 Body redaction silently no-ops on anything but a flat top-level object, `test/helpers/recorder.ts:123-135`
**Problem**: `redactBody()` only redacts `secretBodyFields` when `JSON.parse(bodyText)` yields a plain object. If the body is a top-level array (`Array.isArray(parsed)` at line 133), not valid JSON at all (the `catch` at line 130), or an object whose credential lives at a nested path rather than a top-level key, the function returns `bodyText` completely unchanged — no redaction attempted, and no signal that redaction was skipped. `warnRecorded()` prints the same generic warning regardless ("Read the file before you commit it"), so nothing distinguishes "this body was fully scanned per its declaration" from "this body's shape wasn't one this function understands, so nothing happened."
**Why it matters**: Spec 0004's own follow-up names this recorder as the tool Adzuna (feature 11) and the model client router (feature 13) will use for their own fixtures. A job-search API returning a top-level array of results, or nesting a token/key one level deep in a response object, is a very plausible shape — more plausible than the flat objects the two services declared here (`GITHUB`, `CREDENTIAL_CARRYING`) exercise. The mitigating control is a human reading the file before commit, but the warning text doesn't call out that a chunk of the body was never scanned, so a reviewer skimming a large array or nested payload is exactly the person most likely to miss it.
**Suggested fix**: Either recurse into arrays and nested objects when matching `secretBodyFields` (matching by key name at any depth, not just top level), or make the fallback loud rather than silent — have `record()` detect a body shape `redactBody` can't handle and refuse to write until a human names how, similar to how `fixtureMode()` already refuses an unrecognised value rather than guessing. A one-line addition to `services.ts`'s doc comment already says "a service whose credential travels somewhere unusual needs its own declaration"; the code should enforce that rather than assume it.

## Minor

### 🟡 URL fragments are never redacted, `test/helpers/recorder.ts:104-114`
**Problem**: `redactUrl()` only touches `parsed.searchParams`; nothing looks at or clears `parsed.hash`. If a caller ever passes a `recordedFetch` URL carrying a credential in the fragment (the OAuth implicit-grant pattern puts `access_token=...` there), it is captured and committed verbatim — `service.secretQueryParams` has no equivalent for the fragment.
**Why it matters**: Low probability given today's two declared services, but it's a blind spot in the one function whose whole job is "nothing credential-shaped survives to disk," and the code gives no indication the fragment is out of scope.
**Suggested fix**: Either strip `parsed.hash` unconditionally (fragments are never sent to the server anyway, so nothing legitimate is lost by dropping them) or add it to the redaction pass explicitly.

### 🟡 The cookie jar's deletion branch has no direct test, `test/helpers/cookie-jar.ts:33-42`
**Problem**: `setAll()` treats an empty cookie value as "delete this cookie" (`cookies.delete(name)` at line 41) rather than storing an empty string. Nothing in `test/helpers/recorder.test.ts`, `test/helpers/admin.test.ts`, or the integration suite exercises a sign-out/cookie-clearing path that would hit this branch.
**Why it matters**: It's a small but real piece of logic (get it backwards and a "signed out" jar would still read as holding a session), and TEST_SIGNAL is `configured` here, so untested branching logic is a finding per the review bar. It's currently proven correct only by code reading, not by a test that would fail if it regressed.
**Suggested fix**: A short unit test on `createCookieJar()` directly — set a cookie, then `setAll` it to `""`, assert `names()` no longer includes it — would close this without needing the stack.

## Strengths

- The security model holds up under adversarial reading, not just on paper: `devOnlyAdminClient()` is the single choke point for the secret client from test code (`test/helpers/admin.ts:59`), it's the only caller under `test/`, and a repo-wide grep confirms nothing under `src/app` or `src/lib` (besides the one colocated test file, which only reaches unrelated Sentry test infra) can reach it. The guard is read at call time rather than import time, so a test can actually observe the refusal, and it's proven to fail closed on *absence* of the variable, not just an explicit `false` — the state production is actually in.
- The team's own vacuousness discipline (documented in `verify.md`'s "Proved during the build" section, and independently checked against the actual test code in this review) is real: the isolation test's "no `eq` filter" design means RLS being disabled genuinely flips five assertions from pass to fail, and the recorder's redaction tests assert against the bytes written to disk rather than the function's return value, which is exactly the distinction that would have caught a "redacts the object but writes the original" bug.
- The `process.stderr` fix for the swallowed record-mode warning (found by the team's own `/check verify` run, not by this review) is a good example of turning a found bug into a regression test rather than just a fix — `recorder.test.ts`'s "warns on the way out" test would fail if it reverted to `console.warn`.
- Cookie jars and Supabase clients are constructed fresh per call with no module-level mutable state (`createCookieJar()`, `createClient()`), so there's no cross-test session leakage to find — confirmed by reading, not just by the tests passing.
- `createClient()`'s new optional cookie adapter is a genuinely minimal, well-reasoned change: default behavior is byte-for-byte preserved (`nextCookieAdapter()` is the same code, just extracted), and it's the kind of testability seam that avoids building a second, parallel Supabase client in test code.

## Test coverage

25 unit tests and 9 integration tests, all exercising real behavior rather than mocks consistent with the project's "tests use real dependencies" rule. Coverage is genuinely strong on the paths that matter most: the `DEV_SESSION_ENABLED` guard (both explicit-false and absent, plus the other `z.stringbool()` spellings), the Sentry reporting contract (fingerprint, tags, level, and that nothing reaches a real ingest host), row-level security in both directions (hidden read, refused cross-user write), the missing-fixture failure path (including a network-call assertion, not just an error message), and record-mode redaction proven through a real HTTP round trip rather than a direct call to `redact()`. The two gaps worth naming: the body-redaction shape assumption (Major above) has no test that would catch it, because nothing exercises a non-flat-object body; and the cookie jar's deletion branch (Minor above) is unexercised. Everything else checked in this review — the fixture pool's UUID validity against real rows, the secret client's revoked table privilege, the `.test`-domain-only fixture identities — is asserted against the real database rather than trusted from the seed file's text.

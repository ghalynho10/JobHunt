## Minor

### 🟡 The spec's "Next may report it twice" undercounts the real number of capture paths, `docs/specs/0020-spend-visibility-and-gating-polish/index.md:60`

**Problem**: The Decision says a rejection shared by two consumers means "Next may report it twice." I reproduced the exact shape (a synchronous throw inside `searchListings()`'s span callback, standing in for "a throw from `cookies()` or the span wrapper," run against a real Next 16.3.1 dev server with a real minted session) and the server log showed the underlying error logged **three separate times, in two different forms**: one line explicitly tagged `unhandledRejection: Error: ...` (Next's own global handler, confirmed by reading `node_modules/next/dist/server/node-environment-extensions/process-error-handlers.js`, whose comment describes this exact "late awaiting" pattern as an accepted, by design Next.js idiom, not a bug), plus two further identical `⨯ Error: ...` blocks with the same `digest`, one per component that independently awaited the shared promise. That is three log entries from one root cause, not two. Separately, `src/sentry.server.config.ts` does not override `defaultIntegrations`, so Sentry's `OnUnhandledRejection` integration is active (confirmed in `@sentry/node-core`'s `getDefaultIntegrations()`, which lists it under "Global Handlers" and registers its own `process.on("unhandledRejection", ...)`), and it calls `captureException` independently of whatever the render pipeline reports. So the realistic count in Sentry is plausibly three captures for one bug: one from `OnUnhandledRejection`, and up to two more from the render pipeline's own catch, one per component.
**Why it matters**: The spec's own conclusion, that this is acceptable noise and not worth a test, is still right in my judgment (see the named section below), so this does not change the verdict. But this project's spec text has twice before recorded a guarantee that was subtly wrong about its own mechanism (the prop, then "two independent guards"), and the reflex this branch itself added on 2026-09-02 is that a recorded reason is read later as settled. Undercounting "twice" to what is really "three, one of them from a completely different subsystem" is the same shape of small inaccuracy, just about severity rather than mechanism.
**Suggested fix**: Either soften "so Next may report it twice" to "so this may be reported more than once, through more than one channel" or, if precision is wanted, name the two channels (Next's own per component render catch, and Sentry's `OnUnhandledRejection` default integration).

### 🟡 The added migration comment does not mention that `auth.uid()` must itself be `stable` for this to be safe, `supabase/migrations/20260911120000_job_search_usage_summary.sql:42`

**Problem**: The comment says the function is `stable` "because the body reads tables and calls `auth.uid()`," giving the reason `stable` is chosen over `immutable`. It does not note the reason `stable` is safe to put around `auth.uid()` at all: a `stable` function is permitted to call other `stable` (or `immutable`) functions, and Supabase's `auth.uid()` is itself declared `stable` (it reads a per request session variable that does not change intra transaction). Postgres does not enforce this pairing at `create function` time, so nothing would have caught it if `auth.uid()` had been `volatile`.
**Why it matters**: This is not a bug today, since `auth.uid()` genuinely is `stable`. But the comment reads as if the two reasons given ("reads tables", "calls `auth.uid()`") are jointly sufficient for correctness, when the second one is only safe because of a fact about `auth.uid()` that lives in a different codebase entirely. A later reader who copies this pattern onto a function calling a genuinely volatile helper would have no comment here warning them that the pairing needs checking.
**Suggested fix**: One clause, e.g. "`auth.uid()` is itself `stable`, so calling it from here does not violate the marker." Not blocking; the current comment is not wrong, just slightly less complete than it could be given how carefully worded everything else here is.

## The three questions on the shared promise that is not awaited by the page

**Setup**: `SearchPage` calls `searchListings({ title: q, location: where })` without `await`, and the resulting promise (`searchInFlight`) is handed to both `UsageNotice` and `SearchResults`, which each `await` it independently. I reproduced a genuine promise rejection (a synchronous `throw` inside the `Sentry.startSpan` callback, standing in for the "throw from `cookies()` or the span wrapper" the spec names as the only realistic cause) against a real, running Next.js 16.3.1 server with React 19.2.8, using this project's own `test/helpers/app-server.ts` and `test/helpers/session.ts` to drive a real authenticated HTTP request at `/search`, run from an isolated git worktree so nothing under review or already running was touched.

**1. Can a rejection reach the error boundary TWICE?** Yes, at the logging/reporting level, though the HTTP response the browser sees is still a single 500. The server log showed the identical underlying error, same stack, same `digest`, logged in two separate `⨯ Error: ...` blocks. Since awaiting an already rejected promise throws that same error value again rather than cloning it, and both `UsageNotice` and `SearchResults` independently `await searchInFlight`, each one's own render task throws and gets caught and logged by Next's render error reporting on its own, even though only one page level error response is ultimately produced. If Sentry's per request error capture is wired the same way (which `@sentry/nextjs` generally is, through `onRequestError`), this reads as two separate captures for Sentry, not one.

**2. Can it escape as an UNHANDLED REJECTION before either consumer awaits it?** Yes, confirmed both by direct reproduction and by reading Next's own source. The server log carried a line explicitly tagged `unhandledRejection: Error: REVIEW_PROBE_SYNTHETIC_BUG`, which is Next's own global `process.on("unhandledRejection", ...)` handler (`node_modules/next/dist/server/node-environment-extensions/process-error-handlers.js`) firing and logging through `_log.error('unhandledRejection:', reason)`. That file's own comment describes this exact shape as an accepted, intentional Next.js idiom: it gives an example almost identical to this one (`const promise = fetchData(); const cond = await x(); if (cond) return <Component promise={promise} />`) and says plainly that Next deliberately does not treat this as fatal, specifically because "late awaiting" a promise created before a component decides whether to use it is something Next.js itself expects application code to do. Separately, `src/sentry.server.config.ts` does not disable Sentry's default integrations, and `@sentry/node-core`'s `OnUnhandledRejection` integration (confirmed present in `getDefaultIntegrations()`) registers its own listener and calls `captureException` for exactly this event, independent of whatever the render pipeline reports. So this is not a theoretical race: it is a real, reproducible, and (per Next's own source comments) expected consequence of the "start now, await later, maybe not at all" pattern this page uses on purpose.

**3. Is leaving that path untested acceptable as the spec records it?** Yes. Three reasons, in order of weight. First, this is explicitly a programmer bug path (`searchListings()` returns a `Result` for every expected failure; a rejection only happens if something like `cookies()` throws outside a request context), and the project's own convention is that a programmer bug should throw and reach an error boundary rather than become a value, which is exactly what happens here, twice over if anything. Second, both of the failure modes I confirmed make the bug loud rather than silent: Next logs it as an explicit `unhandledRejection`, and Sentry's default integration reports it independently of the render pipeline, so "no silent failures" is not at risk even without a dedicated test. Third, and this is the practical argument: I could not get a deterministic reproduction of this without spinning up a real Next server and driving it with a real authenticated request; a unit test using this project's own render helper (`renderDeepAsync`) cannot answer either of the first two questions, because both depend on React's actual Flight scheduler and Node's actual `unhandledRejection` timing, neither of which the test helper models. A test that only proved "the page still returns something when the promise rejects" would not touch either real question, and one that tried to assert on `process.listeners('unhandledRejection')` counts would be exactly the kind of fragile, environment coupled test this project's own testing conventions (real dependencies, no mock encoding the same assumption as the code) would reject. My one adjustment to the spec's own reasoning here is the Minor above: the acceptable conclusion holds, but "twice" should be corrected, since the real number of independent report channels is closer to three once Sentry's own default global handler is counted alongside Next's per component render catch.

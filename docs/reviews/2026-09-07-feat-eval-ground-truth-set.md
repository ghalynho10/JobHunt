## Minor

### 🟡 Stale pair counts survive the AC-4 amendment, `docs/specs/0016-eval-ground-truth-set/index.md:113`, `:123`, `docs/specs/0016-eval-ground-truth-set/rationale.md:41`
**Problem**: The Build plan's intro paragraph still reads "authoring the remaining thirteen pairs, rather than writing all four archetypes and fifteen pairs first," and step 9 still says "against the complete fifteen pair set." `rationale.md`'s Option 2 pros/cons still says "four archetypes, fifteen pairs instead of ten." The delivered set has sixteen pairs (confirmed by the pair table, `pairs.ts`, and the guard test's `PAIRS.length >= 16`), because `preference-title-conflict` was added later as the AC-4 amendment the spec itself documents (index.md's "The reasoning this replaced" block). The amendment updated AC-4's own text, the Follow-up, and Build plan step 7, but missed the intro paragraph, step 9, and the rationale doc.
**Why it matters**: This is exactly the failure mode `docs/reflexes.md` calls out twice (2026-08-27, "resolve each member against the source before writing the range"; 2026-08-31, "fix every instance in the same pass"): a later reader trusts a stale count and miscounts what was actually built, or assumes step 9's guard test only needs to cover fifteen pairs when a sixteenth already exists.
**Suggested fix**: Update the three stale counts to sixteen (and "fourteen" for the "remaining" figure in the intro paragraph, since one archetype + one pair are already authored in step 1-3 of the same plan).

### 🟡 `weak-match-shallow-overlap`'s single exact band is a closer call than the other control pairs, `src/features/scoring/eval/pairs.ts:232-246`
**Problem**: The posting (Backend Engineer, distributed systems, Kafka, service architecture) names nothing that appears in `adjacent-insufficient-depth`'s own skill list (React, TypeScript, CSS, Accessibility, Component design, Node.js, Git) or work history text. The rationale's basis for `weak_match` over `not_a_match` — "general software engineering and Node scripting carry over a little" — is a holistic argument rather than one grounded in a named skill or work history line that visibly overlaps the posting, unlike every other control pair in the set (each of which points at a literal named skill or requirement match). `weak_match`'s anchor ("only a small part... carries over") and `not_a_match`'s anchor ("do not carry over... in any substantial way") are both defensible readings of zero literal overlap plus general software literacy, which is structurally the same kind of anchor silence the `boundary-seniority-gap` pair was given `acceptableBands` for.
**Why it matters**: AC-2 requires a single exact `expectedBand` only "wherever the rubric's wording alone can support one confident answer." If this pair is actually as ambiguous as `boundary-seniority-gap`, feature 16's harness will report a `weak_match`/`not_a_match` split here as a scoring regression when it may be the same kind of honest rubric silence the spec elsewhere treats with tolerance.
**Suggested fix**: Either strengthen the rationale with a more concrete carryover argument (e.g., point at a specific line in the archetype's work history that plausibly transfers), or, if the ambiguity is genuine, widen this pair to `acceptableBands: ["weak_match", "not_a_match"]` the same way the boundary pair is handled. Not blocking — it's a judgment call the spec's own author is better positioned to make than a reviewer reading the text cold.

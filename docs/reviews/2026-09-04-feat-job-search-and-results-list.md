## Major

### 🟠 The value pass cannot see a header-borne credential, but the branch records that it protects the features whose credentials are header-borne, `test/helpers/recorder.ts:229`
**Problem**: `secretValues()` reads credential values exclusively from `service.secretQueryParams` on the request URL. A credential that travels in a request header (an `Authorization` bearer token, an `x-api-key`) is redacted positionally in `recordedFrom.headers`, but its *value* is never fed to `scrubValues()`, so a service that echoes it into a response body field nobody declared — the exact Adzuna-shaped failure this pass was built for — commits it to git untouched. Meanwhile `docs/scope/scope.md`'s feature 11 Test row states the change "protects features 13 and 14 too": feature 13 is the model client router, and both OpenAI and Anthropic take their keys in headers, not query params, so for the two named beneficiaries the value pass contributes nothing.
**Why it matters**: This is shared security infrastructure governed by spec 0004 AC-13, and the failure mode is a live credential committed to a public portfolio repo. The near miss that motivated this change proves services do echo request credentials into undeclared fields. Worse, the overstated claim in scope.md is precisely the kind of recorded assurance a later session reads as settled: whoever records feature 13's first fixture will believe the value pass has their back, and it will not.
**Suggested fix**: Two halves. (1) Give `ServiceDeclaration` a way to name credential-carrying *request header* names (do not blindly scrub every non-allow-listed request header value — `accept: application/json` scrubbed by value would shred a body), and feed those values into the same `secretValues()`/`scrubValues()` pass; `CREDENTIAL_CARRYING` already sends a bearer token, so `recorder.test.ts` can prove it the same way the echoes-key-in-url route does. (2) Or, if that is deliberately deferred to feature 13, correct the scope.md sentence now so the protection claimed matches the protection built — the wrong claim is the part that must not survive this branch either way.

## Minor

### 🟡 The registered `search.run` description misstates the span's own failure ratio, `docs/observability/spans.md` (search.run row) / `src/features/search/adzuna.ts:282`
**Problem**: The registration says the span's failure ratio is "`external_service_failed` and `response_malformed` against every attempt, never a gate refusal … which never reaches this span at all since `withUsageGate()` short circuits before calling in." Two inaccuracies, verified against the code. First, `searchListings()` returns `failure(validation_failed)` *inside* the `search.run` callback (`adzuna.ts:288`), and `failure()` marks the active span failed regardless of severity (`result.ts:97`), so every blank-pair submit — one click on an empty form, `?q=&where=` — produces a failed `search.run` span. Second, a gate refusal executes entirely within `search.run` (the whole `withUsageGate` call is inside the span); it correctly does not *fail* the span, but "never reaches this span at all" is not what the code does.
**Why it matters**: spans.md exists so a later engineer can build the binding-rule-4 rate alert from the registered description without re-deriving it. An alert built on this row's words would attribute user-typed blank submissions to an Adzuna integration incident. The code itself is consistent with the project's error model (expected failures deliberately count in ratios, per `result.ts`); it is the registered prose that is wrong.
**Suggested fix**: Rewrite the row to name all three kinds that can fail this span (`validation_failed`, `external_service_failed`, `response_malformed`), and say the refusal runs inside the span but leaves it unfailed. If blank submits polluting the outbound-call ratio is *not* wanted, that is a spec conversation (moving the parse ahead of the span collides with binding rule 4), not a quiet edit.

### 🟡 The inverted-salary drop has no test anywhere, `src/features/search/adzuna.ts:138`
**Problem**: The transform that drops both salary figures when `salary_max < salary_min` (a spec-mandated rule: the Data model sketch says an inverted pair is dropped because spec 0003's check constraint would refuse it at feature 12's insert) is the one branch in `adzuna.ts` no test exercises. I confirmed the engineer's suspicion: no `adzuna.test.ts` exists beside the module. That absence is otherwise well covered — `test/integration-serial/search-listings.test.ts` drives the real `searchListings()` through every error branch, the drop-and-count rule, the empty batch and the recorded bytes, which honours the project's real-dependencies rule better than a unit file re-declaring the schema would — but the inverted pair appears in no fixture and no forced body.
**Why it matters**: A later simplification of the transform could silently start passing inverted pairs forward, and nothing would go red until feature 12's insert hits the database constraint in production.
**Suggested fix**: One more case in the existing `respondWith()` harness: take a real fixture item, set `salary_min: 200000, salary_max: 100000`, and assert the parsed listing carries no salary figures and no currency.

### 🟡 A failed prefill read renders identically to "no preferences stated", `src/app/(app)/search/page.tsx:80`
**Problem**: `PrefilledForm` catches a `Failure` from `readSearchPrefill()` and renders the bare form — the same screen a caller with no `job_preference` row sees. The doc comment argues the failure is already reported by `failure()` itself, and the page test locks the behaviour in ("still shows a usable form when the preference read fails", asserting zero alerts).
**Why it matters**: AGENTS.md's rule is "a failure is always visible, never a default that reads like success", and spec 0013's AC-9 defines blank fields as the meaning of *no stated preference* — a database outage now borrows that meaning. Not blocking the form is the right product call (the reader can still type), but the caller who *has* preferences sees them silently gone and has no way to distinguish "I never set these" from "the read broke".
**Suggested fix**: Either render a small non-alert notice on the prefill-failure branch ("your saved preferences couldn't be loaded"), or record the exception explicitly in spec 0013 so the deliberate trade against the binding rule is a decision rather than an accident of an early return.

### 🟡 `z.url()` accepts any scheme, and `redirect_url` lands in an `href`, `src/features/search/adzuna.ts:120`
**Problem**: Zod's bare `z.url()` validates WHATWG-parseable URLs, which includes `javascript:alert(1)`. The parsed value flows into `Button href={listing.url}` on every card. React has warned on `javascript:` hrefs since 16.9; I have not verified whether React 19 hard-blocks them, so I will not claim it does or does not.
**Why it matters**: The boundary parse exists precisely so this app does not extend trust to Adzuna's response shape. The exposure needs a hostile or compromised upstream, so it is hardening rather than a live hole — but it is one option away.
**Suggested fix**: `z.url({ protocol: /^https?$/ })` (Zod 4 supports the option). An off-scheme listing is then dropped by the existing item-level drop-and-count rule rather than rendered.

### 🟡 The fixture test's env-derived negative assertions can fail spuriously or pass vacuously, `test/helpers/adzuna-fixture.test.ts:71`
**Problem**: `expect(whole).not.toContain(process.env["ADZUNA_APP_ID"] ?? " ")` misbehaves at the edges: an env value of `""` makes `not.toContain("")` fail unconditionally (`includes("")` is always true), an unset value substitutes `" "` and fails against any body containing a space (every real body), and a short placeholder like `abc` can spuriously match ordinary listing text. CI's long placeholder and a real local pair both work, which is why nothing has surfaced.
**Why it matters**: The failure message ("expected not to contain ''") points nowhere near the actual cause, and this is the assertion standing guard over "commits no credential" — it should only ever fail for the reason it names.
**Suggested fix**: Skip the containment assertion for values shorter than the scrubber's own 6-character floor (reusing that constant keeps the two in agreement), or assert the values are present-and-long before using them.

- The attribution work treats licence terms as a contract: link targets asserted as literals where the terms fix them, the logo geometry held to the supplied SVG by a drift test, and the minimum sizes set as real CSS floors with the un-measurable half honestly delegated to verify.md.
- `renderDeepAsync` (the other requested hostile read) is sound: it mirrors the sync walker's semantics exactly (fragments, arrays, stop-at boundary, children-only descent), its licence comment correctly limits it to stateless plain functions, and adding it as a second function rather than widening `renderDeep` kept every existing caller's type intact.

## Summary
The change adds `Searches used this week: N of 25.` to `/search`, read live through a new read only `security definer` function, and then fixes a real defect its own verification found: on a search render the line used to show the pre search count, which at the cap boundary told a person on their last allowed search that one remained. The fix, lifting `await searchListings()` into `SearchPage`, is correct and the ordering does hold under React Server Components. The headline problem is that the code and the spec attribute that guarantee to the wrong thing: the `searchResult` prop and its `void searchResult;` line hold nothing at runtime, the `await` before `return` in `SearchPage` is what orders the read, and the shape the spec rejected as weaker (pass the promise, await it inside `UsageNotice`) is the one that would survive the most plausible future refactor. Everything else is solid: the migration mirrors `check_usage_gate`'s hardening exactly, the integration tests drive the real gate to the boundary and prove the next search is refused, and the failure path never renders a zero. Concurrency was checked and raises nothing: two tabs each order their own read after their own gate call, and a week boundary landing between the gate call and the read shows the new week's figure, which is the true position.

## Major
### 🟠 The ordering guarantee is held by the `await`, not by the prop, and every comment and the spec say the opposite, `src/features/search/usage-notice.tsx:25`
**Problem**: The header comment says the `searchResult` prop is "THE ONLY THING MAKING THAT TRUE" and `src/app/(app)/search/page.tsx:112-117` says "Removing the prop compiles and renders and quietly brings the boundary bug back." Neither is true. Under React Server Components a child element does not exist until its parent returns a tree, and `SearchPage` cannot return until `await searchListings()` at `page.tsx:94-96` has resolved, which is after `withUsageGate()` has awaited the committed gate call. That `await` before `return` is the whole mechanism. The prop is a plain resolved value, React does not await props, and `void searchResult;` at `usage-notice.tsx:85` awaits nothing. Delete the prop and the `void` line, keep the `await`, and the ordering is byte for byte the same. The diff's own new reflex (`docs/reflexes.md`, 2026-09-13, "a hand written broken `SearchPage` left an `await` inside the JSX, so the ordering the test existed to check was still enforced") is a recorded observation of exactly this: any `await` before the tree is returned keeps the order, prop or no prop.

The spec's Decision (`docs/specs/0020-spend-visibility-and-gating-polish/index.md`, "TypeScript refuses to render `UsageNotice` before `SearchPage`'s `await` has resolved", and AC-11's "A refactor cannot reorder it without moving the read out of the component") records the same wrong mechanism, and the invariants list tells a reviewer that "What holds it is the `searchResult` prop, not the order of statements."

**Why it matters**: Two things. First, the plausible refactor this shape was chosen to survive is the one it does not survive. The obvious next optimisation on this page is streaming: stop awaiting the search in `SearchPage`, pass the promise down, `await` it inside `SearchResults` under a `Suspense` boundary (the pattern spec 0015 already uses for scoring), and widen `UsageNotice`'s prop type to `Promise<...> | undefined` to keep typecheck green. After that edit `void searchResult;` still lints clean, the required prop is still "an awaited value" in name only, and `UsageNotice`'s read runs concurrently with the search again, restoring the 24 of 25 bug with every comment in the file still saying it cannot happen. The rejected runner up, passing the promise and awaiting it inside `UsageNotice`, survives that same refactor untouched, because the dependency is then real at runtime, and it has identical lint protection (deleting its `await` leaves the prop unused, the same failure `void` was chosen to avoid). The spec's comparison of the two is inverted. Second, the project's documentation strategy depends on load bearing comments being true (`AGENTS.md`, "comments say why ... so a later session cannot simplify a rule away", and the 2026-09-02 reflex on a wrong reason being ratified as settled). A "DO NOT DELETE THIS LINE" on a line that protects nothing sends the next maintainer to guard the wrong thing and says nothing about the `await` that actually matters.

**Suggested fix**: Pick one and make the words match. Preferred: pass the promise (`hasQuery ? searchListings(...) : undefined`, no `await` in `SearchPage`) and `await` it as the first statement of `UsageNotice`, so the prop is genuinely the ordering, and pass the same promise to `SearchResults`; this also lets the results stream later without touching the notice. Otherwise keep the current shape but rewrite the two comments and the spec (AC-11, the Decision's "How the prop satisfies lint" paragraph, and the invariants list) to say what is true: the order is held by `SearchPage` awaiting the search before it returns its tree, the prop is a signpost only, and the page tests under "the usage read is ordered after this render's own search" are the guard. Either way, drop the claim that removing the prop restores the bug.

### 🟡 The function is not declared `stable`, so "read only" rests on a grep and a test rather than on Postgres, `supabase/migrations/20260911120000_job_search_usage_summary.sql:33`
**Problem**: The migration's comment says the function "must never create" a row and verify.md proves it with a `grep -c "insert\|update\|delete"`. The function is left at the default volatility (`volatile`), which is what permits writes. Declared `stable`, Postgres itself refuses any data modifying statement inside the body at execution time (`INSERT is not allowed in a non-volatile function`, from SPI's read only mode), which is the same guard `auth.uid()` and `now()` are already compatible with. Verified from Postgres semantics, not by executing it against the local stack.
**Why it matters**: AC-3's "no insert or update of any kind" would then hold by construction, matching the migration's own stated preference for "by construction rather than by a check somebody has to remember." It also lets PostgREST serve the call over GET if that is ever wanted.
**Suggested fix**: Add `stable` to the function definition and let the existing "creates none" test keep pinning the outcome.

## Strengths
- The migration mirrors `check_usage_gate`'s hardening exactly: `security definer`, `set search_path = ''`, every reference schema qualified, `execute` revoked from `public` and granted to `authenticated` only, no parameter so no caller can widen the readable surface, and no new grant on either table. AC-15's test pins both functions' ACLs with `has_function_privilege` in both directions, so a future recreate that forgets its `revoke` fails a test.
- `test/integration-serial/usage-line-ordering.test.ts` drives the real gate to one below the cap, runs the last allowed search, asserts `25 of 25`, and then proves the next search is refused. That last step is what makes the shown number mean what a reader takes it to mean.
- The unit ordering tests wire the two mocks through one shared counter with a yield inside the search, so they genuinely discriminate the old sibling composition rather than restating the new one.
- `queries.ts` parses the row with nullable columns, treats `data: null` with no error as a failure, and refuses to render a zero through a `configured: true` row carrying a null. No path reaches the page as a silent zero.
- The `usage_gate.read_summary` entry in `docs/observability/spans.md` explains precisely why this span must not join `usage_gate.check`'s alert, including the denominator dilution from bare visits.
- `test/integration/usage-cap-descriptions.test.ts` reads the real `usage_cap` call types and fails on an unclassified one, so the privacy notice cannot go stale the same way twice.

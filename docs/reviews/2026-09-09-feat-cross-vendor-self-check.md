## Summary

The branch chains a second vendor (Google, `ai_check`) after every successful OpenAI score to ask whether each claimed `matchedSkills` name is grounded in the same listing text, drops what the check disputes from the rendered chips with a note, and renders a broken check as its own visible state. The structure is sound: the listing block and the grounding criterion were genuinely extracted rather than copied, the score-then-check ordering and both budget skips are enforced by construction, the span partition holds, and the card keeps a skipped check silent while a broken one speaks. I proved the load bearing "byte identical scoring prompt" claim empirically rather than by reading the diff (see Strengths). The one Major is in the check's own system prompt: a sentence outside the shared constant tells the checker that a skill "appearing as part of a longer phrase" counts as grounded, which is the substring rule `keepOwnNames()`'s own comment names as the exact false claim this project refuses, applied in the direction that makes the check miss the over-claim it exists to catch. The rest are Minors, most of them the familiar shape from `docs/reflexes.md`: an instrument or a comment that cannot tell a pass from a defect.

### 🟠 The check prompt adds a substring grounding rule the scorer never had, `src/features/scoring/check.ts:78`
**Problem**: `CHECK_SYSTEM_PROMPT` reads the shared `SKILL_GROUNDING_CRITERION` at line 71 (verified: the constant is interpolated there, and `rubric.ts:149` interpolates the same constant into `matchedSkills`'s schema description). Line 78 then adds, in this file's own words: "A clear synonym counts as grounded. So does the skill appearing as part of a longer phrase, or in the title rather than the description." The synonym and title halves merely restate the constant. "As part of a longer phrase" is a new rule, and as written it tells the checker that `Java` claimed against a posting that says `JavaScript`, or `Go` against `Django`, is grounded, because each name does appear as part of a longer phrase. That is the substring match `rubric.ts:202-206` describes as "the exact false claim this filter exists to stop", and it is looser than the criterion the scorer produced the claims under.
**Why it matters**: AC-2 exists so the check "can never flag" a synonym the scorer counted; it says nothing about the check being told to accept more than the scorer was, because the spec did not anticipate the check being handed a looser rule. The direction matters: a check that is stricter than the scorer produces visible false flags a reader can argue with; a check that is looser silently passes exactly the over-claim (a fragment of a different word) that a fabricated match most often is. The feature's `Done when` in `docs/scope/scope.md` is "a fabricated skill in the reasoning is caught"; this sentence instructs the second vendor not to catch one whole class of them. `verify.md` step 10 noticed the extra sentence when its `"clear synonym"` grep returned two hits and amended the step to grep the identifier instead, which proves the constant is shared but does not judge what the extra sentence says. No test can see this: `check.test.ts:172-180` asserts only that the constant's text is present.
**Suggested fix**: Delete line 78, or replace it with a sentence that says what was presumably meant and forbids the fragment reading, for example that a name counts when it appears as a whole word inside a longer phrase (PostgreSQL inside "PostgreSQL administration") and does not count when it is only a fragment of a different word (Java inside JavaScript). Whichever form is chosen, the spec's own logic argues it belongs in `SKILL_GROUNDING_CRITERION` so both vendors are held to it, not in a sentence only one of them reads.

**RESOLVED 2026-09-09 in `f0bbfb2`.** The finding was verified in the code before being acted on, not taken on the reviewer's word. The offending sentence was **not** simply deleted, because it was reaching for a real case: a posting saying "Kubernetes administration" genuinely should ground a claim of "Kubernetes", and a check refusing that would flag true claims constantly. The distinction is word boundary, not substring, so line 78 became three lines that keep the legitimate case and refuse the fragment one explicitly, each with its own example:

- "A clear synonym counts as grounded, and so does the skill appearing in the title rather than in the description."
- "A skill also counts as grounded when it appears as a COMPLETE TERM inside a longer phrase, so `Kubernetes administration` grounds `Kubernetes`."
- "It does NOT count when the claimed name is only a fragment of a longer word, so `JavaScript` does not ground `Java`."

`check.ts`'s own doc comment now records why the wording is load bearing and which direction the dangerous error runs in, so a later edit cannot casually reintroduce it.

**The test gap that let it through is closed too, and that half matters more than the sentence.** The reviewer's point that `check.test.ts` could only assert the constant was PRESENT, and so was blind to a sentence contradicting it, is the same shape `src/features/scoring/eval/prompt.test.ts` was corrected for on 2026-09-07 when a comma formatted `191,919` walked past a search for `191919`. The same correction was applied here: the **whole** rendered `CHECK_SYSTEM_PROMPT` is now pinned byte for byte against a fixture (27 lines), so any added sentence fails and has to be read by a person. A second, narrower test names the specific defect by regex so a reviewer re-adding it in different words gets a message saying why.

Both were broken on purpose **after** the commit hooks reformatted the files, per the 2026-09-05 reflex. Re-adding the original sentence verbatim failed both tests. Re-adding the same rule in **different words** ("A claim also counts when the name appears anywhere inside another word") slipped past the regex guard and **was still caught by the whole render pin**, which is exactly the division of labour the pin exists for and the reason it is not redundant with the regex.

## Minor

### 🟡 The paid latency run can time out and lose its own deliverable, `test/integration/cross-vendor-check-live.test.ts:111-120`

> **RESOLVED** in `f0bbfb2`, and this is the finding that could have cost real money twice. Two changes. First, the test now carries its own timeout, `TEST_TIMEOUT_MS = LATENCY_SAMPLES * TIERS.ai_check.timeoutMs + 30_000`, which is **derived rather than picked**: it reads `ai_check`'s configured ceiling so a future re-derivation under AC-6 moves it too, and the added 30 seconds covers the fixture mint and session exchange that precede the first call. At today's values that is 130 seconds against the `integration` project's 30 second default, so a slow but entirely healthy vendor day can no longer fail this test on the clock after spending every one of its calls. Second, the artifact is now written by a `save()` helper called after **every** call rather than once after the loop, and it records `samplesTaken`, `samplesExpected` and a `complete` flag, so a failure on call four keeps the three latencies already paid for. That was the same lesson as the earlier `console.log` loss applied only halfway: the fix had moved from a stream to a file but had left the write in the same place at the end. A stale comment still describing the old end of loop write was corrected in the same commit.
**Problem**: The single `it` makes `LATENCY_SAMPLES = 5` sequential `checkFitScore()` calls under the `integration` project's `testTimeout: 30_000` (`vitest.config.mts`). Each call can legitimately take up to `TIERS.ai_check.timeoutMs` (now 20 000 ms), so the worst case is 100 seconds against a 30 second budget, and the observed spread already includes two calls near 6 seconds; five of those is the limit. The artifact is written at line 192-215, after the loop, so a test timeout mid-loop discards every latency collected so far. That is the exact loss the file's own comment at lines 169-191 says the artifact was added to prevent, only with a different trigger.
**Why it matters**: The run costs real money and its output is the only source of AC-6's figure. A timeout would report a failed test and no numbers, and the way back is to pay again.
**Suggested fix**: Give this `it` its own timeout derived from the tier (`LATENCY_SAMPLES * TIERS.ai_check.timeoutMs` plus a margin) via the test options argument, and write the artifact incrementally after each call rather than once after the loop.

### 🟡 A test comment claims a proof its assertion cannot make, `src/features/scoring/check.test.ts:172-180`

> **RESOLVED** in `3d4f221`. The comment was not merely reworded, because the finding was that the ASSERTION was the wrong one. The case is now split in two. The first keeps `toContain` and says plainly what it proves, that the criterion's text reaches the rendered prompt, and states outright that it does NOT prove the constant is read, since a `check.ts` pasting the same sentence as a literal would pass identically. The second is a structural guard following the source reading pattern `tiers.test.ts` already uses for its import ban, comment stripping included: it reads `check.ts`, strips block and line comments, then asserts the source CONTAINS the identifier `SKILL_GROUNDING_CRITERION` and does NOT contain a literal copy of the criterion's text. Broken on purpose after the commit hooks ran, per the 2026-09-05 reflex, which matters especially here because a source reading test is the kind Prettier can silently invalidate: pasting the criterion verbatim failed, and referencing the constant only inside a comment ALSO failed, which is what proves the comment stripping is doing real work rather than decorating the regex.

### 🟡 The partition test cannot catch the case its comment says it exists for, `src/features/scoring/score-listings.test.ts:453-487` (and `score-listings.ts:121-136`)

> **RESOLVED** in `3d4f221`, in the code first and the prose second. The tally is now exhaustive over `ListingOutcome["check"]` by construction: `typeof check === "string"` splits the two skip variants, each narrowed by name, and the remaining branch ends in `const exhaustive: never = check`, with the `Result` side split into its failure and its two decision branches explicitly. ### 🟡 Twenty concurrent Gemini calls per page and no stated rate limit headroom (inferred, not verified), `src/features/scoring/score-listings.ts:79-83`
**Problem**: `scoreListings()` dispatches up to twenty `scoreThenCheck()` chains at once, so as scores resolve the page can have up to twenty `ai_check` calls in flight against `gemini-3.5-flash-lite` with `maxRetries: 0`. Nothing in the repo records the Google AI Studio project's quota tier, and Google's per-model requests-per-minute limits on the lower tiers are, to my knowledge, low enough that a burst of twenty could return 429s; I could not verify the current figure for this model from inside the repo. A 429 classifies as `external_service_failed` and renders every affected card as AC-7's unverifiable note.
**Why it matters**: The verify run observed 12 requests over a day, never twenty at once, so the first real `/search` with a full profile is the first time this burst happens. It would read as the check being flaky rather than as a quota.
**Suggested fix**: Confirm the AI Studio project's tier and its RPM limit for this model, and record the figure beside `ai_check` in `tiers.ts` the way `timeoutMs` is now recorded. If the limit is below twenty per burst, this is a design question for the spec (a concurrency bound on the check, or a paid tier), not a code fix.

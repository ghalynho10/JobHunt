## Summary

This change lands the six tables spec 0003 calls for: `profile`, `profile_skill`, `work_experience`, `job_preference`, `application`, `application_answer`, plus a shared `updated_at` trigger, twenty three row level security policies, and an explicit grant per table with `anon` and `service_role` holding nothing. The schema matches the spec's data model sketch column for column, the composite foreign key that ties `application_answer.profile_id` to its parent application is a genuinely careful piece of design, and the expand then contract discipline (the create migration merged and was confirmed live on production before the drop migration was even written) was followed correctly across two separate pull requests. `readOwnProfile()` and the repointed health page hold up under the project's error model: the named span opens first, the session is checked, the row is parsed with Zod, and every failure kind used is a real member of `FailureKind`. I found no correctness or security bugs in the SQL itself. The one real gap, covered below as the sole Major, is that the schema level guarantees on five of the six tables (duplicate prevention, cross user write refusal, cascading deletes, pay pairing) have no automated regression test today, only a hand run SQL script.

## Major

### 🟠 Five of the six tables' constraints have no automated regression test, `supabase/migrations/20260825162457_data_model.sql:350` to `:443`
**Problem**: `test/integration/isolation.test.ts` and `test/integration/profile-read.test.ts` exercise `profile` only: one user cannot read another's profile row, and `readOwnProfile()` returns the right shape and the right failure kinds. Nothing in the current test suite touches `profile_skill`, `work_experience`, `job_preference`, `application`, or `application_answer`. That means the case insensitive skill uniqueness (AC-10), the duplicate application refusal (AC-7), the orphan application foreign key (AC-8), the pay pairing and range checks on both tables (AC-9), the work history date rules (AC-11), and the `with check` refusal that stops a user from moving a row under someone else's profile on four of those five tables (AC-4) are proved today only by `docs/specs/0003-data-model/verify.sql`, a script a person has to open in the Supabase SQL editor and read by eye. I confirmed this by reading every file under `test/integration/` and grepping for the table and column names those constraints touch: nothing matched outside the profile tests.
**Why it matters**: These are exactly the guarantees spec 0003 says exist so "a caller that forgets to check for a duplicate application still cannot create one." A future migration that loosens a check constraint by accident, or a policy edit that drops a `with check` clause, would pass `pnpm typecheck` and `pnpm test` cleanly and only be caught if someone remembers to paste `verify.sql` into a database by hand. I want to be fair to the team's own reasoning here: `docs/scope/scope.md` line 96 records that this was a deliberate, considered call made on 2026 08 27 by the project's own `/test` step, not an oversight, and it names the exact trigger for revisiting it (feature 9 and feature 12 building the write paths that hit these constraints through real code). I am raising it anyway because the review brief asks me to judge test adequacy against the current state of the repository, and by that measure this is real, security relevant branching logic sitting outside the automated safety net.
**Suggested fix**: A full port of all eighty three checks in `verify.sql` into Vitest would be the kind of duplication the team already decided against, and I do not think that is the right ask. A smaller, well aimed slice would close most of the risk: one test proving the `with check` trap on a second table besides `profile` (the update that changes zero rows rather than raising, which is the one behavior spec 0003 calls out as easy to get backwards), and one test proving the duplicate application unique constraint. Both are cheap, both are the kind of regression a schema refactor is most likely to break silently, and both would fail loudly in CI instead of waiting for the next manual SQL run.

## Minor

### 🟡 `Profile` type export has no doc comment, `src/features/profile/queries.ts:61`
**Problem**: `export type Profile = z.infer<typeof profileSchema>;` carries no comment of its own. The doc comment above it documents `profileSchema`, a variable that is not exported, and the comment below documents `readOwnProfile`, a different export. `Profile` itself is left without the doc comment AGENTS.md requires on every export.
**Why it matters**: This is a small thing on its own, but the rule exists so a later session can tell why an exported shape looks the way it does without re deriving it from the schema. Left unfixed, it is the kind of gap that is easy to copy into the next feature's query module.
**Suggested fix**: A one line comment above the `export type Profile` line, even just pointing back at `profileSchema`'s own comment for the reasoning, satisfies the rule.

## Strengths

- The composite foreign key on `application_answer` (`application_id, profile_id`) referencing `application (id, profile_id)`, with a plain, non partial, non expression unique constraint on `application` existing only to be its target, is real schema craftsmanship. It makes an answer belonging to the wrong user structurally impossible rather than relying on a policy alone to catch it, and the comment explaining why (`supabase/migrations/20260825162457_data_model.sql:222` to `:227`) is exactly the kind of "why, not what" comment AGENTS.md asks for.
- Every one of the twenty three row level security policies carries exactly the clause its action permits: `select` and `delete` with `using` only, `insert` with `with check` only, `update` with both. This is a real and easy to get backwards Postgres subtlety, and `docs/specs/0003-data-model/verify-production.sql` proves it mechanically with a query over `pg_policies` rather than by eye.
- `verify.sql` is a genuinely well built proof. It runs entirely under a throwaway user so it never touches the dev one and dev two fixtures, every refusal it checks rolls itself back inside a plpgsql exception block, and it explicitly proves the AC-4 trap correctly: an update aimed at another user's row is not an error, it changes zero rows, and the script asserts the row count rather than just the absence of an exception, which is the exact distinction the spec calls out as easy to get wrong.
- The expand then contract sequencing was followed for real, not just described. The create migration (`20260825162457_data_model.sql`) and the drop migration (`20260825175250_drop_scaffold_check.sql`) sit in separate commits behind separate pull requests, the drop's own comment records that production was confirmed serving `readOwnProfile()` before it was written, and `verify-production.sql` is a read only script built specifically so proving this on production carries no risk of leaving a row behind.

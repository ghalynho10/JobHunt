# Review, feat/apply-redirect-and-application-record, 2026-09-05

**Reviewed by**: Claude Sonnet 5 (author on unspecified/multiple sessions, per spec 0014's revision history)
**Scope**: 52 files, branch vs `main` (merge base `d3b672c46`)
**Verdict**: Blocked

## Summary

Feature 12 adds the apply-and-record loop (`recordApplication`/`removeApplication`, `/applications`, the applied marker on `/search`) and, at the end of the branch, a fix to `src/proxy.ts` for a real bug the team found at runtime: the proxy's own session refresh was writing a cookie into a Server Action's response, forcing a `/search` re-render and spending one of 25 weekly Adzuna calls. The application read/write paths themselves are careful and well tested: caller verification is independent per action, row level security is the real guarantee, the listing is re-parsed on arrival despite the closure encryption, and failure mapping never leaks a raw Postgres error. The proxy fix, however, keys its cookie-withholding branch on the presence of the `next-action` request header, and that header is only set for the JavaScript-driven fetch dispatch of a Server Action — Next's own bundled source shows a plain (no-JS or pre-hydration) form submission of the same action arrives as `multipart/form-data` with no such header, and is still treated as a valid action dispatch. That gap reopens the exact cost this fix exists to close, for a request shape the team had already observed behaves differently elsewhere in this same spec (the AC-21 "hand built POST" finding). A second, lower-confidence concern: the spec's claim that the session "stays alive" across repeated actions spaced beyond `refresh_token_reuse_interval` with no intervening navigation is asserted with no measurement recorded anywhere, and GoTrue's own documented reuse-detection behavior suggests it may not hold.

## Blockers

### 🔴 The `next-action` header is absent on a real, supported Server Action request shape, so the cookie-withholding fix does not cover it, `src/proxy.ts:36-38,87`
**Problem**: The withholding branch is `if (request.headers.has(SERVER_ACTION_HEADER))` where `SERVER_ACTION_HEADER = "next-action"`. The doc comment above it (lines 36-38) asserts: "A request without it is not dispatched as an action either, so nothing is lost by trusting it here." That is not what Next.js actually does. `node_modules/next/dist/server/lib/server-action-request-meta.js` computes `isPossibleServerAction` as `isFetchAction || isURLEncodedAction || isMultipartAction`, and only `isFetchAction` depends on the `next-action` header (`actionId = req.headers.get(ACTION_HEADER)`). `isMultipartAction` and `isURLEncodedAction` are derived purely from `req.method === "POST"` plus `content-type`, which is exactly the progressive-enhancement path React 19 builds into `<form action={serverAction}>` (`ApplyControl` in `src/features/applications/apply-control.tsx:94` renders exactly this form) so the button still works before hydration completes or with JavaScript disabled. A request in that shape carries no `next-action` header — browsers do not let a plain form submission set an arbitrary header — so the proxy's branch does not fire, `setAll` falls through to its normal path, the refreshed session cookie is written to the response, and Next puts the `/search` re-render into that response exactly as it did before this fix (the same mechanism `server-actions.md:47` and the bug this branch was written to close both document).
**Why it matters**: This is the single load-bearing guarantee of the whole feature — spec 0014 calls it "the design's whole purpose" and the reason the branch exists at all. A user on a slow connection who clicks "Mark as applied" before hydration finishes, a user with JavaScript disabled, or an automated/assistive client that submits the native form, would silently spend one of the account's 25 weekly Adzuna calls on every apply attempted while their access token has expired — precisely the scenario `test/integration/proxy-action-refresh.test.ts` was written to prevent, but that test (and every other test asserting this behavior) only ever constructs a request with the `next-action` header set (`requestWith({ asServerAction: true })` in that file sets `"next-action": "0123..."` explicitly), so this gap has zero coverage in either direction. The project had already independently discovered that "the no JavaScript request shape" behaves differently for this exact action (recorded in spec 0014's Follow-up and `## What the build measured`, regarding AC-21's stale-build case) and did not carry that lesson over to this fix.
**Suggested fix**: Detect a possible Server Action the same way Next does — check method `POST` plus `content-type` (`multipart/form-data` or `application/x-www-form-urlencoded`) in addition to the `next-action` header — or find a signal from Next itself that identifies all three shapes. Add a test that drives the withholding branch through a `multipart/form-data` POST with no `next-action` header and confirms the cookie is still withheld.

## Major

### 🟠 AC-20a's "confirmed alive" claim for repeated actions beyond the reuse window is unverified and, per GoTrue's own documented behavior, likely false, `src/proxy.ts:60-93`, `docs/specs/0014-apply-redirect-and-application-record/index.md:51`
**Problem**: AC-20a's prose says the trade is safe because "the browser keeps its stale cookie until its next ordinary request, which refreshes and persists as usual," and separately claims this was "confirmed alive across three consecutive applies and a twelve second pause." That specific claim appears nowhere else in this exceptionally well-documented spec: `verify.md` records exact numbers and browser-driven methods for every other quantitative claim in this feature (counter values, header names, byte counts, encryption keys), but this one has no corresponding step, no method, and no numbers. The scenario it needs to cover is two (or more) Server Action requests on the same expired-token session with **no ordinary request between them** and **more than `refresh_token_reuse_interval` (10 seconds, confirmed in the running container's `supabase/config.toml`: `refresh_token_reuse_interval = 10`) elapsed between them** — exactly the shape a reader gets by opening `/search`, marking one job applied, reading for 15 seconds, then marking a second job applied with no page navigation in between. Per Supabase's own published documentation (github.com/supabase/auth), reuse of an already-rotated refresh token **inside** the interval returns the same child token, but "should a reuse attempt not fall under the allowed exceptions, the whole session is regarded as terminated and all refresh tokens belonging to it are marked as revoked." Since the proxy withholds every refreshed cookie from the browser on every Server Action request, the browser's stored refresh token is never updated by an action, so a second action-triggered refresh after the window closes presents the same already-used token outside its grace period.
**Why it matters**: If GoTrue's documented reuse detection fires here, the entire refresh token family — including the token silently handed to the *first* action's own request — is revoked. The user's browser still holds what looks like a valid session cookie, but every subsequent request (action or ordinary) will fail to refresh, `callerId()` in `src/features/applications/actions.ts` will return `session_missing`, and the user is effectively signed out until they explicitly re-authenticate, with no visible cause. This does surface through the existing `session_missing` failure path rather than crashing or reading as silent success, so it is not a data-integrity or budget problem — but it is a real, currently-unmeasured session correctness regression introduced by this exact fix, on a specific claim the spec asserts as settled without evidence.
**Suggested fix**: Actually drive the scenario described (two+ actions on one expired session, spaced beyond 10 seconds, with zero ordinary requests in between) against the real stack and record the result with the same rigor the rest of this spec uses, or add the missing method/numbers to `verify.md` if it was in fact tested. If the session does get revoked, decide whether that is acceptable (and word AC-20a accordingly) or whether the proxy needs to let through a cookie write on some cadence even for actions.

## Minor

### 🟡 The stale-build catch is a blanket `catch` with no reporting, so it also swallows and mislabels unrelated client errors, `src/features/applications/apply-control.tsx:74-89`
**Problem**: `useActionState`'s async callback wraps `action()` in a bare `try { ... } catch { return failedState(APPLICATION_FAILURES.stale_build.message); }`. The doc comment justifies this for the one case it was built for (a dispatch Next itself refuses because the build's closure key rotated), but the same `catch` also fires for a genuine network failure, a browser extension blocking the request, or any other client-side exception unrelated to a stale build. In every one of those cases the reader is told "This page is out of date. Refresh and try again," which is actively misleading when the real problem is transient, and — per `AGENTS.md`'s failure model — nothing here calls `Sentry.captureException` or anything equivalent, so none of those other causes are ever visible to the team either. The spec's own text ("the one failure in the feature that never passes through `failure()` and never reaches Sentry") documents that the *stale-build* case is invisible to Sentry as an accepted tradeoff, but does not seem to have considered that the same silence now also covers every other client-side failure mode this catch happens to intercept.
**Why it matters**: A real client bug or a spike in some other client failure would be indistinguishable from ordinary stale-build refusals (an expected, frequent occurrence on a project that "deploys often," per the spec's own Consequences), so a genuine regression here could hide indefinitely behind a copy string that says nothing is wrong beyond staleness.
**Suggested fix**: At minimum, capture the caught error with Sentry (client-side) before returning the stale-build message, so a real anomaly is still visible even though the reader sees one generic sentence either way.

## Strengths

- The two Server Actions (`src/features/applications/actions.ts`) verify their own caller independently, narrow every write and delete by the caller's own id in the statement itself in addition to row level security, and never let a raw Postgres error reach the reader — the failure-mapping table (`failures.ts`) is exactly as disciplined as the rest of this codebase's error model.
- `listingSnapshotSchema` genuinely re-parses the inline closure's payload rather than trusting the encryption, and the `postedAt` tightening closes a real gap (an unparseable date reaching Postgres as `22007` and being reported as an outage) with a concrete, well-reasoned schema.
- The test suite is unusually honest about its own limits: `test/integration/application-actions.test.ts` explicitly says its own cookie-write assertion "does not guard AC-20 on its own" and names the real guard; `src/features/applications/actions.test.ts` documents the same escaped-vacuous-test history and fixes it with a source-level regression guard instead.

## Test coverage

The application write/read paths are well covered by real integration tests against actual constraints and policies (unique/foreign-key/check violations, row-level isolation between two real users, empty-id and malformed-id removal paths). The gap that matters is that every test exercising the proxy's Server Action branch (`test/integration/proxy-action-refresh.test.ts`) constructs the request with the `next-action` header set by hand, so the entire progressive-enhancement/no-header request shape identified above is untested in both directions — a test in that shape would have failed today and shown the gap immediately. The two scenarios in `## Major` above (the reuse-interval edge case) are likewise absent from both the automated suite and `verify.md`'s manual steps.

## Verification of these findings, by the main thread, same day

_The reviewer read the code and Next's bundled source. Both of its top findings turn on runtime behaviour, so each was driven against a real production build before being accepted. Two did not survive as stated. The reviewer's reasoning is kept above in full; what follows is what the measurements showed._

### The blocker does not hold for the apply control, and the reason is specific

**Not reproduced.** With JavaScript disabled, pressing `Mark as applied` produced no `POST`, no row, and no counter movement (15 to 16 across the whole run, which is the page load alone).

The reviewer's account of Next is right in general: `isPossibleServerAction` is `isFetchAction || isURLEncodedAction || isMultipartAction`, and only the first needs the `next-action` header. What is wrong is the claim that `ApplyControl` renders such a form. It does not, and the served markup says so plainly:

```
<form action="javascript:throw new Error('React form unexpectedly submitted.')">
```

with **zero hidden inputs**, no `$ACTION_ID_` field. That sentinel is React's own, emitted when a form's action is a **client** function rather than a Server Action reference. `ApplyControl` passes `useActionState` an inline client closure (the `try`/`catch` AC-21 requires), so React cannot progressively enhance it and deliberately makes native submission impossible. There is no no-JavaScript request shape for this control to exploit, before hydration or after.

**But the reviewer found a real defect underneath the wrong example.** The comment at `src/proxy.ts:36-38` says "A request without it is not dispatched as an action either, so nothing is lost by trusting it here." That is false as a general statement, and this repo has forms it is false for: `remove-form.tsx:40` passes `removeApplication` **directly** to `useActionState`, as do the three profile forms, so those are genuinely progressively enhanced and their no-JavaScript submissions do bypass the carve out. It costs nothing today, because no page hosting them spends an Adzuna call. It would cost something the first time a Server Action is added to a page that does. **Major, not blocker: wrong comment and a fragile signal, not a live budget leak.**

### The major's predicted failure does not occur, but its criticism of the evidence was correct

**Not reproduced.** One apply on an expired session, then **16 seconds** with no intervening request, then a second apply: both succeeded, both rows landed, no alert on either, and the following navigation returned `200` still signed in with a freshly rotated cookie. The token family was not revoked.

**The reviewer was right that the original evidence did not cover this.** The run recorded in AC-20a spaced its three applies about six seconds apart, inside the reuse interval, and its twelve second pause came before an ordinary **navigation**, not before a second action. So the exact dangerous shape, two actions more than ten seconds apart with nothing between them, was never driven, and "confirmed alive across three consecutive applies and a twelve second pause" implied more than had been measured. It is measured now, and the claim holds. **The wording in AC-20a should say what was actually driven.**

### The minor stands

The blanket `catch` in `apply-control.tsx` really does relabel every client side failure as a stale build and reports none of them anywhere. Not verified away, and worth fixing.

### What this leaves

One major (correct the proxy comment, and decide whether to broaden the detection to the two shapes Next also accepts), one major downgraded to a wording fix in AC-20a, and one minor. No blocker.

**Worth noting about the review itself:** the blocker was wrong about this component but right about the mechanism, and chasing it is what surfaced the genuinely wrong comment and the progressively enhanced forms nobody had considered. A finding does not have to be correct to be valuable.

## Summary

This change builds spec 0017's `pnpm eval`: a fourth Vitest project that scores feature 15's sixteen ground truth pairs five times each through the real `scoreListing()` path under one minted fixture session, decides each pair by a pure verdict function (strict majority with a 3 of 5 floor, the `acceptableBands` no majority exception, the `stability-probe` every success rule, the three way preference leak comparison), prints a table, and writes a JSON report carrying the resolved model id and a hash of `BAND_ANCHORS`. The verdict rules are correct on a line by line read and each branch has a constructed fixture; the paid project is genuinely unreachable from `pnpm test` (`--project unit`) and `pnpm test:integration` (two named projects), verified in `package.json` and `ci.yml`; `maxConcurrency` and `fileParallelism` are both honoured per project in the installed Vitest 4.1.11 (`NonProjectOptions` excludes neither); and the AC-10 hash recomputes independently to `1b45f524b356`. The headline problem sits in the one seam nothing tests: when the `beforeAll` gate throws, `afterAll` still runs (proved against the installed runner) and writes a report that says `status: "completed"`, `filter: null`, all sixteen pairs `skipped`, which describes a refused run as a completed full run. Beside that, the printed table glues `INCONCLUSIVE` to the pair id, the AC-11 grep step in `verify.md` now matches the gitignored reports and cannot pass, and the scope row's "closing both gaps" overstates what `/test` closed.

## Major

### 🟠 A refused or failed `beforeAll` writes a report that reads as a completed full run, `test/eval/harness.test.ts:120`
**Problem**: `afterAll` (lines 120 to 187) assumes the run reached its test bodies. When the `beforeAll` (lines 94 to 111) throws, whether from `validateGroundTruth()` returning an issue, `mintFixtureUser()` failing, or `mintSession()` failing, Vitest 4.1.11 still runs `afterAll` and marks every test skipped. I proved this against the installed runner with a scratch file (a `beforeAll` that throws, two `it.concurrent` bodies, an `afterAll` that prints): the output was `AFTERALL_RAN attempted=0`, `Tests 2 skipped (2)`. In the harness that path produces a report with `status: "completed"`, `filter: null`, `skipped` holding all sixteen ids (because `attempted` is empty), `incomplete: []`, `pairs: []`, and `preferenceLeak: leak-check-skipped, preference-match did not run.`, and prints `run completed` under the table. Nothing in the report says the data gate refused or the mint failed.
**Why it matters**: The report is the one artifact spec 0017 says people compare weeks later, and AC-8's own reason for keeping `skipped` and `incomplete` apart (report.ts line 44: "folding them together would describe an aborted run as a filtered one") is exactly what happens here: a run that never started is described as a full run whose pairs were all filtered out by no filter. The command's exit code is non zero, so the terminal is honest, but the file on disk is the "default that reads like success" AGENTS.md's no silent failures rule forbids. The `verify.md` duplicate id step (line 26) checks the throw and the skipped count and never opens the report this path writes, which is why the hand verification passed it. A secondary consequence on the same lines: the report literal (lines 133 to 151), including `resolvedModel()` and `preferenceLeakCheck()`, is assembled outside the `try`/`finally` at 153 to 170, so a throw during assembly skips `deleteFixtureUser` and leaves the minted user behind.
**Suggested fix**: Record that setup did not complete. One shape: a module scoped `setupFailure: string | undefined` set inside a `try`/`catch` around the `beforeAll` body (rethrowing after recording), and in `afterAll` either skip the write entirely when it is set, or write `status: "not-started"` with the failure message and print `RUN NOT STARTED: <reason>` instead of `run completed`. Move the report assembly inside the `try` so cleanup always runs. Add to the `verify.md` duplicate id step what the report says (or that none is written), and consider the same for a stopped stack between `require-stack` and the mint.

## Minor

### 🟡 `INCONCLUSIVE` rows print with no gap before the pair id, `test/eval/report.ts:82`
**Problem**: `verdict.status.toUpperCase().padEnd(12)` pads `PASS` and `FAIL` to twelve characters, but `INCONCLUSIVE` is exactly twelve, so `padEnd(12)` adds nothing and line 88 concatenates the pair id straight onto it. Rendered through the real `formatReportTable()` with a real inconclusive verdict shape, the row is `  INCONCLUSIVEcontrol-one-gap       good_match, 1 of 5 succeeded (insufficient-successes)`. The two row tests in `test/helpers/eval-report.test.ts` do not catch it: `prints the status, the pair id and the bands observed` (line 122) asserts only the `PASS` row, and `never renders a pair row without its denominator` (line 135) selects rows with `/^ {2}(PASS|FAIL|INCONCLUSIVE)/`, which matches the glued row as happily as a spaced one.
**Why it matters**: This is the table AC-1 asks the command to print, and `inconclusive` is the verdict a reader most needs to pick out at a glance. It is cosmetic, but the test that appears to cover the row does not, which is the shape the 2026 09 07 reflex warns about.
**Suggested fix**: Widen the status column to at least fourteen and name it once. The column width is currently hard coded in four places that must agree: the `padEnd(12)` on line 82, the `14 + width` cause indent on line 97, and the literal spacing of the `SKIPPED` and `INCOMPLETE` lines on 104 and 108. Then add a test asserting the inconclusive row matches `^ {2}INCONCLUSIVE\s+control-one-gap`.

### 🟡 The AC-11 grep step recurses into the gitignored reports and now fails, `docs/specs/0017-eval-harness-runner/verify.md:21`
**Problem**: `grep -rn "openai\|gpt-\|gemini\|anthropic" test/eval/ test/helpers/eval-verdict.ts` descends into `test/eval/.output/`, where every report's `model` field names the vendor's model (`gpt-5.6-luna` in thirteen files, `gemini-3.5-flash-lite` in the AC-11 vendor swap run). Run today, it exits 0 with fourteen matches. The step is ticked and instructs "check the exit status, do not append `|| echo`", which is right, but the status it now returns says the opposite of what the step means.
**Why it matters**: The step cannot be reproduced after any paid run, so its tick is stale the moment the harness does its job. This is the 2026 09 07 reflex about naming the scope a check ran over: the source tree is clean, the check's scope was wider than the claim, and it is the paid artifact, not the code, that trips it.
**Suggested fix**: Scope the grep to source, `--include='*.ts'` or `--exclude-dir=.output`, and rerun it before ticking. The code itself is clean: I ran the narrowed form and it exits 1 with no matches.

### 🟡 The scope row says `/test` closed both recorded gaps; it closed one, `docs/scope/scope.md:322`
**Problem**: `verify.md`'s "Known gaps, for `/test`" (line 48) names two: the harness file's own orchestration (the abort flow, the `skipped` against `incomplete` split, the report assembly) and `report.ts`. The 27 tests the row counts are `eval-report.test.ts` (21, closes the second gap), `eval-filter.test.ts` (4, the `-t` channel, not a listed gap) and two for `resolvedModel()` (not a listed gap). The first gap is untouched: no test drives the harness's `afterAll` or how it computes `skipped` and `incomplete`, and the Major above sits exactly there.
**Why it matters**: A later reader trusts the row and believes the orchestration is locked. It is not, and `verify.md` itself still lists it as open, so the two documents disagree.
**Suggested fix**: Reword the row to say the report gap is closed and the orchestration gap remains (or close it: the `afterAll` logic could be lifted into a pure `assembleReport(attempted, verdicts, abortReason, setupFailure, ...)` in `test/helpers/` and tested free, leaving the harness to call it).

### 🟡 The three preference pair ids are literals nothing ties to `PAIRS`, `test/helpers/eval-verdict.ts:75`
**Problem**: `PREFERENCE_BASELINE_ID` and `PREFERENCE_CONFLICT_IDS` name `preference-match`, `preference-violation` and `preference-title-conflict` as strings. Spec 0016's guard test pins only `preference-title-conflict` by id (`src/features/scoring/eval/ground-truth.test.ts:503`); the other two are reached there by tag. Rename either in `pairs.ts` and every full `pnpm eval` reports `leak-check-skipped, preference-match did not run.` and exits 0, since AC-7 does not fail a run on a skipped check.
**Why it matters**: AC-5 is the one structural leak detector the set has, and this turns it off permanently with a green exit and one line of table text as the only tell. The harness's own `afterAll` (line 126) even handles `baselinePair === undefined` gracefully, which makes the path quieter still.
**Suggested fix**: A free unit test asserting each of the three ids exists in `PAIRS` carrying `preference-isolation`, or derive the trio from the tag and assert exactly three with one designated baseline.

### 🟡 No test for a strict majority landing outside a present `acceptableBands`, `test/helpers/eval-verdict.test.ts:198`
**Problem**: The three `acceptableBands` cases are majority inside (pass, line 198), no majority inside (pass, line 266), no majority outside (inconclusive, line 288). Missing is the fail: `boundary-seniority-gap` with `acceptableBands: ["weak_match", "not_a_match"]` and three `possible_match` plus two `weak_match`, which must be `fail` with band `possible_match`. A mutation that returned `pass` from the majority branch whenever `acceptableBands` is present survives the suite.
**Why it matters**: The scope row records "seven of eight mutations caught"; this is a ninth the suite would not catch, on the one real pair that carries the field.
**Suggested fix**: Add that case beside line 198.

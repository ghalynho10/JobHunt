# Verify: fit scoring with shown reasoning · spec 0015 · updated 2026-09-07

_Steps derived from spec 0015 acceptance criteria. `/check verify` runs these; `/test` locks the durable ones._

Every step below needs a signed in caller with a real profile, a real Adzuna
search, and real `ai_scoring` budget left, unless it says otherwise. A scored
`/search` render spends up to 20 `ai_scoring` calls plus one Adzuna call, so
plan the run rather than reloading freely.

**Two counter reading rules this feature inherits, both learned the hard way.**
Read `usage_gate_counter` through `test/helpers/database.ts` or `psql`, never
through the Supabase Data API: that table carries no row level security policy
(spec 0011), so PostgREST cannot see it and every reading comes back zero
whatever the app did. And make any counter move on purpose once before trusting
a "did not move" reading.

## Value sourcing

_One step per row of spec 0015's Value sourcing table, so each value's SOURCE is exercised rather than only its presence._

- [x] Score the same listing against two different profiles → the band, the matched skills and the reasoning all change → the score comes from the caller's own profile, not from the listing alone. **Converted into a real test on 2026-09-07**, `test/integration/fit-scoring-isolation-live.test.ts`, behind `TEST_LIVE_MODEL_CALLS_ENABLED`: one backend heavy posting scored against a backend profile and a pure frontend profile with no skill in common, asserting the backend profile bands strictly higher. _Passed on two independent runs, 4 tests in 15.91s and 14.45s, so the direction is not a single lucky sample._ **The step's own wording asks for slightly more than can honestly be asserted, and the test deliberately does less.** Comparing `matchedSkills` between the two proves nothing: `normalizeFitScore()` filters each answer to that caller's own skill names, so two profiles sharing no skills come back with disjoint lists whatever the model said, or even if it said nothing. The band is the only field here a profile can move that the filter cannot fake, so the band is what is held.
- [x] Sign in as user A, search, note a band; sign in as user B with a different profile and search the same terms → B never sees A's score → the profile scored is always the caller's own, through `readOwnProfile()`. **Converted from a manual browser check into a real integration test on 2026-09-07**, `test/integration/fit-scoring-isolation-live.test.ts`, matching how every other cross account proof here works: two real minted sessions, two profiles seeded through their own clients under the real policies, `readScoringProfile()` called once as each. Each account resolves to its own skills AND is checked for the absence of the other's, since a read returning both rows would pass the first assertion alone. _It needs no vendor call, so it runs on every `pnpm test:integration` rather than behind the live flag._ **Proved non vacuous**: with row level security disabled on `profile_skill` it fails, reading all ten skills across both accounts instead of two, and passes again once the policy is back.
- [x] Add a skill to `/profile` that no posting mentions, then search → it can appear under "Not mentioned in this posting" but never under "Matched in this posting" on a card whose text does not contain it. **Converted into a real test on 2026-09-07** in the same file: `Terraform` is on the profile and absent from the listing's visible text, which the test checks rather than assumes so the fixture cannot drift, and it asserts the name never reaches `matchedSkills`. _Only the "never matched" half is asserted, because only that half is a rule_: this step says the skill "can" appear under not mentioned, and that list is relevance filtered on purpose, so a posting that would not value it legitimately omits it. Asserting its presence would fail on correct behaviour. **The generalisation is the stronger guard and is asserted too**: every name in `matchedSkills` has to actually occur in the text the model was shown, which is what AC-5 claims and what a reader believes when they see the chip.
- [x] Rename a skill in `/profile` (delete plus re-add with different capitalisation) → the card renders the NEW spelling, proving the displayed name comes from the caller's row rather than from the model's echo
- [x] Give a profile more than 50 skills and more than 5 work history entries → the scoring still succeeds and the reasoning references only recent roles → the prompt is bounded by `boundProfile()`, not by the row count. **Already proven by the unit suite, cited here on 2026-09-07 rather than driven again**: `src/features/scoring/rubric.test.ts:271` feeds `boundProfile()` 80 skills and asserts 50 come back, taken from the front of the existing order rather than sampled, and `:284` feeds it 9 work history entries and asserts the 5 most recent, in the order they arrived. **One inference this does not directly cover**: whether `scoreListing()` itself still succeeds against a real vendor when the caller's rows are over sized. The risk is low by construction, since `boundProfile()` runs before the prompt is built, so the vendor never receives an over sized payload either way and the live path is the same one `fit-scoring-live.test.ts` already exercises. Recorded as an inference rather than left to read as measured.
- [x] Set a `minimum_pay` well above every listing's salary, and `remote_preference` to `remote`, then search on site listings → bands still reflect skills and experience; a preference mismatch alone never pushes a listing down a band → the band's source is skills and experience only. **Also converted into a real test on 2026-09-07**, in the same file, behind `TEST_LIVE_MODEL_CALLS_ENABLED` because only a real vendor can fail it: the rule is carried by one sentence of `SCORING_SYSTEM_PROMPT` and nothing in the schema or the parse can enforce it, so a stubbed vendor would only assert a fake answer came back unchanged. _A paired comparison, not a single reading_: the same posting is scored twice against profiles differing in exactly one field, once with no preferences and once with preferences the posting flatly fails (on site against `remote`, 55,000 EUR against a 250,000 EUR minimum), and the clashing band must be no worse. A vacuity guard requires the neutral band to be `good_match` or better first, so two `not_a_match` results cannot pass it. Both tests passed on 2026-09-07, 2 tests in 5.63s. **This is the pair `rubric.ts` says does not exist yet, arriving early, and it does not close spec 0015's Follow-up**: one pair on one posting against a nondeterministic model can catch a preference dragging a band down, but cannot measure how often it happens, which is still feature 16's ground truth harness.
- [x] Break the profile read (stop the database mid render, or point at a bad key) → the page shows `We couldn't read your profile just now…` rather than the "add your skills" sentence, and still renders the results → a failed read never borrows the thin profile's meaning. **Already proven by the unit suite across two files, cited here on 2026-09-07**, and the claim needs both halves. `src/features/scoring/profile-gate.test.ts:137` and `:149` prove the classification: a failed profile read and a failed sections read each resolve to `unavailable`, never `thin`, which is the distinction the whole step rests on. `src/app/(app)/search/page.test.ts:647` then proves what a reader sees for that outcome, asserting the failure sentence appears AND that `Add your skills or work experience` does not, so the two states cannot be confused; `:665` proves it is announced as an alert, and `:668` proves the results still render and nothing was scored. **Asserting the absence of the thin sentence is the half that matters**: a page rendering both would pass a check that only looked for the failure sentence, while telling somebody with a full profile to go and fill it in during an outage.
- [x] After the one time re-sort, confirm each card's band, skills and reasoning still belong to the job title above them → outcomes are paired to their listing before the sort runs, and the pair moves as a unit, so no later step matches by a position that has since changed. **Covered by a plain unit test as of 2026-09-07**, `src/app/(app)/search/page.test.ts`, "keeps each card's own band and reasoning with its own job after the re-sort". No vendor call and no live flag: this is pure pairing and sorting logic in `ScoredResults`, so the outcomes are constructed and real model output would add cost and nondeterminism while proving nothing extra. **It was genuinely missing**, and the two ordering tests beside it do not cover it: they read titles only, so a pairing that sorted correctly while attaching the wrong band to the wrong job satisfies both. Proved by breaking exactly that, taking each row's listing from the sorted array and its outcome from the unsorted one: the list order stays identical, both ordering tests still pass, and only this test fails. **One discrepancy worth recording rather than ticking over.** AC-9 and the spec's Value sourcing table (line 100) both say outcomes are matched back by `sourceJobId`, never the array index. `src/app/(app)/search/page.tsx:383` actually pairs by array index, at the one point where the index is still valid, then carries the pair through the sort. The observable guarantee AC-9 exists for does hold, and this test proves it, but the mechanism named in the spec is not the mechanism in the code. `scoreListings()` returning one outcome per listing in order is what makes index pairing safe, and a `sourceJobId` pairing would not depend on that. Worth a `/architect` pass to settle which the spec should say.

## Known gaps this list cannot close

- **~~AC-16's focus clause is not proved by any test in this repo, and may not hold.~~ The prediction was right, and it was fixed.** `/check verify` drove the running app on 2026-09-06 and found the reveal dropping focus to `<body>`, exactly as this gap said it might. The spec level decision it called for was taken the same day (spec 0015's second Decision, AC-17): a small client module records the focused control by a stable key and gives focus back to it after the reveal. **The gap that remains is narrower and still real**: no test in this repo proves a reader ends up back on their control, only that the pieces are wired the way AC-17 says. The focus block above is the whole proof, and it is manual.
- **`document.activeElement === body` is a proxy for "the reveal orphaned this reader", not a measurement of it.** A reader who clicks blank page space moments before the reveal reads identically to one the reveal orphaned. Spec 0015's Consequences accepts this as narrow rather than engineering around it, so it is a known behaviour rather than a step that can fail. The "touch nothing at all" step above is the closest thing to a bound on it: with no control ever focused there is no key, so nothing moves.
- **`SCORING_COPY.profileReadFailed` is not in spec 0015's copy table.** It was added during the build for the state the spec left with no sentence, the same way `COPY-6` of spec 0013 and `COPY-8` of spec 0014 were. It needs ratifying into the spec's copy table.
- **~~Spec 0015's first Follow-up item is a release blocker.~~ Closed 2026-09-06**, before this feature reached a pull request, by `fix(ai): opt ai_scoring out of OpenAI's 30 day retention with store: false` (pull request 104). Training was already safe with no action, so the privacy notice's "not used to train models" claim stands unchanged; retention needed `store: false` on the `ai_scoring` tier and now has it. See spec 0015's Follow-up for the full record. Nothing here blocks a release any more, but the two steps below are what actually prove it against a running app.

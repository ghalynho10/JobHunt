# 0023. Chip input for skills, titles and locations

**Date**: 2026-09-23
**Status**: In Progress

## Summary

This spec replaces the one line per value textarea used for skills, desired job titles and desired locations with a chip control: type a value, press Enter, it becomes a removable chip. It changes only how these three fields are typed in; the database columns, the parsing rules, and the two Server Actions that save them stay the same. This spec has been through three rounds of independent cross checking. The first pinned down the exact interaction mechanics the initial draft left open (the no JavaScript handoff, refusal and announcement wording, the two step Backspace, the submit blocking mechanism). The second caught mistakes the first round of fixes introduced (a factually wrong edit to spec 0010, a hardcoded limit, a missing plan for the server's own field error, and a client bundle leak). A third, deliberately narrow pass then checked only those corrections and found one test technique that needed replacing (a component holding hooks cannot be called as a plain function the way a hookless one can) and several cross references to spec 0010 that the second round's fix to spec 0010 itself had left behind in this file. All are corrected here.

## Context

See [rationale.md](rationale.md) for the full problem space, the options weighed, and why each was decided the way it was, including both cross checks this spec responds to.

## Requirements

**User stories**:
- As a signed in user editing my profile, I want to add a skill, title or location by typing it and pressing Enter, so that entering several values feels like building a list rather than writing lines of text.
- As a signed in user, I want to remove a value I no longer want with one clear action, so that correcting my profile does not mean retyping the whole field.
- As a signed in user who saved skills, titles or locations before this change, I want them to appear as chips with nothing lost, so that this change does not feel like it reset my profile.

**Acceptance criteria** (the contract, each criterion is independently checkable):
- **AC-1**: All three fields (skills, desired_titles, desired_locations) are entered by typing a value and pressing Enter, which commits it as a removable chip. Values already saved under the old textarea flow render as chips on load, with every value and its casing preserved. Order is preserved exactly for desired_titles and desired_locations (real `text[]` columns, insertion order). Skills render in the same `lower(name)` sorted order `readProfileSections()` already applies today (`src/features/profile/queries.ts`, sorted in the application because PostgREST cannot order by an expression); this feature does not change that ordering. This is not a new behaviour: a textarea reader already saw their typed lines re-sort on reload. It is called out here because a chip reads as a list you built in order, which makes the same, pre-existing reorder more visible than it was as plain text (see Consequences).
- **AC-2**: A committed value may contain any character, including a comma ("Chicago, IL" stays one chip). Commit happens only on Enter, on the auto commit paths in AC-8, or on the per line paste split in AC-7, never by splitting on a comma. Pressing Enter inside the entry box never triggers the surrounding form's own submission (`preventDefault()` always fires there, matching how the fallback `Textarea` never submitted on Enter either).
- **AC-3**: The FormData contract is unchanged from spec 0010. Each field still submits as a single newline joined string under its existing key (`skills`, `desired_titles`, `desired_locations`), read with `formData.get(name)` and parsed by the unchanged `newlineList()` in `src/features/profile/schemas.ts`. `ActionState`, `submittedValues()`, `fieldErrors()`, and the `saveSkills` and `savePreferences` Server Actions keep their current shapes. The value crosses once the chip control has mounted through a controlled `<input type="hidden" name={name}>` that `chip-field.tsx` itself renders and keeps at `committed.join("\n")`, never through the `Textarea` component (see AC-4).
- **AC-4**: Exactly one control ever carries the field's `name` at a time, never both. Before the chip control mounts, and with JavaScript disabled entirely, the field renders `src/components/ui/Textarea` exactly as it does today: visible, fully editable, one value per line, submitting and validating exactly as spec 0010's `newlineList()` behaviour describes (the entry mechanism spec 0010 AC-5 and AC-9 described is superseded by this spec; the parsing rules those two criteria and AC-6 state are not, and remain what this fallback path runs against, see the correction recorded on spec 0010 itself). Once mounted (a `useState(false)` flag flipped to `true` in a `useEffect` with an empty dependency array, so the first client render matches the server render and no hydration mismatch occurs), the `Textarea` is not rendered at all; the chip UI and the hidden input from AC-3 take its place. `src/components/ui/Textarea` cannot take a `ref` (it destructures a fixed prop list and is not wrapped in `forwardRef`), and it must not be given one for this feature alone, so the seeding reads the DOM by id instead: inside that same mount effect, before calling `setMounted(true)`, `document.getElementById(id)` finds the still rendered `Textarea` (the same `id` this component also puts on the mounted branch's entry input, so exactly one element answers to it at any moment), and its `.value` is split on `/\r?\n/`, trimmed, with empty lines dropped, to seed the committed chips. This runs strictly before the swap, so it reads the `Textarea` that is about to disappear, not the entry input that is about to appear. Seeding from the live DOM value rather than only the page's initial server rendered values is what keeps a value typed during a slow connection's brief pre hydration window from being silently lost. The mounted branch also renders the server's own field error exactly as `Textarea` did: `FieldError` (from `src/components/ui/field.tsx`), keyed by `fieldErrorId(id)`, with the entry box carrying `aria-invalid` and `aria-describedby` pointing at it. This is a separate element from the AC-9 refusal paragraph; the two can be visible at once (a server error left over from the last submit, and a fresh client side refusal from the current attempt), and neither replaces the other, since they answer different questions.
- **AC-5**: A value that case insensitively duplicates an already committed chip is refused at commit: no second chip is created, and the entry box's own inline message (see AC-9's live region rule) names the existing chip it matches (spec 0023's `COPY-1`, `alreadyAdded`). The existing chip's casing is never rewritten; first occurrence wins, matching `newlineList()`'s rule and spec 0010 AC-5.
- **AC-6**: A value is trimmed first, then checked. A trimmed value longer than the shared 100 character limit, or, for `desired_titles` and `desired_locations` only, a value that would exceed the 50 value cap, is refused at commit the same way, with the same inline message (spec 0023's `COPY-2` `tooLongValue`, `COPY-3` `tooManyValues`, both taking the limit itself as a parameter, not a hardcoded number, so the message can never quote a different number than the one actually enforced). Both numbers are read from named constants exported once from a new, import free module, `src/features/profile/limits.ts` (see Rationale for why they do not live in `schemas.ts` or `copy.ts`), and the message text itself is one shared function in `copy.ts` that both the client check and `schemas.ts`'s own Zod messages call, so the client and the server cannot show different words, or a different number, for the same rule. `skills` carries no count cap, unchanged.
- **AC-7**: Pasting text into the entry box splits on newline characters only, never on commas, into one candidate value per line; each candidate is trimmed and runs through the same commit checks as AC-5 and AC-6. No committed chip may ever contain a literal `\n` or `\r` character, checked and stripped or refused at the commit step regardless of source (typed Enter, paste, or the auto commit in AC-8), and covered by a test asserting against both characters, not `\n` alone. When a paste produces more than one refusal (for example, several lines over the count cap), the field shows and announces one aggregated message naming how many were not added (spec 0023's `COPY-4`, `pasteRefusedSome`), not one message per refused line.
- **AC-8**: Text left in the entry box when it loses focus, or when the form is submitted, auto commits through the same checks as AC-5 and AC-6. "Loses focus" means focus leaves the field entirely, not merely the entry box: a focus move to a control inside the same field, such as a chip's own remove control, does not auto commit, only a focus move outside the field does. This auto commit first clears (never removes through this path) any chip currently marked pending removal under AC-10. Removing a chip, by either its own remove control or the Backspace shortcut, clears any inline message currently shown for that field's entry box (see also AC-9, AC-10), since the message may have been about a value the removal just changed the meaning of. If the auto commit is refused, the Server Action must not run: a capture phase `submit` listener attached to the hidden input's own `<form>` calls `preventDefault()` and `stopPropagation()` there before React's own submit handling runs (verified against this project's installed React DOM: the form action plugin that dispatches a `useActionState` action runs from a bubble phase listener on the root container, never on the form element itself, so a capture phase listener on the form runs strictly earlier and stopping propagation there keeps the event from ever reaching that root listener), the inline message shows, and the text stays in the box, uncommitted and unsubmitted. On every submit, whether or not the entry box held anything to commit, that same synchronous handler writes `committed.join("\n")` onto the hidden input's `.value` before letting the submission proceed; `FormData` is built from the live DOM at dispatch time, after this handler runs, which is what makes the imperative write, and not a `setState` alone, land in what actually submits. `chip-field.tsx` keeps its own state unchanged across a failed server submission (no remount, no effect that copies `state.values` back over live state); `state.values[name]` is read only once, to seed the very first render, exactly like the unmounted `Textarea` path's existing `defaultValue={state.values.skills ?? skills}` pattern, and the submit handler clears any stale inline message before evaluating a new attempt.
- **AC-9**: Each committed chip has a visible, focusable remove control at least 24 by 24 CSS pixels (WCAG 2.2 SC 2.5.8, satisfied directly, not through the spacing exception, as its own fixed size box, never the full width `controlSurface` box `Input` and `Textarea` use), fully contained within its own chip so it cannot overlap an adjacent chip's control, with the accessible name "Remove {value}" (spec 0023's `COPY-8`, `removeChipLabel`), never the page's generic "Remove" control label. `Chip` accepts the remove control as a `ReactNode` `action` prop and a `pendingRemoval` boolean, both only assignable when `state="editable"`: the non `editable` branches of the union declare `action?: never; pendingRemoval?: never`, the exact shape `Button`'s own `ButtonAsLink` branch already uses for `disabled` and `type` (`button.tsx`), not a bare union that excess property checking alone would police. `pendingRemoval` may not be `true` without `action` also being set, so a pending removal state can never exist on a chip with no remove control to eventually activate it. `chip.test.ts` pins the union at compile time with a `@ts-expect-error` case naming `action` directly on a non `editable` chip, called without a prop spread (a spread defeats excess property checking, which is why `button.test.ts` hoists its `LINK` props to a named object first), and the 24 by 24 measurement itself is a `/check verify` browser step, matching how every other component's computed size is verified in this design system (`src/components/ui/AGENTS.md`'s Testing section). After a chip is removed, whether by its own control or by the Backspace shortcut, focus moves to the entry box. Removing a chip is announced (spec 0023's `COPY-5`, `chipRemoved`) through a dedicated, always rendered, visually hidden `aria-live="polite"` region used only for events with no visible text of their own; the visible refusal message from AC-5 through AC-7 is its own `aria-live="polite" aria-atomic="true"` paragraph, never `role="alert"` (a refusal here is not an interruption) and never duplicated into the hidden region, so no event is ever announced twice. Each announcement is keyed on a counter in state, so two identical, consecutive announcements both fire rather than the second being silently deduplicated.
- **AC-10**: Backspace on an empty entry box marks the last chip pending removal (a visible, shape based change, not colour alone, expressed as a boolean `pendingRemoval` prop accepted only alongside `state="editable"`, and announced through AC-9's hidden region via `COPY-6` `chipPendingRemoval`); a second consecutive Backspace removes it and announces the removal (`COPY-5`). The pending mark clears, and its clearing is announced (`COPY-7` `chipPendingRemovalCleared`), on any of: a keydown in the entry box that is neither Backspace nor a lone modifier key, any input typed into the entry box, the entry box losing focus (which is also what AC-8's blur commit already hooks, so leaving the field this way is one clear, not two competing behaviours), or the form being submitted. Clicking a chip's own remove control removes that chip and clears any pending mark in one action, regardless of which chip was pending. This shortcut is in addition to, never a replacement for, the remove control in AC-9.
- **AC-11**: Chips are not editable in place. Correcting a value means removing its chip and typing it again.
- **AC-12**: For `desired_titles` and `desired_locations`, the first chip is load bearing: `job_preference.desired_titles[0]` / `desired_locations[0]` prefill `/search` (spec 0013). The field's own inline label states this plainly, in the same slot today's "one per line" hint occupies in `preferences-form.tsx`, replaced with exactly this text: for `desired_titles`, `Job titles you want` with the hint `the first one prefills your search`; for `desired_locations`, `Locations you want` with the same hint. This stays inline copy, written where every other field label already lives, not moved into `copy.ts` (see Rationale for why). Because it is inline rather than a `copy.ts` entry, it sits outside `copy.test.ts`'s `EVERY_SLOT` guard, which enforces spec 0007's no em dash, no en dash, no semicolon rule only over that file. That gap is accepted rather than fixed by moving the label: the text is fully pinned here, character for character, the same way spec 0010 already left the calendar month names outside a `Copy` slot on the same reasoning (AC-7 there), and this spec's own review is what holds the line for it instead of an automated check. No reorder control is added; removing and re-adding the first value is what changes the prefill, and that is disclosed rather than hidden.
- **AC-13**: `chip-field.tsx` takes `disabled` as a prop from its parent form's own `pending` state (from `useActionState`), the same way `Input`, `Textarea` and `Select` already do; it holds no `useActionState` of its own. While `disabled`, the entry box and every remove control are individually disabled, matching the existing Save button's disabled state. The hidden transport input from AC-3 is never given the `disabled` attribute at any time, since a disabled form control submits nothing at all.
- **AC-14**: The interactive chip control (typing, commit, remove, the two step Backspace) is a client component, `src/features/profile/chip-field.tsx`, never a file in `src/components/ui/`, per that directory's rule that a base component never holds state, takes an event handler, or crosses the client boundary. Its top comment cites `src/components/ui/AGENTS.md` line 7 as the reason. Its own outer field box (the entry box's border and sizing) reuses the shared `controlSurface` from `src/components/ui/field.tsx`, called as `controlSurface({ invalid: error !== undefined })`, the same box `Input` and `Textarea` already use; this is the first feature level file to import a `tv` recipe out of `src/components/ui/` rather than a component, which is deliberate (a shared token rather than a hand composed box) and is called out so a later reader does not read it as an accident. `controlSurface`'s own `disabled:cursor-not-allowed disabled:opacity-55` classes key off the native `:disabled` pseudo class, which never matches a wrapping `<div>`, so `chip-field.tsx` applies the disabled appearance to that box explicitly under AC-13 rather than assuming `controlSurface` supplies it for free. `chip.tsx`'s new `action` slot and `pendingRemoval` prop are the only new surface `chip-field.tsx` adds to `src/components/ui/`.
- **AC-15**: `schemas.ts` changes only to import the two limit constants from the new `src/features/profile/limits.ts` and the two message functions from `copy.ts`, and to point its three existing `newlineList()` call sites (skills, desired_titles, desired_locations, together carrying five literal message strings: three `tooLong` and two `tooMany`) at them. `newlineList()`'s parsing behaviour and accepted arguments are unchanged, and no `schemas.test.ts` assertion changes; the two sentences it already asserts on (`"Keep each skill to 100 characters or fewer."`, `"Add at most 50 titles."`) coming back byte for byte from the new functions is what proves the extraction lost nothing.
- **AC-16**: No new test dependency is introduced. Every acceptance criterion above that is interaction or state logic (AC-1 through AC-3, AC-5 through AC-8, AC-10, AC-11, AC-13, AC-15, the compile time and announcement halves of AC-9, and AC-12's chip mechanics) has automated coverage in `src/features/profile/chip-field.dom.test.tsx`, using the same hand rolled `react-dom/client` plus `act` harness already precedented by `src/features/search/focus-keeper.dom.test.tsx` (a `// @vitest-environment jsdom` docblock, not a project wide switch; `package.json` is unchanged). The unmounted branch (part of AC-4) is proven with `renderToStaticMarkup` from `react-dom/server` (already installed, no new dependency, and `useEffect` never runs during a server render, so this genuinely produces the unmounted branch rather than approximating it), asserting the rendered markup carries `<textarea name="...">` and no hidden input; `chip-field.tsx` holds hooks (`useState`, `useEffect`, `useRef`), so, unlike the hookless `Chip`, it cannot be called directly as a plain function outside a render, which is why this needs a real render rather than `chip.test.ts`'s technique. What stays manual, in `/check verify`, and why: a real computed pixel measurement (AC-9's 24 by 24 target, since jsdom does not run a layout engine); whether a real screen reader actually announces something; and AC-4's pre hydration DOM seeding scenario, which needs `hydrateRoot` against server rendered markup with a value already typed into it to reproduce honestly, not `createRoot`, which would seed from a value trivially equal to the prop it is meant to override and could not tell a correct implementation from one that silently ignored the DOM and used the prop instead. `chip-field.dom.test.tsx`'s docblock states this limitation, the same way `focus-keeper.dom.test.tsx` already documents a scenario it cannot reproduce.

## Decision

**Chosen option**: visual grammar in `src/components/ui/chip.tsx`, all interactivity in a new client component, `src/features/profile/chip-field.tsx`; committed chips transport to the Server Action through a controlled hidden input that replaces the `Textarea` once mounted, reusing the unchanged `newlineList()` parser; the two limit numbers live in a new, import free `src/features/profile/limits.ts`; no new test dependency, automated coverage through the existing jsdom precedent.

`chip-field.tsx` owns the committed values array, the mounted flag, every event handler, the duplicate and limit checks (against constants from `limits.ts` and message functions from `copy.ts`, both also used by `schemas.ts`), the paste splitter, the two step Backspace removal, and the two `aria-live` regions (the visible refusal paragraph and the hidden announcement region). `chip.tsx` gains a handler free `action` slot and a `pendingRemoval` prop, both accepted only when `state="editable"` (a discriminated union with `action?: never; pendingRemoval?: never` on every other branch, so a call site cannot pass an `action` to a `matched` or `missing` chip and accidentally render a check mark beside a remove button), with no props that are functions.

## Copy

**Written by the engineer, used verbatim**, following the same rule spec 0010 and spec 0007 already state for their own `## Copy` tables: `/develop` must not invent or reword any of these, and spec 0007's punctuation rule applies (no em dashes, no en dashes, no semicolons). These land in the existing `src/features/profile/copy.ts`, which already holds spec 0010's `COPY-1` through `COPY-6`; because that file is shared across specs, each entry below is labelled "(spec 0023)" in its own doc comment to avoid colliding with spec 0010's own `COPY-1` through `COPY-6` in the same file, rather than continuing spec 0010's numbering (spec 0023 restarts at its own `COPY-1`, the same way spec 0010 restarted independently of spec 0007's). `copy.test.ts`'s `EVERY_SLOT` array, which enforces the no em dash, no en dash, no semicolon rule, gains one entry per slot below, called with representative arguments.

The two numeric limits these functions quote are not copy: they live in `src/features/profile/limits.ts` (see Feature design), passed in as `max`, never hardcoded in a string here.

| ID | Context | Text |
|---|---|---|
| `COPY-1`, `alreadyAdded(existingValue)` | A commit refused as a case insensitive duplicate (AC-5) | `"${existingValue}" is already added.` |
| `COPY-2`, `tooLongValue(noun, max)` | A commit refused for length, `noun` is `skill`, `title` or `location` (AC-6); also replaces `schemas.ts`'s three existing inline `tooLong` messages | `Keep each ${noun} to ${max} characters or fewer.` |
| `COPY-3`, `tooManyValues(noun, max)` | A commit refused on `desired_titles` or `desired_locations` for the count cap, `noun` is `title` or `location` (AC-6); also replaces `schemas.ts`'s two existing inline `tooMany` messages | `Add at most ${max} ${noun}s.` |
| `COPY-4`, `pasteRefusedSome(count, noun)` | A paste where one or more lines were refused, aggregated into one message (AC-7) | `${count} ${count === 1 ? noun : noun + 's'} could not be added.` |
| `COPY-5`, `chipRemoved(value)` | A chip removed, by the remove control or the Backspace shortcut, announced only (AC-9, AC-10) | `Removed ${value}.` |
| `COPY-6`, `chipPendingRemoval(value)` | A chip marked pending removal by the first Backspace, announced only (AC-10) | `${value} marked for removal. Press Backspace again to remove it.` |
| `COPY-7`, `chipPendingRemovalCleared(value)` | The pending mark cleared without removing the chip, announced only (AC-10) | `${value} is no longer marked for removal.` |
| `COPY-8`, `removeChipLabel(value)` | The accessible name of a chip's remove control (AC-9) | `Remove ${value}` |

**One constraint this copy creates.** `COPY-2` and `COPY-3` are read by both `chip-field.tsx` and `schemas.ts`, so `schemas.ts` imports these functions from `copy.ts` rather than keeping its own literal strings (AC-15), and imports the `max` values they are called with from `limits.ts`. This is the mechanism that makes AC-6's "the client and the server cannot disagree" true of the words and the numbers shown, not only the numbers alone.

## Feature design

**Data model sketch**:
No change. `public.profile_skill.name`, `public.job_preference.desired_titles` and `public.job_preference.desired_locations` are already `text[] not null default '{}'` (`supabase/migrations/20260825162457_data_model.sql`, lines 139 to 140). This spec adds no migration.

**State transitions**: none persisted. `chip-field.tsx` holds three pieces of transient client state per field: the committed values array, the mounted flag, and which chip index (if any) is pending removal, none of them stored.

**New module**: `src/features/profile/limits.ts`. Exports `LIST_VALUE_MAX_LENGTH = 100` and `PREFERENCE_LIST_MAX_COUNT = 50`. **This file must stay import free.** The two limit constants started this spec as a `schemas.ts` export; a cross check found that every current importer of `schemas.ts` is server only (`queries.ts` even carries an explicit `import "server-only"`), while this feature needs the same numbers in a client component (`chip-field.tsx`) and a `"use client"` form (`preferences-form.tsx`). Importing `schemas.ts` from either would pull `zod` and `./calendar` into the client bundle for two integers, silently, since `schemas.ts` carries no `server-only` guard of its own. Putting the numbers in `copy.ts` instead was considered and rejected: that file's own header binds it to spec 0010's Copy table rule, engineer written and used verbatim, and a number is not copy; folding it in either weakens that rule or subjects a plain limit to a review process built for prose. A separate, import free module is what lets both `schemas.ts` (server) and `chip-field.tsx` / `preferences-form.tsx` (client) import the same two numbers with nothing else attached, and staying import free is the property that must hold for that to keep being true.

**API surface**:
Unchanged from spec 0010.

| Surface | Kind | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `saveSkills` | Server Action | `skills` (newline joined string, built by `chip-field.tsx`'s hidden input instead of typed directly into a textarea) | redirect; field errors | signed in, caller owns the profile | `validation_failed`, `session_missing`, `record_not_found`, `database_unavailable` |
| `savePreferences` | Server Action | `desired_titles`, `desired_locations` (same newline joined shape), plus the unchanged preference fields | redirect; field errors | signed in, caller owns the profile | `validation_failed`, `session_missing`, `record_not_found`, `database_unavailable` |

**Value sourcing**:

| Action | Value produced or displayed | Source |
|---|---|---|
| render the skills field, editing, unmounted | the `Textarea`'s value | `state.values.skills ?? skills.map(skill => skill.name).join("\n")`, the existing pattern in `skills-form.tsx`, unchanged |
| render the skills field, editing, mounted | the initial committed chips | seeded once, at the mount swap, from the live `Textarea` DOM value (AC-4), which itself came from the row above |
| render the preferences fields, editing, mounted | the initial committed chips for each list | the same seeding as above, from each field's own unmounted `Textarea` value, itself `state.values[name] ?? (preferences?.desired_titles ?? []).join("\n")` / the locations equivalent, both already returned by `queries.ts` as `z.array(z.string())` |
| refuse a duplicate commit | the existing chip's value named in the message | `COPY-1`, fed the current committed values array held in `chip-field.tsx`'s own state, matched case insensitively |
| refuse an over limit commit | the limits and the noun shown in the message | `LIST_VALUE_MAX_LENGTH`, `PREFERENCE_LIST_MAX_COUNT` (from the new `limits.ts`) and the `noun` prop `chip-field.tsx` is given per field, fed into `COPY-2` / `COPY-3` |
| state the first chip's significance (AC-12) | the label text on `desired_titles` and `desired_locations` | static inline copy in `preferences-form.tsx`, written once, not derived from data (see Rationale for why this stays inline rather than in `copy.ts`) |
| announce an event with no visible text (AC-9, AC-10) | the announcement string | `COPY-5` through `COPY-7`, fed the affected chip's value from the same committed values state |
| render the mounted field's server error (AC-4) | the error sentence and its wiring | `state.errors[name]`, rendered through `FieldError` and `fieldErrorId(id)`, exactly as `Textarea` renders it today |

**Key invariants**:
- A chip is never created from an empty or whitespace only commit (matches `newlineList()`'s existing empty line drop).
- No committed chip value ever contains a literal `\n` or `\r` character, regardless of whether it arrived by Enter, paste, or auto commit (AC-7).
- First occurrence wins on casing, enforced identically client side (the duplicate check in AC-5) and server side (`newlineList()`, unchanged).
- `skills` carries no count cap; `desired_titles` and `desired_locations` each cap at 50 values; all three cap each value at 100 characters, all read from `limits.ts` and expressed in the same shared message text on both sides of the boundary (AC-6, AC-15).
- Exactly one control carries a given field's `name` at any moment: the `Textarea` before mount, the hidden input after (AC-3, AC-4).
- `Chip`'s `action` and `pendingRemoval` props are only assignable when `state="editable"`, enforced by TypeScript's discriminated union, not by convention.

**Security model**:
Unchanged from spec 0010. Each Server Action independently verifies its caller with `getClaims()`; row level security remains the real guarantee; this feature adds no new authorization path, since it changes only how the same two already authorized actions are typed into.

**Configuration required**:
None. No new environment variables, and, per AC-16, no new test dependency either.

**Critical test scenarios** (each maps to an acceptance criterion above; the automated ones live in `chip-field.dom.test.tsx` per AC-16, the browser only ones in [verify.md](verify.md)):
- Happy path (automated): type three skills, pressing Enter after each → three chips exist holding those three values, verifies **AC-1**.
- Duplicate refusal (automated): with `React` already committed, type `react` and press Enter → no second chip, the visible message reads `"React" is already added.`, the existing chip still reads `React`, verifies **AC-5**.
- Limit refusal (automated): attempt to commit a 101 character value, and, on `desired_titles`, a 51st value → both refused immediately with the matching `COPY-2` / `COPY-3` message, quoting the actual configured limit, neither reaches the hidden input, verifies **AC-6**.
- Paste splitting (automated): paste a three line clipboard value where one line is a duplicate → two chips are created, one aggregated refusal message names one value not added, verifies **AC-7**.
- Auto commit failure blocks save (automated): type a duplicate value, do not press Enter, submit the form → the capture phase listener prevents the submit, the message shows, the text remains in the box, verifies **AC-8**.
- Backspace two step (automated): with the entry box empty, press Backspace once → the last chip is marked pending and announced; type a character → the mark clears and is announced; press Backspace twice in a row from empty → the chip is removed and announced once, verifies **AC-10**.
- Unmounted rendering (automated, via `renderToStaticMarkup` from `react-dom/server`, since `chip-field.tsx` holds hooks and cannot be called as a plain function the way the hookless `Chip` can): the rendered markup is the `Textarea`, one value per line, and no hidden input exists, verifies **AC-4**.
- Pre hydration typing (manual, `/check verify`, and documented in `chip-field.dom.test.tsx`'s docblock as a known automation limit per AC-16): on a slow connection, type into the visible `Textarea` before the chip control mounts → the typed value survives as a chip once it mounts, verifies **AC-4**.
- Order significance (manual, `/check verify`): with two desired locations saved, remove and re-add the first one with a corrected value, then load `/search` with no query params → the prefilled location is the corrected value, and the field's label already said this would happen, verifies **AC-12**.
- Accessibility (manual, `/check verify`): measure the remove control at 24 by 24 CSS pixels or larger in the browser, and confirm a real screen reader announces both a refusal message and a chip removal, verifies **AC-9**.

## Consequences

**Positive**:
- One consistent, accessible way to enter all three list fields, with immediate feedback on a duplicate or an over limit value instead of only finding out at Save, and a validation error that is never buried by the mount swap (AC-4 renders exactly one control at a time and its own `FieldError`, on both the mounted and unmounted paths).
- `schemas.ts`, `form-state.ts`, and both Server Actions are untouched beyond importing two constants and two message functions, so the risk of this change is contained to the profile feature's UI layer, and the client and server can no longer show different words, or a different number, for the same limit.
- `chip.tsx` gains a small, reusable extension (the `editable` state, the `action` slot, the `pendingRemoval` prop) that a future editable list control elsewhere in the product can reuse without inventing its own chip styling.
- No new test dependency, no new e2e runner. The existing jsdom precedent (`focus-keeper.dom.test.tsx`) turns out to cover essentially all of this feature's behaviour; only what this design system has never automated for any component (a real pixel measurement, a real screen reader, and one genuinely hydration dependent scenario) stay manual.

**Negative / tradeoffs**:
- `chip-field.tsx` is a genuinely nontrivial piece of new client side code (a mounted flag, a capture phase submit listener, a two step Backspace state machine, two `aria-live` regions) and is materially harder to get right than the plain `Textarea` it replaces. Steps 5 through 8 exist specifically because this complexity needs test first coverage, not a single test pass at the end.
- A skill chip added last today still moves after save and reload, because skills render in `lower(name)` sorted order, not insertion order (unchanged from the current textarea behaviour, see AC-1). This was already true, but a chip reads as an ordered list you built, which makes the same reorder more noticeable than it was as plain text lines.
- Correcting the first `desired_titles` or `desired_locations` value takes a remove and a retype, which is more interaction than editing line one of a textarea used to be. This is accepted in exchange for not hiding that the change also moves what prefills `/search` (AC-12).
- `limits.ts`'s two numbers and `copy.ts`'s two message functions are now depended on from both `schemas.ts` and `chip-field.tsx` / `preferences-form.tsx`, one more import path to check if either ever changes, though centralising them removes the drift risk this would otherwise carry rather than adding one. `limits.ts` must stay import free for that boundary to hold; a later change that gives it an import is the signal to re-examine which side of the server or client line it has drifted onto.

**Neutral**:
- Spec 0010's AC-5 and AC-9 are marked superseded in place for the JavaScript entry mechanism only (their entry mechanism clause struck through, not deleted), following the precedent already set at spec 0006 AC-7, so a reader of 0010 sees the entry mechanism changed without first discovering this spec. AC-6 carries a plain, unstruck note instead, because it states only the parser's own behaviour (trimming, dropping empties, deduplicating, the character limit), which this spec leaves entirely untouched; nothing in it stopped being true, so nothing in it is struck. All three criteria's parsing rules stay normative, including for the no JavaScript fallback path AC-4 of this spec still depends on.
- No database migration. Single deployment, fully revertible by reverting the introducing commit; no `## Migration plan` section is needed under this project's own threshold for one (spec 0010's tables, parsing rules, and Server Actions are unchanged, and no data transformation, code freeze, or coordination window is required).

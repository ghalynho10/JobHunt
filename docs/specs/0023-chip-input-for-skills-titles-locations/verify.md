## Finding (2026-09-23, /check verify)

**A real click on Save can silently miss the button and lose unsaved chips, when a refusal message is showing and gets cleared right as Save is clicked.**

Reproduced three times against a running dev server and a real signed in session: type a genuinely new skill (e.g. "Kubernetes"), commit it with Enter, then trigger an unrelated duplicate refusal (type "kubernetes", Enter), clear the entry box with real Backspace key presses (not a scripted value assignment), then click the Save button with a real pointer click (Playwright's own `locator.click()`, not a coordinate hack). The new skill is not saved; a fresh page load shows only the skills that were already stored before this attempt. The dev server's own log confirms no `saveSkills` Server Action ever ran for that click (`grep saveSkills` on the terminal log shows only the one call from an earlier, unrelated save).

Root cause, confirmed by direct evidence, not by reading the code:
- `chip-field.tsx`'s own submit guard logic is correct. A temporary `console.log` inside `handleSubmit` shows it runs, reads an empty `raw`, computes `result: undefined`, and does not call `preventDefault()`, whenever Save is clicked programmatically (`element.click()` via `page.evaluate`), even with a refusal freshly cleared. The same programmatic click also correctly blocks the submit and keeps the text in the box when the box is left non-empty (item 19), proving `evaluateCandidate` and `handleSubmit` both behave exactly as specced.
- The failure is specific to a real, coordinate based pointer click (`locator.click()`). The `console.log` never fires at all in the failing case, meaning the "submit" event never reaches the form, meaning the click itself did not land on the Save button.
- The mechanism: clicking Save first blurs the entry input. `onEntryBlur` calls `commitFromEntry()`, which (correctly, since the box is empty) calls `setRefusal(undefined)`. That removes the refusal `<p>` from the DOM, which sits above the Save button in `skills-form.tsx`'s `flex flex-col gap-5` layout, shifting the button upward. If this reflow lands between the pointer's mousedown and mouseup (or between Playwright's own visibility/stability check and its dispatch), the click can resolve against whatever is now at the old coordinates instead of the button, and nothing happens: no error, no redirect, no console output, and the chip the reader just typed is gone with no warning.

This reproduces on `skills-form.tsx`; `preferences-form.tsx` renders the same `ChipField` the same way and is architecturally exposed to the same layout shift, though it was not separately reproduced there in this run.

Not a logic bug in `evaluateCandidate` or `handleSubmit`, both proven correct above. It is a layout stability issue: the refusal paragraph's appearance/disappearance shifts content below it, including the Save button, at the exact moment a real click can be resolving. → `/debug`. A fix likely needs to keep the Save button's position stable regardless of whether the refusal paragraph is showing (reserved space, an overlay, or moving the message somewhere that cannot shift the button), rather than a change to the commit or refusal logic itself, which is already correct.

The fixture session used to reproduce this (local Supabase only; email `chip-verify-cb1c6ca9-7eb6-4e69-9f7c-fd298b77930a@example.test`, user id `0af13dbc-314d-4c42-9422-d63cf493957a`) was left in place rather than deleted, so `/debug` can reproduce against the same state without re-seeding: skills `Rust`, `TypeScript`, `Zephyr`; preferences `desired_locations: ["Austin, TX"]`, `desired_titles: []`. Mint a fresh session cookie for that same email with `test/helpers/session.ts`'s `mintSession()` (the earlier one has already expired); `DEV_SESSION_ENABLED=true` is already set in `.env.local`. The dev server this run started (`pnpm dev`, logging to `/tmp/jobhunt-dev-server.log`) and the local Supabase stack were left running.

### Resolved (2026-09-23, /debug)

Reproduced the exact sequence above against the same fixture session with a real Playwright pointer click, on the first attempt: the click focused the Save button but no `submit` event reached the form and no `saveSkills` call appeared in the dev server log, confirmed by a page reload showing "Kubernetes" never persisted.

Root cause confirmed against spec 0023 AC-8's own text: AC-8 requires only the SUBMIT handler to clear a stale refusal message ("that same synchronous handler ... clears any stale inline message before evaluating a new attempt"); nothing in AC-8, AC-9, or AC-10 requires blur to clear it. `commitFromEntry()`'s own `setRefusal(undefined)` on an empty box was incidental, not spec required, and it is what fired on every blur, including the one a Save click's own mousedown triggers.

Fix, in `chip-field.tsx`: `commitFromEntry()` no longer clears `refusal` when the box is empty (an empty commit is a no-op now, matching AC-8's letter); a new `onEntryChange` handler clears a shown refusal as soon as the reader types, which is what still makes a stale message go away for someone correcting their entry, decoupled from blur's timing entirely. In the corrected browser run, the refusal already cleared while backspacing, well before Save was touched, so no reflow competed with the click.

Verified: the same real click now completes the save on both `skills-form.tsx` and `preferences-form.tsx` (separately reproduced on the `desired_locations` field, closing the gap this Finding left open), `pnpm test` passes at 1411 of 1411, and two new jsdom cases in `chip-field.dom.test.tsx` pin the state-clearing mechanism itself (confirmed to fail against the pre-fix code first). The click-miss reflow still needs a real layout engine and has no automated coverage; re-run the two repro sequences above by hand if `chip-field.tsx`'s blur or refusal handling changes again.

## Finding (2026-09-23, /check verify rerun): pre hydration DOM seeding (item 13, AC-4)

**Reproduced twice: a value typed into the visible `Textarea` during a throttled load is not seeded into the chip control once it mounts; the chips that appear are the stored values, not the typed ones.**

Method: `page.route()` delayed every `_next/static/chunks/*` request by 2 seconds (no CPU throttling, which an earlier, discarded attempt used and which produced confounded results, an HMR reconnect and a Next.js dev "slow execution" instrumentation message that made that run's evidence untrustworthy). Loaded `?edit=skills`, confirmed the server rendered `Textarea` present with its stored value (`Rust\nTypeScript\nZephyr`), filled it with a new value, confirmed that write landed (`textarea.inputValue()` read back the typed text), then waited for the chip control to mount. Both attempts: the mounted chips read `Rust`, `TypeScript`, `Zephyr`, the ORIGINAL stored values, never the typed text. No hydration mismatch was logged in the browser console in either attempt.

A baseline check without any throttling could not even be attempted the same way: at normal dev server speed, hydration completes before a scripted `fill()` can reach the textarea at all (`locator.fill()` timed out waiting for a stable element, because the textarea had already been swapped for the chip input). That confirms the throttling is necessary to reach this scenario at all, exactly as spec 0023's own AC-16 docblock already says, and is also why this evidence is not being treated as fully conclusive on its own.

**Why this is reported as a real finding rather than a confirmed root cause.** `chip-field.tsx`'s mount effect reads `document.getElementById(id)` for a live `HTMLTextAreaElement` before flipping `mounted`, which should read back whatever a reader typed into the still rendered element, including under this project's own comment justifying why the effect exists at all. Two clean reproductions with no console error is a real signal that this path is not working as specced. It is reported as a finding, not fixed here, because `/check verify` does not fix, and because an artificial per chunk network delay is not proven to reproduce the same code path a genuinely slow connection does. Next.js dev mode's own HMR client and instrumentation add behavior a production build does not have, and this file's own AC-16 docblock already independently concluded that a live timing race is not a trustworthy way to test this scenario, prescribing `hydrateRoot` against server rendered markup with a value pre seeded into it instead. That is the reproduction this finding recommends `/debug` build, rather than continuing to lean on live browser throttling.

Not the same issue as the Finding above (which is fully resolved): that one was a layout shift moving the Save button during a click; this one is about whether a pre hydration keystroke survives at all, and touches AC-4, not AC-8. → `/debug`, with the `hydrateRoot` based reproduction this file's own docblock already names as the honest way to test it.

### Investigated (2026-09-24, /debug), root cause confirmed, AC-4 still unmet

Reproduced deterministically with the `hydrateRoot` based harness this file's own docblock prescribes: `renderToString` the field, type into the resulting `Textarea` via the native value setter (never `element.value = x` directly, which a later check in this same investigation found React itself intercepts, see below), then `hydrateRoot` over that markup. Fails on the first attempt, every time, no throttling, no dev server, no HMR: the hidden input reads the stored values, never the typed ones.

Three hypotheses were weighed. Ranked by fit, tested in order:

1. **React Strict Mode double invoking the mount effect, the second run landing after the swap.** Tested directly (`createRoot` plus `<StrictMode>`, an instrumented `console.log` counting invocations): the effect **does** double invoke, exactly twice, but both invocations land back to back before the swap's own state update has re-rendered anything, so both read the still present `Textarea`, both get the same answer, and committing a chip afterward survives fine. **Refuted** as the cause of item 13.
2. **React resets the textarea's DOM value to its `defaultValue` during hydration, before any effect runs.** Confirmed directly from the installed `react-dom` 19.2.8 source, not by reading `chip-field.tsx`: `initTextarea` (`react-dom/cjs/react-dom-client.development.js:1855`) runs during the hydration commit, strictly before any component effect, and unconditionally does `element.value = element.textContent` whenever `element.textContent === defaultValue`. A textarea's `textContent` is its original server rendered markup and is never touched by typing (browsers decouple `.value` from `.textContent` the moment a user edits the field), so this condition is true after any amount of typing, every time, and the reader's keystroke is always overwritten before `chip-field.tsx`'s mount effect can read it. A stack trace from an instrumented `.value` setter confirms the write happens inside `initTextarea`, called from `prepareToHydrateHostInstance`, part of React's synchronous hydration commit, before the effects phase. **Confirmed** as the root cause of item 13. No effect timing fix (not `useLayoutEffect`, not reading earlier) can help: the value is destroyed by React itself before any application code runs.
3. **The measurement was wrong** (the live browser test from the prior `/check verify` rerun typed into the wrong element). **Ruled out** for this reproduction: the harness explicitly confirms the typed text lands on the actual `Textarea` (read back via `.value` right after typing, and the mount effect's own `previous.tagName` reads `TEXTAREA`, not the entry `<input>`), independent of the earlier live browser evidence's own risk of this.

**Not fixed.** This is a flawed decision, not a coding mistake: no effect inside `chip-field.tsx` can ever observe a pre hydration keystroke on a `<textarea>`, because React's own hydration adoption destroys it unconditionally, synchronously, before any user code runs, for every React 19.2.8 app, regardless of how the effect is written. A real fix needs a mechanism outside this effect entirely (for example a raw, non React `input` listener attached before hydration, stashing the value somewhere React's hydration can't reach), which is a genuine architectural decision, not a patch. AC-4's pre hydration seeding requirement is therefore **still unmet** and is not being quietly resolved here. → `/architect`, to either design that mechanism or narrow AC-4 to state plainly that this one sub scenario is not preservable under React's hydration model, and record why.

**A separate, real latent bug was found and fixed while investigating hypothesis 1**, independent of item 13's own root cause. The mount effect's dependency array is `[id]`; nothing about that stops it running a second time, and a parent re-rendering the same mounted instance with a changed `id` genuinely does trigger a second run, on the same fiber, with `committed` state intact. Confirmed live: after committing a chip, changing `id` alone silently discarded it, falling back to `initialValues`, in a `createRoot` harness with no hydration and no Strict Mode involved. Fixed in `chip-field.tsx` with a `seededRef` guard so the seeding read runs at most once per mounted instance, regardless of cause. A new jsdom test in `chip-field.dom.test.tsx` ("does not re-seed and discard already committed chips if the mount effect runs again after the swap") pins this, confirmed to fail against the pre-fix code first. This does not touch item 13: confirmed unaffected by re-running the same `hydrateRoot` reproduction against the fixed code.

### Narrowed (2026-09-24, /architect)

AC-4 is narrowed to state plainly that the pre hydration case is not preservable for any field that already holds a value, citing the same `initTextarea` source above; item 13 is retired above, not failing. The `seededRef` guard and the DOM read it protects are now scheduled for removal (spec 0023's Build plan step 11), since seeding never needed the DOM: `initialValues` was always available as a prop. Two `<noscript>` based alternatives (deferring the hidden input's presence, or shipping it `disabled` until mount) were considered and rejected: both leave a real window, JavaScript enabled but not yet loaded, where no control carries the field's name at all, and `actions.ts` reads every one of these fields as `formData.get(name) ?? ""`, with `newlineList("")` returning `[]`, so that gap would silently wipe the field's stored values, not merely lose a fresh keystroke. Dropping the no JavaScript path outright was also rejected: every other field on these forms already gets working no JavaScript submission for free, and `form-state.ts`'s own top comment treats that path as live for this form family.

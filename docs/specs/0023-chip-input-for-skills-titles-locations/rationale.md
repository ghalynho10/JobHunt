# Rationale: chip input for skills, titles and locations · spec 0023

## Context

Skills, desired job titles and desired locations are today typed into one `Textarea` each, one value per line (spec 0010, AC-5, AC-6, AC-9). All three share one parser, `newlineList()` in `src/features/profile/schemas.ts`, which trims each line, drops empty lines, deduplicates case insensitively (first occurrence wins on casing), enforces a 100 character cap per value, and, for `desired_titles` and `desired_locations` only, a 50 value cap. The three database columns are already `text[] not null default '{}'` (`supabase/migrations/20260825162457_data_model.sql`), so this is a rendering change only, not a migration.

Scope row 34 asks for a chip control instead: type a value, press Enter, it becomes a removable chip. The one hard constraint the scope row states is that commit must happen on Enter only, never by splitting on commas, because a location such as "Chicago, IL" is a real single value.

Three forces shaped this decision, none of them visible from the scope row alone.

First, `src/components/ui/AGENTS.md` states plainly that a base component in that directory "never holds state, takes an event handler, or crosses the client boundary." Every component there today (`Button`, `Input`, `Textarea`, `Select`, `Chip`) is handler free, confirmed by reading each file. A chip input's commit on Enter and per chip removal genuinely need event handlers somewhere, which puts the initial framing (the chip control belongs in `src/components/ui/`) in direct tension with the directory's own rule.

Second, `src/features/profile/form-state.ts` deliberately types `ActionState.values` as `Record<string, string>`, reasoning in its own comment that "every field is a plain string because that is what `FormData` holds" and that this is what lets the state cross the server to client boundary "with no reviver." That type is shared by all six profile write paths (identity, skills, two work history actions, preferences, and the delete action), not just the three fields this feature touches.

Third, `job_preference.desired_titles[0]` and `desired_locations[0]` are not decorative. `src/features/search/preferences.ts` (the block returning `{ title: parsed.data.desired_titles[0], location: parsed.data.desired_locations[0] }`) feeds them straight into `/search`'s prefill, and spec 0013's own Value sourcing table names them as the source of the prefilled title and location. A chip UI that only supports remove and retype changes which value is first, and therefore what search prefills with, the moment a person corrects a typo in their first title or location. Today's textarea has no such effect, since line one can be edited without moving.

The `newlineList()` function itself is module private, with its only three call sites in `schemas.ts` and no importer outside `src/features/profile/`, which meant this design was free to change its call sites and the constants it uses without an external compatibility concern.

## Options considered

The load bearing decision is where the interactive parts of the chip control live, given the `src/components/ui/AGENTS.md` rule above.

### Option 1: Visual grammar in `src/components/ui/`, interactivity in `src/features/profile/`

`src/components/ui/chip.tsx` stays a plain, handler free component, extended with a data only `action` slot (a `ReactNode` the caller supplies) and a `pendingRemoval` style variant, both pure rendering. All state (the committed values array, the mounted flag, the pending Backspace removal, the auto commit logic) and all event handlers (`onKeyDown`, `onClick`, `onBlur`, `onPaste`) live in one new client component, `src/features/profile/chip-field.tsx`, which composes `Field`, `Chip` and the icons from `src/components/ui/` the same way `skills-form.tsx` and `preferences-form.tsx` already compose `Field` and `Textarea`.

**Pros**:
- Matches the existing precedent exactly: every interactive piece in this codebase already lives in `src/features/profile/` as a `"use client"` file, and nothing in `src/components/ui/` has ever taken a handler prop.
- The riskiest, accessibility critical wiring (keyboard commit, focus management, live region announcements) uses ordinary, direct `onClick`/`onKeyDown` handlers, the same pattern every other interactive control in this codebase already uses and that this team already knows how to get right.

**Cons**:
- The literal file most people would call "the chip control" lives in `src/features/profile/`, not `src/components/ui/`, which is a real, visible departure from how the feature was first framed. This has to be stated, not left implicit, or a later reader moves it back and reintroduces the handler problem.

### Option 2: Whole widget in `src/components/ui/`, via event delegation

A new `src/components/ui/chip-input.tsx` renders the full assembly (chip list, remove buttons, entry box, fallback textarea) as pure, handler free JSX: plain HTML buttons and `data-*` attributes carry no `onClick`. A thin client wrapper in `src/features/profile/` attaches one delegated `onClick`/`onKeyDown` to a wrapping element and reads `event.target` to work out what was activated or typed.

**Pros**:
- Every prop on the `src/components/ui/` file stays a plain value, technically satisfying "never takes an event handler" to the letter, and the named "chip control" does live in the design system directory as first framed.

**Cons**:
- Event delegation for keyboard commit, Backspace, blur driven auto commit and per chip removal has no precedent anywhere else in this codebase. Every other interactive surface here uses direct handlers. Introducing a new interaction pattern for the first time on a control that WCAG 2.2 AA and an aria live announcement both depend on is exactly where a subtle bug (a delegated handler that mishandles focus, or a blur event that does not bubble the way `onClick` does) would be hardest to catch in review.

## Rationale

Option 1 was chosen. The `src/components/ui/AGENTS.md` rule is not a style preference to route around; the file itself frames the split as: "A consuming feature adds its own `\"use client\"` boundary where it needs real interactivity; a base component never does." That sentence already names where the interactivity belongs. Event delegation (Option 2) would satisfy the rule's letter while putting a keyboard and screen reader critical control on a pattern this codebase has never used, which is the wrong place to spend a first attempt at something new. The instruction that framed this decision, that the chip control belongs in `src/components/ui/`, is therefore corrected rather than followed: the same `AGENTS.md` it cited is the reason the interactive assembly lives in `src/features/profile/chip-field.tsx` instead, with a doc comment at the top of that file citing `src/components/ui/AGENTS.md` line 7 so a later reader sees why before moving it.

A second, smaller decision follows the same reasoning: how committed chips reach the Server Action. Two shapes were weighed. Multiple hidden `<input>` elements sharing one `name`, read server side with `formData.getAll()`, is the structurally cleaner shape for genuinely repeated data, but it requires widening `ActionState.values` to `string | readonly string[]` across all six profile write paths, rewriting `submittedValues()` and `fieldErrors()` to handle arrays, and replacing `newlineList()` with an array based equivalent, none of which the other three write paths (identity, the two work history actions) need. A single hidden field carrying the values newline joined keeps `newlineList()`, `submittedValues()`, `fieldErrors()` and the two Server Actions' `formData.get(name)` calls completely unchanged. This is safe only because the commit step defends it directly, not because the shape makes it structurally impossible: Enter commits rather than inserting a newline, and pasted multi line text is split at the commit step (AC-7), but neither of those alone rules out a stray `\r` or an un-trimmed edge surviving into a stored value. The first draft of this spec asserted the stronger, unqualified claim and a cross check caught it; AC-7 now states the guard in terms (strip or refuse any `\n` or `\r`, trim first, at every commit path) rather than leaving it implied by how Enter happens to behave. The smaller, well contained diff was still chosen over the structurally purer `formData.getAll()` shape, since nothing in this feature's requirements needs the array shape and the existing shared infrastructure is both working and tested; it just needed its safety argument corrected rather than assumed.

A third, smaller decision follows from the same cross check: whether this feature should introduce a browser based test runner or a component testing library, given that its whole acceptance surface is keyboard and pointer interaction (commit, paste, the two step Backspace, blur driven auto commit, live region announcements) that the project's plain unit and integration suites cannot reach. Root `AGENTS.md` records that no end to end runner is installed and that Playwright is the recorded choice for whichever feature needs a browser first; that made this a real question rather than an oversight to route around silently. The answer is that this is not that feature. `src/components/ui/AGENTS.md`'s own Testing section already draws the line this design needs: DOM level interaction and state (what a click, a keydown, or a paste event does) is unit testable in jsdom, already proven inside this exact codebase by `src/features/search/focus-keeper.dom.test.tsx`'s hand rolled `react-dom/client` plus `act` harness; only genuinely computed, rendered properties (a real pixel measurement, a real screen reader announcement) are not, and this project has never automated those for any component, leaving them to `/check verify` instead. Nearly everything this spec's acceptance criteria ask for is the first kind. Introducing Playwright, or a component testing library such as `@testing-library/react`, for the small remainder (one pixel measurement AC-9 already sends to `/check verify`, and one screen reader pass no automated tool in this stack could honestly claim to verify anyway) would be new, ongoing infrastructure bought for two manual steps this project already knows how to run by hand. AC-16 records this explicitly as a decision, not a silent default, precisely so a later reader does not need to re-derive it from the absence of a `## Migration plan`-style callout.

The `desired_titles[0]` / `desired_locations[0]` prefill dependency was resolved by disclosure rather than by adding a reorder control. Building drag or up or down reordering for two fields, solely so a typo fix does not silently change which value prefills `/search`, is disproportionate to the actual requirement in scope row 34, which asks for a chip control, not a reordering one. Stating the first position's significance in the field's own label, in the same slot the "one per line" hint uses today, makes the effect visible at the point of action instead of hidden, without adding a second, more complex interaction mode.

A fourth decision, caught by the second cross check rather than the first: where the two limit numbers (100 characters, 50 values) live. The first revision of this spec put them in `schemas.ts`, exported alongside the parser that already used them. That is wrong for a reason the first cross check had no occasion to notice, since it was reviewing a draft that had not yet moved these numbers into a client component: every current importer of `schemas.ts` is server only (`queries.ts` even declares `import "server-only"`), so having `chip-field.tsx` and `preferences-form.tsx`, both `"use client"`, import from it would pull `zod` and `./calendar` into the browser bundle for two integers, with nothing to stop it, since `schemas.ts` carries no `server-only` guard of its own. Putting the numbers in `copy.ts` instead was considered next and also rejected: that file's own header binds every export in it to spec 0010's Copy table rule, engineer written and used verbatim, `/develop` may not invent or reword it, and a plain numeric limit is not copy in that sense; folding it in would either weaken that rule for everything else in the file or subject a number to a review process built for prose. `src/features/profile/limits.ts`, a new module with no imports of its own, is what lets both sides of the server and client boundary read the same two numbers with nothing else attached. Staying import free is not incidental to that; it is the property that makes the file safe to import from a client component in the first place, which is why the spec states it as a constraint on the file rather than a description of its current state.

**On the two cross checks.** The first pass (documented above, and reflected throughout `index.md`) found fifteen decision completeness gaps in the initial draft: no home for the new user facing strings, a "keep the `Textarea` in sync while hidden" design that both`Textarea`'s actual props and the need to still show the server's own validation error made unworkable, an unqualified safety claim about newlines, an unnamed mechanism for blocking a bad auto commit from submitting, and several others. All fifteen were fixed. A second pass, re reviewing the fix rather than trusting the diff (this project's own standing rule after a revision), verified the two hardest technical claims directly against this project's installed React DOM source (the capture phase submit listener claim in AC-8, and the "state seeded once" claim) and found both correct, but found ten new problems the rewrite itself introduced, four of them blocking: a wrongly worded edit to spec 0010 that claimed skills "no longer arrive as lines to parse" when the parser is explicitly unchanged (corrected on spec 0010 itself, narrowed to the entry mechanism only, with a clause preserving the parsing rules as normative on both the JavaScript and no JavaScript paths); a refusal message that hardcoded its limit instead of taking it as a parameter, which would have made the client and server disagree on the very number AC-6 says they cannot disagree on; the missing plan for the mounted field's own server error, now AC-4's explicit `FieldError` clause; and the `schemas.ts` placement of the two limit constants, resolved above. Per the engineer's own instruction after the second round, a third pass ran, but deliberately narrowed to checking only the second round's own ten fixes rather than the whole spec again, since the untouched parts had already been reviewed twice. It found nine more issues, all of them small enough to fix in place without reopening a design question: three stale cross references left in this spec by the correction made to spec 0010 (fixed here), a test technique that assumed `chip-field.tsx` could be called as a plain function the way the hookless `Chip` can, when it in fact holds hooks and needs a real render (`renderToStaticMarkup` for the unmounted branch, `Chip`'s own technique kept only for `Chip` itself), an unstated rule for whether a focus move within the field counts as the blur that auto commits, an unenforced `controlSurface` assumption (its `disabled:` classes never match a wrapping `div`), an unconstrained `pendingRemoval` that could be set without `action`, and a couple of small gaps in `verify.md`. None of the nine required reopening Options considered or the Decision above; every fix landed as a targeted edit to the affected criterion. That is the stop condition this project's standing rule and the engineer's own instruction both point at: a fourth round does not run regardless of what a future reader might still find, and anything beyond a small, surgical fix from here is a matter for a human read, not another turn of the same wheel.

# Verify: usage gating and kill switch · spec 0011

_Steps derived from spec 0011's acceptance criteria. `/check verify` runs these; `/test` locks the durable ones._

All steps below start unticked and are ticked only with the evidence recorded
beside the step; an unticked step means that evidence has not been recorded
yet. Run against a real local database connection unless a step says
otherwise; none of this can be proved against a mock.

## Schema and grants

- [x] `usage_cap` and `usage_gate_counter` both show `relrowsecurity` and `relforcerowsecurity` true, and neither `anon` nor `authenticated` holds any privilege on either table (`has_table_privilege(...)` for both roles, both tables, all of `select`/`insert`/`update`/`delete`, all false). Verifies **AC-15**. *Confirmed 2026-09-03 against the local stack: both flags `t, t` on both tables, all four privileges `false` for both `anon` and `authenticated` on both tables.*
- [x] `service_role` holds `select` on `usage_cap` and nothing on `usage_gate_counter`. Verifies the grant design in `## Feature design`. *Confirmed 2026-09-03: `service_role` select on `usage_cap` is `true`, on `usage_gate_counter` is `false`.*
- [x] `check_usage_gate`'s `EXECUTE` privilege: `authenticated` holds it, `PUBLIC` does not (`has_function_privilege('public', 'public.check_usage_gate(text)', 'execute')` is false). Verifies the "written out rather than inherited" hardening note in the Build plan. *Confirmed 2026-09-03: `authenticated` execute is `true`, `public` execute is `false`.*
- [x] Insert two `usage_gate_counter` rows for the same `(call_type, period, period_start)` with `scope = 'global'` and `profile_id null` on both: the second insert is refused by the partial unique index. Then insert two `account` scoped rows for the same user and window: the second is also refused. Verifies the data model's partial unique index design. *Confirmed 2026-09-03 in a rolled back transaction: both duplicates raised `duplicate key value violates unique constraint` against `usage_gate_counter_global_window_idx` and `usage_gate_counter_account_window_idx` respectively.*
- [x] `usage_gate_counter.profile_id`'s foreign key targets `auth.users(id)`, not `public.profile(id)` (`select confrelid::regclass, pg_get_constraintdef(oid) from pg_constraint where conname = 'usage_gate_counter_profile_id_fkey'`). Verifies the data model row, corrected 2026-09-04 after a fresh model review found no committed check pinned the FK's target beyond a comment. *Confirmed 2026-09-04 against the local stack: `references_table` reads `auth.users`, `definition` reads `FOREIGN KEY (profile_id) REFERENCES auth.users(id) ON DELETE CASCADE`. **Confirmed the same day against the hosted development project too**, after a third fresh model review found this step had only ever been run locally, the one environment that was never in doubt, while `20260902120000_usage_gating.sql` had already been pushed there once before the FK retarget existed: `supabase db reset --linked` (safe against this project only, since spec 0002 records it holds synthetic data by construction) replayed every migration from the current file, and a schema dump confirmed `ADD CONSTRAINT "usage_gate_counter_profile_id_fkey" FOREIGN KEY ("profile_id") REFERENCES "auth"."users"("id") ON DELETE CASCADE`, and the collapsed `usage_cap` lookup (`pg_catalog.max(cap.cap_value) filter (...)`) present in `check_usage_gate`'s body, matching the file exactly.*

## Atomicity and the refusal/attempt split

All of the following run through the Data API with a real minted test session (spec 0004), never the
direct database connection helper: that connection carries no `auth.uid()`, so it either fails
`usage_gate_counter`'s owner check constraint or has no privilege on the table at all under the specced
grants.

- [x] Under cap, a `job_search` call returns `configured: true, allowed: true`, and both `attempt_count` and `consumed_count` increment by one on all three window rows. Verifies **AC-1**, **AC-9**. *Confirmed 2026-09-03 in a throwaway integration test against the real local stack: a real minted session's allowed `job_search` call left `attempt_count: 1, consumed_count: 1` on the global day, global month, and account week rows alike, not just the account row the committed suite checks.*
- [x] A burst of concurrent calls for one account, sized to what the Data API's own statement timeout allows (confirm the current timeout first; do not assume 200 is safe), lands exactly 25 allowed and the rest refused; every call in the burst increments that account's `attempt_count`, and `consumed_count` never exceeds 25. Repeat for the global daily window (66) and monthly window (2000) with enough concurrent callers to exceed each, sized the same way. Verifies **AC-1**, **AC-2**. *Account window: `test/integration/usage-gating.test.ts`'s committed 30-way burst against the real cap of 25 lands exactly 25 allowed. Global windows: confirmed 2026-09-03 in two throwaway integration tests, 15 concurrent calls from 15 distinct real accounts against a dedicated call type with a global day cap of 5, then again with a global month cap of 5, each landing exactly 5 allowed and 10 refused with the matching reason, counter row `attempt_count: 15, consumed_count: 5` both times. The month run's first attempt returned one `database_unavailable` from a transient local connection hiccup, which is itself AC-14 firing correctly under real stress rather than a defect; it passed clean on immediate retry.*
- [x] A refused call's response is `success({ allowed: false, reason })`, never a `Failure`; confirm by asserting `result.ok === true` on a deliberately over cap call. Verifies **AC-5**. *Confirmed throughout the burst and isolation tests above and in the committed suite: every refused decision was read off `result.value` after `isFailure(result)` was `false`.*
- [x] With both the account weekly cap and the global daily cap already exhausted, the next call for that account reports `account_week_cap_reached`, not a global reason. Verifies **AC-3**. *Covered by the committed `test/integration/usage-gating.test.ts` precedence test, re-run clean 2026-09-03.*
- [x] With the kill switch engaged (`app_settings.kill_switch_enabled = true`), a call is refused with `kill_switch_engaged`, and no `usage_gate_counter` row for that call type changes at all (neither counter, on any window), and the RPC is never called at all (confirm by call count, not just by outcome). Verifies **AC-4**, **AC-5**. *Confirmed twice over. A committed integration test now proves it directly (`test/integration-serial/shared-global-state.test.ts`, added 2026-09-04 after a throwaway version first confirmed it by hand 2026-09-03): flips the real `app_settings` row for a real minted session and finds `kill_switch_engaged` with an identical `usage_gate_counter` row count before and after. The committed `gate.test.ts` unit test independently confirms the mocked `rpc` function is never invoked at all on this path.*
- [x] With `readKillSwitch()` forced to fail (a broken read, not an engaged switch), a call is refused with `kill_switch_unavailable`, distinct from `kill_switch_engaged`, and still with no `usage_gate_counter` row touched. Verifies **AC-4**. *Covered by the committed `src/lib/usage-gating/gate.test.ts`, re-run clean 2026-09-03; this branch is `checkUsageGate()`'s own logic on `readKillSwitch()`'s return value, not a database guarantee, so the project's own test design proves it as a unit test rather than against the real stack.*
- [x] An unrecognised `call_type` (no matching `usage_cap` rows at all) returns `configured: false` and is refused through `failure()` with kind `usage_gate_misconfigured`, severity `unexpected`. Verifies **AC-6**. *Covered by the committed `test/integration/usage-gating.test.ts`, re-run clean 2026-09-03.*
- [x] A `call_type` with only one or two of its three required `usage_cap` rows present behaves identically to a completely unconfigured one: `configured: false`, refused through `failure()`. Verifies **AC-6**. *Covered by the committed `test/integration/usage-gating.test.ts`, re-run clean 2026-09-03.*
- [x] Stopping PostgREST (or revoking the gate function's own table access) mid test makes `checkUsageGate()` return `database_unavailable` rather than hanging, throwing past `attempt()`, or returning an unparsed success from a raised exception. Assert the returned kind is `database_unavailable` and that no output column (`configured`, `allowed`, `reason`) was read to reach that result, not merely that the call did not hang. Verifies **AC-14**, and the `configured` column design in `## Feature design`. *Covered by the committed `test/integration-serial/shared-global-state.test.ts` (revokes the owning role's own table access mid test, asserts the `42501` code came from the `.rpc()` response's own `error` field). Moved there from `test/integration/usage-gating.test.ts` 2026-09-04, since the revoke is process wide, cross file state, the same hazard the kill switch flip above is written against; the citation here went stale for a day before this fresh model review caught it.*
- [x] Simulate an `.rpc()` response of `{ data: null, error: null }` (no thrown exception, no reported error, simply nothing back) and confirm `checkUsageGate()` still returns `database_unavailable` rather than treating it as an absent, harmless decision. Verifies **AC-14**. *Covered by the committed `src/lib/usage-gating/gate.test.ts`, re-run clean 2026-09-03; not producible by the real stack (`.single()` always returns either the one row or a PostgREST error), so a unit test is the correct proof, per that file's own documented reasoning.*

## Identity

- [x] A call made with no session returns `session_missing` before any database call happens (confirm via a query count or a deliberately broken database connection still failing the same way). Verifies **AC-13**. *Covered by the committed `test/integration/usage-gating.test.ts`, re-run clean 2026-09-03, and independently reproduced the same day by 10 real `GET /sign-in` requests against a real `pnpm dev` server with no session cookie, each logging `{"ok":false,"kind":"session_missing",...}` from a live `checkUsageGate("job_search")` call, which also generated the real `usage_gate.check` spans engineer-confirmed in Sentry for verify.md's Observability section below.*
- [x] `check_usage_gate` takes no caller supplied identity parameter; confirm this from the function's own signature, not by testing a bypass that the type system already prevents. Verifies **AC-13**. *Confirmed by reading `supabase/migrations/20260902120000_usage_gating.sql`: `check_usage_gate(p_call_type text)` takes only the call type, reading `auth.uid()` internally for the account id.*
- [x] Grep `src/lib/usage-gating/` for `getSession(`: zero matches. Only `getClaims()` verifies the caller. Verifies **AC-13**. *Confirmed 2026-09-03: two matches, both inside comments explaining why `getSession()` is not used; zero actual calls.*
- [x] A signed in caller with no `profile` row is allowed, not refused, and its account scoped counter row is keyed on the auth user id. This is the FK retarget's entire purpose (spec 0011, `## Feature design`), and no test drove it before this fresh model review: every other gate call in the committed suite seeds a profile row first, so the fixed case could not surface even by accident. *Covered by the committed `test/integration/usage-gating.test.ts` ("a signed in caller with no profile row is allowed, not refused"), added 2026-09-04.*
- [x] The `check_usage_gate` function's owning role carries `BYPASSRLS` (`select rolbypassrls from pg_roles where rolname = (select rolname from pg_proc join pg_roles on pg_proc.proowner = pg_roles.oid where proname = 'check_usage_gate')`), confirmed on both the local stack and the hosted development project, the same way spec 0002's `verify.md` P-1 confirmed it for the migration's own `postgres` role. Without this, `usage_cap` and `usage_gate_counter` return zero rows under forced row level security and the function reports every call as `usage_gate_misconfigured`, which is a permissions bug, not a real misconfiguration. *Local stack confirmed directly 2026-09-03: `postgres`, `rolbypassrls = t`. Hosted development project confirmed by hand by the engineer 2026-09-03 in the project's SQL editor, after PR #86 applied the migration there: `check_usage_gate`, owner `postgres`, `rolbypassrls = true`.*

## Observability

- [x] `usage_gate.check` appears in `docs/observability/spans.md` and opens as the first line of `checkUsageGate()`, before the `getClaims()` check and before the `readKillSwitch()` call. Verifies **AC-7**. *Confirmed 2026-09-03 by reading both files directly.*
- [x] Trace sampling reads 1.0 locally (the environment the forced failure smoke test actually runs in; do not infer this from a production shaped build, confirm it directly in the local run). Verifies **AC-8**, **AC-11**. *Confirmed 2026-09-03: `.env.local` reads `NEXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE=1`.*
- [x] Four metric monitors are visible in the Sentry dashboard in the one `jobhunt` project: `usage_gate.check` and `kill_switch.read`, each in both the `development` and `production` environments, each dataset `Spans`, visualize `failure_rate()`, interval `1 day`, High priority Above `0.2`, Medium Above `0.19`, Resolve default, and each with an alert connected that notifies `mghalynho@gmail.com`, matching what `docs/observability/README.md` records. Sentry's Threshold form offers no minimum sample count, so the recorded absence of an attempt floor is confirmed in the form itself rather than assumed. Verifies **AC-10**. *Confirmed by hand on 2026-09-03: the engineer opened all four monitors — `usage_gate.check` and `kill_switch.read` in `development` and `production` — and confirmed High Above `0.2` / Medium Above `0.19` on each, the `usage_gate.check` pair filtering `span.description:usage_gate.check` plus `failure.kind is not session_missing`, the `kill_switch.read` pair filtering `span.description:kill_switch.read` only, each with a connected alert, and the development gate monitor's alert assigned to `mghalynho@gmail.com` with its last issue visible. `/check verify` refused to accept this step on paper alone, which is why the observation is recorded.*
- [x] Each rule's query filters by failure kind (the `failure.kind` span attribute), not by span status alone: confirm a deliberately triggered `session_missing` does **not** move `usage_gate.check`'s ratio, and a deliberate cap refusal does not either. Verifies **AC-5**, **AC-10**. *Confirmed by hand on 2026-09-03, development environment, 24 hour window, `failure_rate()` over the spans dataset. Ten `usage_gate.check` spans carrying `failure.kind: session_missing` were generated deliberately (10 real `GET /sign-in` requests, signed out, against a real `pnpm dev` server, each locally confirmed to return `session_missing`). `span.description:usage_gate.check` returns 98 matches with a 100% failure spike in the bucket containing them; `span.description:usage_gate.check !failure.kind:session_missing`, the monitor's own configured filter, returns 88 matches with that spike absent, while the three earlier spikes from forced `usage_gate_misconfigured` failures remain at 100%. The cap refusal half is proven in the same view: the spans from an earlier 15 call burst against a dedicated global daily cap (see the burst step above) carry `failure.kind` of (no value), so they sit in the denominator of both queries and the numerator of neither, confirming AC-5's design holds under real traffic.*
- [x] **The forced failure smoke test, run locally against the development Supabase project and the `development` environment of the one `jobhunt` Sentry project. Never the `production` environment of that same project, never a Vercel Preview deployment** (Preview samples at 0.1, per `docs/observability/README.md`; most forced failures there would never be captured at all). Deliberately trigger `usage_gate_misconfigured` (an unknown `call_type`) enough times to cross the alert's High threshold within its 1 day interval (there is no attempt floor to cross; see AC-10), confirm the monitor's Connected Alerts list holds an alert, and confirm a real Sentry alert is delivered, not just an issue created — a metric monitor creates issues and notifies nobody on its own, which the first firing on 2026-09-03 demonstrated. Then confirm that a burst of ordinary cap refusals over the same period does **not** move the ratio, proving AC-5's design holds under real traffic, not just under a unit test. Repeat separately for `kill_switch.read`'s own alert, forcing a real read failure. Verifies **AC-11**. *Proved 2026-09-03 in the development environment: with the thresholds back at High 0.2 / Medium 0.19, the monitor's own next evaluation crossed the threshold, created a new issue, and the connected alert's "A new issue is created" trigger delivered a real email to `mghalynho@gmail.com`; the full chain (forced failure, span recorded, sampling captured, fingerprint grouped, threshold crossed, new issue created, connected alert fired, email delivered) is recorded in `docs/experiments/0011-usage-gating-and-kill-switch.md`.*
- [x] **The temporary `checkUsageGate()` call this test adds must load `/profile`, never `/health`.** Sentry's project level inbound filter "Filter out health check transactions" discards `/health`'s entire transaction, and every span nested inside it, at ingest, while an error event raised on the same request still arrives: a smoke test pointed at `/health` shows 26 `usage_gate_misconfigured` issues with zero matching `usage_gate.check` spans, which reads as a broken span rather than a filtered route (confirmed 2026-09-03, `docs/experiments/0011-usage-gating-and-kill-switch.md`). Verifies **AC-11**. *The session_missing probe above used `/sign-in`, not `/health` or `/profile`: `/profile` sits behind the `(app)` layout's session guard, so it cannot itself produce `session_missing`, which is exactly why a signed out reachable marketing route was needed for that specific probe. `/health` was correctly avoided either way.*

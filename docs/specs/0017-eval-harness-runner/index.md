# 0017. Eval harness runner

**Date**: 2026-09-08
**Status**: In Progress

## Summary

This spec defines the one command that runs feature 15's sixteen ground truth pairs against the real scorer and reports which ones held up. Each pair is scored five times for real, since the scoring model's own randomness is not fixed, and a pair only counts as passing when a clear majority of those five runs land on the expected answer. Three kinds of pair need their own rule beyond a plain majority: a pair that measures instability on purpose, a trio of pairs that must stay consistent with each other, and a pair where too many runs failed outright to trust any answer at all. The command prints a table and writes a JSON report every time it runs, and it costs real money each time, so it lives behind its own explicit command rather than inside the free test suite.

## Context

See [rationale.md](rationale.md) for the full problem context, the options weighed for where and how this runs, and the rejected paths.

## Requirements

**User stories**:
- As the person maintaining the scoring rubric, I want one command that scores every ground truth pair for real and tells me which ones no longer match, so a prompt or model change is checked against real expectations rather than a fresh read of the output.
- As the person running this command, I want to iterate on one pair or one tag cheaply, so debugging a single failing pair does not spend the whole weekly allowance.
- As the person reading a report later, I want it to record which model and which rubric wording it was measured against, so a report from three weeks ago can tell "the scorer changed" apart from "the rubric changed".

**Acceptance criteria**:

- **AC-1**: One command (`pnpm eval`) runs every pair in feature 15's committed set and prints, for each pair, a pass, fail, or inconclusive verdict together with the actual band(s) observed. Before minting any session or spending any vendor call, a top level `beforeAll` runs `validateGroundTruth()` against the committed `ARCHETYPES` and `PAIRS`; if it returns any issue, the run throws with every issue printed, one per line, and exits non zero. This check runs even under a `-t` filtered invocation (AC-8), since a `beforeAll` is not itself filtered out the way an `it` would be.
- **AC-2**: Every pair is scored through the real `scoreListing()` path, passing the run's one minted fixture session (`session.jar`) as its `cookieAdapter` argument, exactly the shape `test/integration/fit-scoring-live.test.ts` already uses. One session is minted once for the whole run (not once per pair), reused by every call. A pair's five reruns happen one after another inside that pair's own test body (never fired at once), because they exist to measure how much the same input moves between separate calls; different pairs' test bodies may run at the same time as each other, bounded by an explicit concurrency limit (Build plan, step 1).
- **AC-3**: `scoreListing()` can return three kinds of outcome, and each is handled differently:
  - **A usage gate refusal** (`Result` success carrying `allowed: false`, any of the five `UsageGateReason` values) is never counted toward any pair's denominator. The FIRST refusal seen anywhere in the run aborts the entire run immediately: every other pair's in flight or not yet started test fails with the refusal's own reason named, the partial report is still written (marked `aborted: "<reason>"`, carrying whatever pair verdicts had already completed), and the run exits non zero. A budget or kill switch stop is an operator condition, not evidence about the rubric, and must never be read as sixteen ordinary `inconclusive` verdicts.
  - **A rerun failure** (a `Result` failure: a vendor timeout or a malformed response) counts against that one pair's own denominator only and never aborts the run.
  - **A scored success** (`allowed: true`, a real band) is what the verdict rule below counts.

  A pair's verdict needs at least 3 of its 5 reruns to be scored successes; with fewer than 3, the pair is `inconclusive` (sub reason `insufficient-successes`), reporting whatever successes did land, never silently folded into a pass or a fail. With 3 or more successes, and the pair is not tagged `stability-probe` (AC-4 covers that case separately): compute how many of the successes landed on each band. If one band holds a strict majority (more than half of the successes), that is the pair's verdict band, and the pair passes if that band equals `expectedBand`, or, when `acceptableBands` is present, if it is one of them. If no band holds a strict majority (e.g. a 2 and 2 split out of 4 successes, or a 1, 1, 1 split out of 3), the pair is `inconclusive` (sub reason `no-majority`) UNLESS `acceptableBands` is present and every successful rerun's band is inside it, in which case the pair passes with no single verdict band, reporting the full observed split instead (this is what makes `boundary-seniority-gap`'s own honest, anchor stated ambiguity, e.g. a 2 and 2 `weak_match`/`not_a_match` split, a pass rather than a false `inconclusive`).
- **AC-4**: A pair tagged `stability-probe` is judged differently, but only once AC-3's own 3 of 5 successes floor is met (fewer than 3 successes is still `inconclusive` under AC-3, unchanged). With 3 or more successes, `expectedBand` is not consulted and no majority is computed: the pair passes only if every one of its successful reruns' band is inside `acceptableBands`. One success landing outside that set fails the pair even if every other success matched, since this pair's whole point is that no single run should be trusted as the answer. Because there may be no single winning band, this pair's verdict is always reported as its observed distribution (e.g. `{ strong_match: 3, possible_match: 2 }`), never a lone band.
- **AC-5**: The three `preference-isolation` tagged pairs (`preference-match`, `preference-violation`, `preference-title-conflict`) are each judged individually by AC-3 first, exactly like any other pair, with no special treatment of their own verdicts. Once all three have a verdict that is neither `inconclusive` nor missing (skipped by a `-t` filter that excluded one of them, in which case the check below is skipped and reported as `leak-check-skipped`), the run additionally compares `preference-match`'s verdict band against `preference-violation`'s and against `preference-title-conflict`'s:
  - If `preference-match`'s band equals both conflict pairs' bands, nothing further is reported; each pair's own individual pass or fail already stands.
  - If all three bands equal each other but none of them equals `strong_match` (`expectedBand`), the run reports `baseline-drift`: something moved the band for every pairing equally, which is a rubric or model question, not a leak, since nothing about the conflicting posting text distinguished itself.
  - If `preference-match`'s band differs from either conflict pair's band, the run reports `preference-leak-suspected`, distinctly from an ordinary mismatch: the skill and experience content is identical across all three, so a divergence here can only be explained by the preference text that does differ between them.
- **AC-6**: Every printed and reported verdict names its own denominator (e.g. "good_match, 3 of 3 succeeded" or, for a distribution shaped verdict, "3 strong_match / 2 possible_match, 5 of 5 succeeded"), never just a band on its own, so a reader can tell a verdict resting on the minimum 3 successes apart from one resting on all 5, and can see a split even where the pair still passed.
- **AC-7**: The command's own exit code is non zero if any pair fails, any pair is `inconclusive`, a preference leak is reported, or the run aborted on a usage gate refusal (AC-3); zero only when every pair that ran passed cleanly and nothing aborted.
- **AC-8**: A subset of pairs can be run without spending calls on the rest of the set, by reusing the test runner's own name filter against each pair's test name, which is generated as `` `${pair.id} [${pair.tags.join(" ")}]` `` (e.g. `control-direct-match [control]`, `stability-probe-generic [stability-probe]`), so `pnpm eval -t control-direct-match` matches one pair by id and `pnpm eval -t stability-probe` matches every pair carrying that tag. A filtered run still writes a JSON report; it records which filter produced it and lists every pair that did not run as `skipped`, never silently absent. Filters can overlap (e.g. `-t control` also matches every pair whose id happens to start with `control-`); this is an accepted property of substring matching, not a bug to design around.
- **AC-9**: The command writes a JSON report every run, in addition to the console table, to a directory this repository does not track, at `test/eval/.output/<ISO timestamp with colons replaced by dashes>.json`, creating that directory if it does not exist. Each report is a single `EvalReport` object (defined in `test/eval/report.ts`) recording: the filter used (if any) and every skipped pair id; per pair, its status (`pass`/`fail`/`inconclusive`), sub reason where relevant, denominator, and every observed band (or band distribution); the preference leak check's own outcome; the run's overall status and aborted reason if any; and, once per report, which model answered (via the shared `resolvedModel()` guard on `TIERS.ai_scoring.model`, never a name typed into the harness) and a hash of `BAND_ANCHORS`'s current text (`bandAnchorsHash()`, defined once and shared with the AC-10 test, so "the same way" is true by construction rather than by two separate implementations agreeing).
- **AC-10**: A committed test (no vendor call, runs under the ordinary free unit suite) asserts `BAND_ANCHORS` literally equals today's text (`toEqual` against the five strings written inline in the test, never a snapshot file, which a routine `vitest -u` could silently rewrite) and that `bandAnchorsHash(BAND_ANCHORS)` equals today's computed hash, both failing by name and naming spec 0016's dataset, the moment either changes, so a rubric edit is caught at commit time rather than only by a human comparing two JSON reports later.
- **AC-11**: The command works against a changed model with no code edit to this feature: nothing here names a vendor or a model id directly, every call goes through the existing `scoreListing()` / `TIERS` path exactly as the rest of the app does, and the model id reported (AC-9) is read off that same resolved config.

## Feature design

**Data model sketch**: none new. This feature reads feature 15's already committed `ARCHETYPES` and `PAIRS` (`src/features/scoring/eval/`) and writes only to a gitignored local file; no table, no migration.

**State transitions**: none, a script run start to finish. Per pair verdict states: `pass` · `fail` · `inconclusive` (sub reasons `insufficient-successes`, `no-majority`). Run level states: `completed` · `aborted` (carrying a `UsageGateReason`).

**API surface**: not a request surface. The one "endpoint" is the command line:

| Command | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|
| `pnpm eval` | optional `-t <pattern>`, matched against each pair's generated test name (id and tags, AC-8) | console table, `test/eval/.output/<timestamp>.json`, an exit code | one fixture session minted once for the run (`test/helpers/mintFixtureUser`, `test/helpers/mintSession`), reused by every call | `validateGroundTruth()` finding an issue in the committed data (AC-1, refused before any spend); a usage gate refusal aborting the run (AC-3); a vendor timeout or malformed response on one rerun (counted against that pair's own denominator, AC-3); the local Supabase stack not running (the existing `require-stack` global setup's own named failure) |

**Value sourcing**:
| Action | Value produced / displayed | Source |
|---|---|---|
| Scoring one rerun of one pair | which profile and listing are sent | `pair.listing` and `ARCHETYPES.find(a => a.id === pair.archetypeId).profile`, exactly feature 15's committed data (AC-1) |
| Scoring one rerun of one pair | the caller's identity | the one fixture session minted once in this run's own setup, passed as `scoreListing()`'s `cookieAdapter` argument, reused (not reminted) across every pair and rerun (AC-2) |
| Computing a pair's verdict | the pass, fail, or inconclusive call, and any sub reason | the pure verdict function in `test/helpers/eval-verdict.ts`, given the pair's `expectedBand`, `acceptableBands`, and `tags`, and this run's own array of scored/failed/refused rerun outcomes, per the rule in AC-3 and AC-4 |
| Computing the preference leak flag | `preference-leak-suspected` · `baseline-drift` · nothing · `leak-check-skipped` | the three `preference-isolation` pairs' own verdict bands, already computed by the step above, compared per AC-5 |
| The JSON report's model field | which model answered | `resolvedModel(TIERS.ai_scoring.model).modelId`, `resolvedModel` exported from `src/lib/ai/tiers.ts` (lifted from the equivalent guard already written, but kept private, in `src/lib/ai/tiers.test.ts:23-30`), never a name typed into the harness (AC-9, AC-11) |
| The JSON report's anchors field | whether the rubric text has moved since the data was authored | `bandAnchorsHash(BAND_ANCHORS)`, a pure function in `src/features/scoring/eval/band-anchors-hash.ts` (sha256 over `BANDS.map(b => \`${b}:${BAND_ANCHORS[b]}\`).join("\n")`, first 12 hex characters), imported by both this report writer and the AC-10 test, so both read the one real function (AC-9) |
| The run's own exit code | pass, fail, aborted, or a mix | the aggregate of every pair's verdict, the preference leak flag, and whether the run aborted on a usage gate refusal (AC-7) |

**Key invariants**:
- A pair's five reruns are never fired concurrently with each other; only different pairs' test bodies may overlap (AC-2), bounded by `maxConcurrency` (Build plan, step 1).
- A verdict is never printed or reported without its denominator alongside it (AC-6).
- `pnpm eval` is never reachable from `pnpm test` or `pnpm test:integration`: it is its own Vitest project, selected only by explicit `--project eval` (which the `pnpm eval` script wraps), so no existing command starts spending real vendor calls by accident.
- Nothing under `test/eval/` or `test/helpers/eval-verdict.ts` names a vendor package or a model id; every real call goes through `scoreListing()`, and the reported model id goes through the shared `resolvedModel()` guard (AC-11).
- The `BAND_ANCHORS` drift assertions (AC-10) live in the ordinary unit suite (`pnpm test`), never behind a vendor call, so a rubric edit is caught on every push, not only when someone happens to run the harness.
- The minted fixture user is deleted (`deleteFixtureUser`) after the report is written, in an `afterAll`, matching `test/helpers/fixture-user.ts`'s own reason for existing: an undeleted fixture user otherwise accumulates in the local database on every run, the same way `fit-scoring-live.test.ts` already avoids it. Cleanup runs after the report write, in that order, so a cleanup failure can never destroy the run's own output.
- One session is expected to outlive the whole run (sixteen pairs, bounded concurrency, five sequential calls each): this is assumed to comfortably fit inside Supabase's session lifetime today, and is not re verified per call. If feature 15's set grows large enough, or `ai_scoring` itself grows slower, to approach that lifetime, this assumption needs revisiting (Follow up).

**Security model**: No user facing surface and no user data. The fixture session this feature mints is the same development only, `DEV_SESSION_ENABLED` gated path `test/helpers/session.ts` and `test/helpers/fixture-user.ts` already use for `fit-scoring-live.test.ts`; nothing new is added to that gate. The one real exposure is that every archetype's `summary`, `skills`, and `experience` text reaches OpenAI on every run of this command, which is exactly spec 0016's own AC-1 (no real person, no real employer) doing its job here too.

**Configuration required**: none new. Reuses `OPENAI_API_KEY`, `SUPABASE_SECRET_KEY`, and `DEV_SESSION_ENABLED`, already validated by `src/env.ts` and already required for the local Supabase stack this command needs running.

**Critical test scenarios**:
- Happy path: `pnpm eval -t control-direct-match` scores that one pair for real, five sequential reruns under the one minted session, and prints a passing verdict with its denominator (e.g. "strong_match, 5 of 5 succeeded"), verifies **AC-1**, **AC-2**, **AC-6**, **AC-9**.
- Failure case: a pair whose five reruns come back as 2 scored and 3 vendor failures is reported `inconclusive` (`insufficient-successes`) rather than a false pass or fail, the run's own exit code is non zero, and the other pairs in the same run still complete, verifies **AC-3**, **AC-7**.
- Abort case: constructed against `test/helpers/eval-verdict.test.ts`'s own fixtures, the first rerun outcome carrying `allowed: false` (any `UsageGateReason`) stops the run from counting it toward any denominator and marks the run `aborted`, verifies **AC-3**.
- Data quality gate: `validateGroundTruth()` returning even one issue against a deliberately broken fixture set stops the command before any vendor call is made, verifies **AC-1**.
- Cross pair check: constructed verdicts where `preference-match` lands on `strong_match` but `preference-violation` lands on `good_match` (with `preference-title-conflict` unchanged) trip `preference-leak-suspected`, while all three landing together on `good_match` instead trips `baseline-drift`, verified against `test/helpers/eval-verdict.test.ts`'s own fixtures rather than a real run, verifies **AC-5**.
- Drift guard: editing `BAND_ANCHORS`'s text fails the AC-10 test by name, under the ordinary free `pnpm test`, verifies **AC-10**.

## Build plan

This project's default build approach is Tracer Bullet (a thin end to end slice proven before scaling). Applied here: prove the whole real path, real vendor call, real verdict, real report, on exactly one pair before scaling to all sixteen and the cross pair and aggregate logic.

1. Add the `eval` Vitest project to `vitest.config.mts`: `extends: true` (pulls in the root `resolve.tsconfigPaths` and the `server-only` alias every other project already relies on; omitting it is exactly the failure Option 2 was rejected for, since `scoreListing()`'s own `import "server-only"` throws without it), `include: ["test/eval/**/*.test.ts"]`, `environment: "node"`, the shared `setupFiles`, `globalSetup: ["./test/setup/require-stack.ts"]`, `testTimeout: 300_000` (five sequential `ai_scoring` calls at its own 30 second `timeoutMs` ceiling each, plus headroom, since one pair's test body cannot finish faster than its slowest rerun), `hookTimeout: 60_000` (the fixture user mint against a possibly cold stack), `maxConcurrency: 4` (a real, installed Vitest 4.1.11 option bounding how many pairs' test bodies run at once; set explicitly rather than left at whatever the installed version currently defaults to), and `fileParallelism: false` scoped to this project alone, the same reason `integration-serial` already carries it: this project is written to hold exactly one file sharing one minted session and one report writer, and a second file here would run in a separate worker by Vitest's own default, mint a second session, and race the first on the same report filename. Add the `"eval": "vitest run --project eval"` script to `package.json`. Satisfies **AC-1**, **AC-2**, **AC-11**.
2. Export `resolvedModel()` from `src/lib/ai/tiers.ts` (lifted from the equivalent already written, but currently private to `src/lib/ai/tiers.test.ts`, which switches to importing it instead of keeping its own copy), and add `bandAnchorsHash()` as a small pure function in `src/features/scoring/eval/band-anchors-hash.ts`. Write the pure verdict logic in `test/helpers/eval-verdict.ts`: the three way outcome classification (refusal, rerun failure, scored success) from AC-3, the majority vote with the 3 of 5 inconclusive floor and the no majority/`acceptableBands` exception, the distinct `stability-probe` "every success inside `acceptableBands`" rule (AC-4), and the `preference-isolation` baseline comparison (AC-5). Wire `test/helpers/eval-verdict.test.ts` against constructed fixtures for each rule, no vendor call involved. Satisfies **AC-3**, **AC-4**, **AC-5**, **AC-6**.
3. The thin thread: `test/eval/harness.test.ts`, one `describe("eval harness")`, a top level `beforeAll` running `validateGroundTruth()` (throwing with every issue if any, before anything else) then minting the one fixture session for the run; one `it.concurrent` per pair named `` `${pair.id} [${pair.tags.join(" ")}]` ``, whose body awaits five sequential `scoreListing()` calls, feeds the outcomes to step 2's verdict function, stores the result in a module scoped `Map<string, PairVerdict>` keyed by pair id, and asserts (via the test context's own `expect`, required under `it.concurrent`) that the verdict's status is `pass`, so `fail` and `inconclusive` both fail their own test with the denominator and distribution in the message; and a final `afterAll` that runs the preference leak check against the map, writes the JSON report (including the model id and anchors hash), then deletes the fixture user. Prove this against exactly `control-direct-match` (real vendor calls) before scaling: get `pnpm eval -t control-direct-match` green end to end. Satisfies the first slice of **AC-1**, **AC-2**, **AC-9**.
4. Scale to the full sixteen pairs, confirm `maxConcurrency` and `fileParallelism` behave as designed under a real, unfiltered `pnpm eval` run, and confirm the run's own exit code is non zero on a fail, an inconclusive pair, a leak, or an abort, and zero only when everything that ran passed cleanly. Satisfies the rest of **AC-1**, **AC-2**, **AC-7**, **AC-8**.
5. Add the committed `BAND_ANCHORS` drift test under `src/features/scoring/eval/` (the ordinary unit project, no vendor call): a literal `toEqual` pin of today's text plus a `bandAnchorsHash()` equality check, both failing by name, pointing at spec 0016's dataset, the moment either changes. Satisfies **AC-10**.
6. Add `/test/eval/.output/` to `.gitignore`. Satisfies **AC-9**.

## Consequences

**Positive**:
- Spec 0015's AC-2 (do the five bands actually spread real listings) and spec 0016's whole purpose (a ground truth set with nothing to run it against) both get their first real answer.
- The preference isolation check gives a structural, named way to catch a preference leaking into the band, distinct from an equally real but different finding (the rubric drifting for everyone at once), which closes the gap `rubric.ts`'s own comment names as otherwise untestable.
- The `BAND_ANCHORS` drift test means a rubric wording change is caught by the free, always run unit suite, not only by someone remembering to run the paid harness and compare two reports by hand.
- Reusing `scoreListing()` unchanged, rather than a second call path straight to `TIERS`, means this feature can never drift from what the real app actually sends; a schema or prompt change is proven here exactly as it is proven in production. Aborting the whole run on the first usage gate refusal, rather than absorbing it into ordinary per pair accounting, keeps that same honesty: a budget or kill switch stop is reported as exactly what it is, not laundered into a wall of `inconclusive` verdicts that would misdescribe what actually happened.

**Negative / tradeoffs**:
- A full run spends 80 real vendor calls (16 pairs times 5 reruns) every time it runs the whole set; the `-t` subset filter is what keeps day to day iteration cheap, but this is still the largest deliberate, repeatable spend in this project, and it grows linearly with every future pair added to feature 15's set.
- The 3 of 5 success threshold for `inconclusive` means a genuinely bad but real result (all 5 reruns land on the same, wrong band) is never confused with a run too broken to trust, which is correct, but it also means an unlucky run (3 vendor timeouts and 2 real, matching answers) is reported exactly the same way as one with no useful data at all, even though 2 real matching answers is weak but real evidence. This spec accepts that loss rather than inventing a second, softer verdict tier.
- The preference leak check only covers the three pairs feature 15 built for exactly this purpose; it is not a general "did any preference move any band" detector across the other thirteen pairs, none of which vary a preference at all.
- `maxConcurrency` bounds how many pairs run at once, not how many vendor calls run at once across pairs; a pair whose own five reruns are mid flight does not free a concurrency slot until all five finish, so the actual number of simultaneous vendor calls can briefly exceed the pair level bound. This is accepted rather than built around, since the global day cap (1320) has wide headroom under this feature's whole weekly spend.
- Aborting the entire run on the first usage gate refusal means one unlucky global cap hit (shared with whatever else is calling `ai_scoring` at the time, including local `pnpm dev` usage) discards every result computed so far in that run, even pairs that had already cleanly passed. This is accepted because a refusal genuinely means the run's remaining data would not reflect real scoring anyway, not because the discarded cost is small.

**Neutral**:
- If the ground truth set (feature 15) grows past sixteen pairs, this feature's cost and run time grow with it; nothing here caps the set's size, that boundary belongs to spec 0016.
- The JSON report format is not versioned or schema checked; it is a plain, structural artifact for a human to read or diff by hand, not a contract another program depends on. If that changes later (a dashboard, a CI gate reading these reports), the format becomes its own decision.

## Follow-up

- [ ] This spec deliberately does not gate `pnpm eval` behind an explicit opt-in environment variable the way `TEST_LIVE_MODEL_CALLS_ENABLED` gates the one paid case inside `pnpm test:integration`. The safety mechanism here is that `eval` is its own Vitest project, reachable only by naming `--project eval` explicitly, and never included in `pnpm test` or `pnpm test:integration`. If a later command is ever added that runs every Vitest project unfiltered, revisit whether that alone is still enough.
- [ ] The global day cap for `ai_scoring` (1320, shared across everything that calls this tier, including local `pnpm dev` usage on `/search`, not scoped per fixture user) is the real ceiling this feature can hit, not the account weekly cap (500): since this feature mints a fresh fixture user every run, that account counter starts at zero each time and is not the binding constraint. Roughly sixteen full 80 call runs a day share that global ceiling with everything else touching `ai_scoring` locally; worth watching once this ships if iteration gets heavy, not solved here.
- [ ] `src/lib/ai/tiers.ts`'s `TIERS[tier].model` is typed `LanguageModel`, a union that also permits a plain gateway model id string `tiers.ts` itself never constructs; the `resolvedModel()` guard this feature exports narrows past that, matching the reasoning already written beside the guard it replaces in `tiers.test.ts`. If `tiers.ts` ever legitimately needs the string form, `resolvedModel()`'s own throw is where that would first surface, and it would need revisiting then, not guessed at now.
- [ ] Root `AGENTS.md`'s `## Commands` section (line 37) still describes Vitest as "two projects"; it was already stale before this feature (spec 0011 added the third, `integration-serial`, on 2026-09-03) and this feature adds a fourth plus a new `pnpm eval` script the commands list does not yet name. `/architect` does not edit `AGENTS.md`; flagging it here for `/sync` or a direct edit once this feature builds.
- [ ] This spec assumes the one minted session comfortably outlives a full run (sixteen pairs, bounded concurrency, five sequential calls each) without needing a refresh. If feature 15's set grows large enough, or a slower model tier is ever routed through this same harness, to make that assumption doubtful, re minting per pair (at the cost of more setup calls) is the fix, not something this build needs to solve preemptively.

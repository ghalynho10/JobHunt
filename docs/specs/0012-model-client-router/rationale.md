## Context

Spec 0001 already named the two files this feature owns, `src/lib/ai/tiers.ts` for the tier to vendor and model map and `src/lib/ai/client.ts` for the router, and already bound the project to AI SDK 7 with direct provider packages, one key per vendor. What it left open is everything this spec decides: which two vendors, what shape a call takes, how a failure is told apart from a budget refusal, and how the two connect to the usage gate feature 10 already built.

Two callers are already named in the project's scope even though neither is designed yet. Feature 14, fit scoring with shown reasoning, needs a bulk call that returns a score plus the matched and missing skills, structured data, not prose. Feature 17, cross vendor self check, needs a second call that checks the first call's reasoning for fabricated skills, and its own done when clause requires that check to run on a demonstrably different vendor than scoring. Both callers need the router to hand back parsed, schema validated data, and neither should ever see a vendor name or a model string.

Feature 10 (usage gating and kill switch) was designed and built on a separate branch, `feat/usage-gating-kill-switch`, and was not yet merged to `main` at the time this spec was written, which is why it was invisible from a plain listing of this branch's specs then. It has since merged (`5b01b4c`, pull request 86), and spec 0011 is Accepted. Its `checkUsageGate(callType, cookieAdapter)` is generic across `call_type` by design specifically so a new call type is a `usage_cap` row, never a migration or a new code path. This spec's router is the second caller of that gate, after `job_search`, and the two tier names chosen here double as the `call_type` strings that gate reads.

Money is the forcing constraint underneath all of this. Adzuna's own limits gave feature 10 a real ceiling to divide a budget against; a model vendor has no such ceiling, so the numbers this spec seeds into `usage_cap` are a spend decision, not a derivation from someone else's terms, and they are recorded here as dollars, not just call counts, so they can actually be judged against the named risk of uncontrolled cost on a self-funded project.

## Options considered

### Option 1: One generic tier dispatch function, structured output only

A single exported function takes a tier name, a Zod schema, and prompt content, resolves the tier's vendor and model from `tiers.ts`, calls the usage gate, then calls the vendor's `generateObject` with the fixed generation parameters `tiers.ts` names for that tier.

**Pros**:
- One function, one shape, matches both known callers (feature 14 and feature 17) exactly, since both need validated structured data, not prose.
- Nothing about a caller's request can widen a tier's cost profile, since generation parameters live in `tiers.ts`, not the call site.

**Cons**:
- A future caller that only wants a short plain text answer still has to shape a one field schema to use the router, a small amount of ceremony for a case that does not exist yet.

### Option 2: Two call functions, one for plain text and one for structured output

Expose both `generateTextTier()` and `generateObjectTier()`, mirroring the AI SDK's own `generateText` and `generateObject` split.

**Pros**:
- Matches the underlying SDK's own shape, so a future caller reads familiar AI SDK documentation directly.

**Cons**:
- Doubles the router's own surface, its tests, and its failure handling for a plain text path neither known caller needs. Every line of that second path is a line no acceptance criterion here exercises.

### Option 3: Callers construct the provider client directly, tiers.ts only holds config

`tiers.ts` stays a plain data map (tier to vendor name and model id); each caller imports the map and calls the AI SDK itself.

**Pros**:
- No router module to write at all, the smallest amount of new code.

**Cons**:
- This is the shape spec 0001 already rejected by naming `client.ts` as "the feature 13 router" in its own directory layout: without one call site, the usage gate check, the span, and the failure mapping would each need repeating in every caller, and a caller that forgets one of them fails silently rather than visibly.

## Rationale

Option 3 is ruled out first: spec 0001's own directory layout already names `client.ts` as this feature's router, which is a decision that a shared choke point is worth building, not a detail left open. Repeating the gate check, the span, and the failure mapping in every caller is exactly the shape that lets one caller forget a step, and a forgotten usage gate check is the named risk feature 10 exists to close, not a small omission.

Between Option 1 and Option 2, the deciding force is that both callers named in scope today, feature 14 and feature 17, need validated structured data, and the acceptance criteria a plain text path would satisfy do not exist yet. Building a second call shape now is the same failure pattern spec 0001's own binding rule 8 warns about deferred tooling choices: a candidate that cannot meet what is actually needed is not a candidate, and a plain text path meets no named need today. A future caller that genuinely wants prose can still ask for a one field schema, or this spec can be revisited when that caller exists.

**Why OpenAI over Anthropic and Google for `ai_scoring`.** `ai_scoring` is the higher volume, higher stakes tier: it runs on every listing a search returns (not once per search, see the call shape correction below), and its output, the shown reasoning, is the feature's whole usability point, so both cost and reasoning quality matter here more than for the narrower check tier. Two things point the same direction at once, which is what makes this a clean pick rather than a coin flip between accuracy and price:
- **Capability**: GPT-5.6 Luna beats this spec's original pick, Claude Haiku 4.5, on Artificial Analysis's own Intelligence Index, and Artificial Analysis's own stated split, "Luna wins on cost-driven, high-volume text work; Haiku 4.5 wins on fast coding and regulated deployments" (per the engineer's brief), maps directly onto this task: fit scoring is text reasoning against a rubric, not code, and this project has no regulated-deployment requirement.
- **Cost**: at $0.20 / $1.20 per MTok, GPT-5.6 Luna is roughly 5x cheaper than Haiku 4.5 ($1/$5) and roughly 10x cheaper than the corrected Claude Sonnet 5 price ($2/$10) on both input and output. This project's own established principle (this spec's 2026-09-03 version, reaffirmed here) is that price is a tiebreak only between candidates of roughly equal accuracy, never the deciding force on its own. It does not need to be invoked as a tiebreak here, because Luna does not trade accuracy for price against Haiku 4.5, it wins on the available benchmark and costs less; the two considerations agree rather than pull against each other. Claude Sonnet 5 remains available as a stronger but far pricier option; nothing in the available evidence suggests fit-scoring against a rubric needs Sonnet class reasoning, and feature 16's eval harness (see Follow-up) is the actual mechanism to prove that wrong if it turns out to be.

Google was not seriously considered for `ai_scoring`: Gemini 3.7/3.8 Flash ($0.75/$3.75) sits between Luna and Haiku on price with no benchmark evidence in hand suggesting it beats Luna on this task, and moving Google onto `ai_scoring` would just relocate the same "which vendor does the narrower check task" question rather than resolve it, since `ai_check` still needs a second, different vendor. Anthropic was not carried forward onto `ai_check` either: Haiku 4.5 costs roughly 3x Gemini 3.5 Flash-Lite ($1/$5 vs $0.30/$2.50) for a task, verifying that cited skills are genuinely present in the listing and profile text, that is narrower and more mechanical than scoring and has no evident need for Haiku's own strengths (fast coding, regulated deployment). Google, already proven as the check vendor in this spec's original design, keeping the same model (`gemini-3.5-flash-lite`) it already used, is the option with no open question left to answer.

**Anthropic is parked, not rejected.** The engineer's own preference for Claude Sonnet 5 rests on Anthropic's aggregate reputation and capability, not on any evidence specific to this project's fit-scoring task, and is recorded as such rather than folded into this pick; feature 16's eval harness against feature 15's ground truth set, not this spec, is the mechanism that should settle whether Sonnet 5 (or Haiku 4.5, or either at a different reasoning effort) actually scores better on this task than GPT-5.6 Luna does.

**Model ids and pricing, verified 2026-09-06 directly against each vendor's own current docs** (Anthropic's own price for the model this feature no longer uses had already moved since 2026-09-03; see the note above the revision):
- OpenAI: `gpt-5.6-luna`, part of the three tier GPT-5.6 family (Sol, Terra, Luna) released 2026-07-09, described in OpenAI's own model guidance as suited to "high-volume, latency-sensitive tasks such as chat, classification, and lightweight agentic workflows." $0.20 per million input tokens, $1.20 per million output tokens (openai.com blocked a direct fetch with HTTP 403; corroborated across OpenRouter, Requesty, and pricepertoken, all agreeing on the exact figure). `reasoning.effort` supports `none | low | medium (default) | high | xhigh | max`; this spec fixes it to `"medium"` in `tiers.ts`, the level Artificial Analysis's own Intelligence Index already shows beating Claude Haiku 4.5 (39 vs 30), without reaching for the cost of `"high"`/`"xhigh"`/`"max"`. **A real constraint, not just a knob**: the OpenAI API rejects `temperature: 0` with an HTTP 400 whenever `reasoning.effort` is not `"none"`, so `ai_scoring`'s tier config leaves `temperature` unset rather than fixed at `0` the way `ai_check` is (see `index.md`'s Build plan and Consequences).

**The determinism decision, made explicitly rather than left as a side effect.** `ai_scoring` cannot be both deterministic and reasoning-capable on this model: `temperature: 0` is only accepted at `reasoning.effort: "none"`, and `"medium"` is what this spec picked. Two options were on the table:
- **Accept nondeterminism, size the bands to absorb it (chosen).** Feature 14's own scope already frames scoring as "an anchored band rubric rather than an open numeric range," bands as coarse categories rather than an exact score, which is the right instrument to absorb ordinary sampling variance: a clear-fit pair should land in the same band on any run, and only a pair that already sits near a boundary should ever flip between adjacent bands. Feature 15, when it authors the ground truth set's expected bands, should treat a same-or-adjacent-band result as a pass, not a regression. This keeps `"medium"` effort, and with it the Intelligence Index comparison (39 vs Claude Haiku 4.5's 30) that this spec's `ai_scoring` pick actually rests on.
- **Drop to `reasoning.effort: "none"` with `temperature: 0` (rejected).** Buys full determinism, but at a real, specific cost: Artificial Analysis's Intelligence Index figures this spec cites (34 at `"low"`, 39 at `"medium"`, 52 at `"max"`) were not measured at `"none"`, so switching would forfeit the exact comparison this pick rests on, in exchange for a capability level with no benchmark evidence in hand, one that could plausibly ship a worse model than Claude Haiku 4.5, the pick this revision replaced. Trading a known, verified capability edge for an unverified one purely to buy determinism is not a trade this spec is willing to make.
- **What this means for Follow-up 119's alias-pin trigger.** That trigger is "a pair falling outside its expected band that cannot be attributed to a prompt change or a ground truth change." A single boundary-adjacent flip on one run is exactly the sampling noise the band width above is sized to absorb, so it is not, on its own, that trigger. What should count is a pair landing two or more bands away from expected, or a flip that reproduces across repeated calls to the same pair rather than appearing once; distinguishing the two, for instance by re-running a flagged pair before treating it as a real signal, is feature 16's own eval harness design to make, not settled here.
- Google: `gemini-3.5-flash-lite`, described on Google's own page as "our fastest, most cost effective 3.5 model for high throughput execution," $0.30 per million input tokens, $2.50 per million output tokens, re-verified unchanged 2026-09-06. Source: `https://ai.google.dev/gemini-api/docs/models` and `https://ai.google.dev/gemini-api/docs/pricing`.
- **`gpt-5.6-luna` is an alias, not a pinned snapshot**, per OpenAI's own model documentation, which lists dated snapshots and aliases separately for GPT-5.6 Luna. Using the alias is consistent with how this spec already treated Anthropic's own alias convention for its original pick; the same tradeoff applies (OpenAI can silently repoint it to a newer Luna build with no commit here) and the same Follow-up trigger carries over, now naming the new vendor (see `index.md`).

At the corrected volume (40000 calls/month, one call per listing rather than one per search), the same spread is roughly $340 a month between the cheapest and most expensive candidate, no longer trivial for a project this size. That volume correction, not a change of philosophy, is why GPT-5.6 Luna's price now carries real weight in this spec's `ai_scoring` pick: it is not a case of price overriding accuracy, since Luna also wins on the one benchmark comparison available (see **Why OpenAI over Anthropic and Google for `ai_scoring`** above); price and accuracy point the same direction. Feature 16 should still rank the full candidate set on accuracy against the ground truth set (feature 15) once it exists, since Artificial Analysis's aggregate Intelligence Index is not the same thing as accuracy on this project's own fit-scoring task, and a real ground truth comparison could still overturn this pick. GLM is also not a price only substitute: it is operated by Zhipu AI, a different jurisdiction than Anthropic, Google, or OpenAI, so choosing it over the others is a deliberate data residency decision for the engineer, not something a benchmark result alone should settle; spec 0009's privacy notice would need a new statement if it is ever chosen.

**Budget derivation, revised 2026-09-06.** `usage_cap`'s account per week cap for `ai_scoring` originally mirrored `job_search`'s own value, 25, on the assumption that feature 14 makes one scoring call per search. That assumption is now resolved, not carried forward: feature 11 (job search & results list) shipped 2026-09-04 with `RESULTS_PER_PAGE = 20` (`src/features/search/adzuna.ts:36`), and this revision decides the call shape is one `ai_scoring` call per listing, not one batched call covering all twenty. **Why per listing, not batched**: batching every listing a search returns into a single call was the other option this spec's original Follow-up left open, and it is rejected here for three reasons, each traceable to a concrete requirement elsewhere in this project. First, scope.md's own Done-when clause for feature 14 requires "every score displays its matched and missing skills," which reads as genuine, engaged reasoning per listing, not a shared pass touching twenty listings in one response; a model asked to reason carefully about twenty unrelated listings in one call is exactly the shape that degrades per-item attention. Second, `generateObject`'s schema validation is all-or-nothing (AC-6): a single malformed field anywhere in a twenty-item batch would fail all twenty scores at once, a much larger blast radius than one listing failing on its own, in direct tension with this spec's own AC-5/AC-6 failure model of a visible, contained failure. Third, feature 16's eval harness runs "every ground truth pair" (scope.md), which is inherently a per-pair, per-listing shape; keeping the router's real call shape one-listing-per-call keeps the harness measuring the same thing production actually does. So the real multiplier feature 11 settles is 20, and `ai_scoring`'s account per week cap becomes `25 × 20 = 500`. With the check tier still sampled at 1.0 (every scoring call also gets a check call, unchanged from the engineer's original answer), `ai_check`'s account per week cap is set equal to `ai_scoring`'s corrected value, 500, for the same reason as before: a lower number would leave some scored listings without a check, a partial failure that reads like a working page.

The global day and month ceilings are, by the same multiplier, `job_search`'s own numbers (66, 2000) times 20: `1320` and `40000`, still borrowed from `job_search`'s shape purely for one consistent budget structure across every row in `usage_cap`, not derived from any vendor ceiling the way `job_search`'s were derived from Adzuna's terms. What actually answers feature 10's named risk, uncontrolled cost on a self-funded project, is the dollar figure this larger ceiling implies: at 40000 calls a month, `ai_scoring` on GPT-5.6 Luna costs at most about $73.60 a month (using the ~1200 output token estimate below, which already accounts for this model's own hidden reasoning tokens), and `ai_check` on Gemini 3.5 Flash-Lite costs at most about $32 a month, a combined worst case of about $105.60 a month. That is roughly ten times the original spec's $10.60 estimate, and it is no longer obviously trivial the way the original, lower-volume figure was; it is still small in absolute terms for a project at this scale, but the engineer should see this number plainly rather than have the 20x volume correction hidden inside an unchanged-looking dollar figure. If it reads as too high once feature 14's own UX is designed, the lever to pull is scoring fewer than all twenty listings per search, which is feature 14's own decision (recorded as a Follow-up in `index.md`), not a reason to under-provision `usage_cap` here. The token counts behind these dollar figures, roughly 2000 input and 500 output tokens for a scoring call (unchanged in kind, since the per-call shape, one listing plus one profile in, one score out, was already what this placeholder assumed) and 1000 input and 200 output tokens for a check call, remain placeholders reasoned from the shape of the task, not measured against a real prompt, since feature 14 and feature 17 do not exist yet; the scoring call's output estimate is adjusted up to ~1200 tokens for the reasoning-token reason given below.

**This arithmetic assumes exactly one vendor call per gated call.** `usage_cap` counts gate calls, since `checkUsageGate()` charges one budget unit per invocation regardless of what happens after. The AI SDK's own default `maxRetries` is 2, meaning a single gated call could make up to three real vendor calls if that default were left in place, which would move the true worst case from about $73.60 and $32 a month to about $220.80 and $96. `tiers.ts` therefore fixes `maxRetries: 0` for both tiers (recorded in `index.md`'s Build plan and Consequences), so the dollar figures above are also the real ceiling, not just the gated-call ceiling.

**Why `ai_scoring`'s output estimate moved from ~500 to ~1200 tokens.** GPT-5.6 Luna is a reasoning model: at any `reasoning.effort` other than `"none"`, it produces internal reasoning tokens before its visible answer, and those reasoning tokens are billed as output tokens even though the caller never sees them in the returned object. `"medium"` effort (this spec's fixed choice, see above) sits in the middle of a `none`-to-`max` range, and no real prompt exists yet to measure its actual reasoning-token count for this specific task, so ~1200 tokens (roughly 2.4x the original non-reasoning ~500 token placeholder) is a deliberately conservative placeholder, not a measured figure. Even at this more conservative estimate, GPT-5.6 Luna remains far cheaper than the original Claude Haiku 4.5 pick at the same corrected volume (~$73.60 vs ~$180 a month), so the vendor decision does not depend on this estimate landing exactly right; feature 16's eval harness, once real prompts exist, is what should replace this placeholder with a measured number.

**Privacy consequence of the sample rate.** At sample rate 1.0, every profile and job description sent to OpenAI for scoring is also sent to Google for the check, every time, not one vendor per call but two, and now twenty times per search rather than once (see the call shape correction above). `src/features/legal/recipients.test.ts` is the drift guard this feature's own build trips: it reads every variable name out of `src/env.ts` and fails unless each is accounted for in `DATA_RECIPIENTS`, so the suite breaks the moment either `OPENAI_API_KEY` or `GOOGLE_GENERATIVE_AI_API_KEY` is declared, which is why both registry entries are part of this feature's own build plan rather than a follow-up. Feature 14's own owed diligence, reading the vendor's terms on training and retention before real profile data flows through `ai_scoring` in production (recorded in scope.md and in `index.md`'s Follow-up), now names OpenAI's terms rather than Anthropic's; nothing about this revision reduces that obligation, it just changes whose terms need reading.

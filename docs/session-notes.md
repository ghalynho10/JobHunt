- The permission classifier that can block a merge does not fire every time. On 2026-08-23, `gh pr merge` was blocked once, for PR 5, and the engineer had to run it by hand. The very same command then went through with no block at all for PR 6, PR 7, and PR 8, and a `vercel promote` call also went through unblocked. So a merge or a promote may or may not be stopped, there is no way to know in advance, and the block is not something to route around if it does fire. The sharpest evidence came on 2026-08-26: `gh pr merge 14` went through and merged, then the same command shape for PR 15, seconds later in the same session, was blocked. A `git push` and a `gh pr create` for PR 12 went through unblocked that day too, and the engineer merged PR 12 and PR 15 by hand. So the block does not track the command, the repository, or the session; treat it as genuinely unpredictable. Keep asking the engineer to confirm before every merge exactly as AGENTS.md's Git section already requires, whether or not the classifier ends up blocking that particular attempt. Confirmed again on 2026-08-27 with a new wrinkle worth knowing: the classifier blocked `git filter-branch`, then blocked a plainly read only `git log --reverse` moments later in the same session, while `git push`, `gh pr merge` for pull requests 19 and 20, `git cherry-pick`, `git branch -D` and a remote branch delete all went through unblocked. So it can block reads too once it is in that mode. The response that worked was handing the engineer the exact commands to run, not retrying. On 2026-08-30 it fired on nothing at all: two pushes, two `gh pr create` calls and two `gh pr merge` calls all went through unblocked, which is more evidence that it does not track the command.
